🕓 Java Date & Time Cheatsheet

The modern java.time API (JSR-310, since Java 8) — immutable, thread-safe, and the only date library you should reach for. Small snippets, the Local/Zoned/Instant mental model, and how time zones & daylight saving actually work.

★ The 30-second mental model

Almost every date bug comes from confusing these three. Pick the one that matches what you actually mean.

LocalDate / LocalDateTime

A "wall clock" reading. No zone, no offset.

"June 10th, 9:00 AM" — but whose 9 AM? Unknown. Great for birthdays, business hours, a date on a form. Not a point on the global timeline.

ZonedDateTime

Wall clock + a real time zone.

"June 10th, 9:00 AM in America/New_York." Now it's unambiguous and DST-aware. Use for events tied to a place & for human display.

Instant

A machine timestamp — nanoseconds from the 1970 epoch, in UTC.

A single point on the global timeline, zone-free. Use for logs, "created_at", ordering events, and what you store in a DB.

Rule of thumb

 

Store an Instant (UTC). Display a ZonedDateTime. Use LocalDate only for things that genuinely have no zone (a birthday).

✅ All immutable & thread-safe
Every java.time type is immutable — methods like plusDays return a new object. You can share them across threads freely, and DateTimeFormatter is thread-safe (unlike the old SimpleDateFormat).

2 Creating & parsing

// now() — reads the system clock (pass a Clock to make it testable, see §9)
LocalDate today      = LocalDate.now();
LocalDateTime nowLdt = LocalDateTime.now();
Instant nowTs        = Instant.now();
ZonedDateTime nowNyc = ZonedDateTime.now(ZoneId.of("America/New_York"));

// of() — build explicitly (months are 1-based here, unlike the old Date!)
LocalDate d   = LocalDate.of(2026, 6, 10);          // 2026-06-10
LocalDate d2  = LocalDate.of(2026, Month.JUNE, 10); // same, more readable
LocalTime t   = LocalTime.of(9, 30);                // 09:30
LocalDateTime ldt = LocalDateTime.of(d, t);

// parse() — ISO-8601 by default; throws DateTimeParseException on bad input
LocalDate p   = LocalDate.parse("2026-06-10");
Instant i     = Instant.parse("2026-06-10T13:00:00Z");   // Z = UTC
ZonedDateTime z = ZonedDateTime.parse("2026-06-10T09:00:00-04:00[America/New_York]");

// epoch conversions (Unix time)
Instant fromMillis = Instant.ofEpochMilli(1_749_560_400_000L);
long millis        = nowTs.toEpochMilli();
long seconds       = nowTs.getEpochSecond();
📌 Months are 1-based in java.time
LocalDate.of(2026, 1, 1) is January 1st — sane. The old java.util.Calendar used 0-based months (a notorious bug source). One more reason never to go back.

3 Accessing, modifying & comparing

Every "mutator" returns a new value. Chain them; the original is untouched.

LocalDate d = LocalDate.of(2026, 6, 10);

// read parts
int year       = d.getYear();        // 2026
Month month    = d.getMonth();       // JUNE
DayOfWeek dow  = d.getDayOfWeek();   // WEDNESDAY
boolean leap   = d.isLeapYear();     // false

// plus / minus — returns a NEW LocalDate
LocalDate next = d.plusDays(5).minusMonths(1);   // 2026-05-15
LocalDateTime rounded = LocalDateTime.now()
        .truncatedTo(ChronoUnit.HOURS);          // chop off mins/secs

// with() — set one field
LocalDate firstOfMonth = d.withDayOfMonth(1);

// compare
boolean before = d.isBefore(next);   // true
boolean eq     = d.isEqual(next);    // false
int cmp        = d.compareTo(next);  // works in sorts / Comparator

// distance between two points — ChronoUnit, NOT manual millis math
long days  = ChronoUnit.DAYS.between(d, next);   // signed; negative if next < d
long hours = ChronoUnit.HOURS.between(Instant.now(), Instant.now().plusSeconds(7200));
⚠️ Never compute gaps with millis / 86_400_000
Manual epoch arithmetic breaks across DST and assumes every day is 24h. Use ChronoUnit.DAYS.between(a, b) — it's correct, signed, and readable. Use Math.abs(...) if you want an unsigned gap.

4 Period vs Duration — the subtle one

Both represent "an amount of time," but they answer different questions — and they diverge across DST.

Period

Date-based: years, months, days. "Calendar" thinking.
Period p = Period.between(
    LocalDate.of(2026,1,31),
    LocalDate.of(2026,3,1));     // 1 month, 1 day
LocalDate due = LocalDate.now()
    .plus(Period.ofMonths(2));   // calendar months

Duration

Time-based: hours, minutes, seconds, nanos. "Stopwatch" thinking.
Duration d = Duration.between(
    Instant.now(),
    Instant.now().plusSeconds(90));
Duration timeout = Duration.ofSeconds(30);
long mins = d.toMinutes();
📌 The DST gotcha they love to ask
Across a spring-forward day, zdt.plus(Period.ofDays(1)) and zdt.plus(Duration.ofHours(24)) give different results. "Plus 1 day" keeps the same wall-clock time (23h elapsed); "plus 24 hours" advances exactly 24h of real time (wall clock shifts by an hour). Period = calendar days, Duration = elapsed seconds.

5 Time zones

A ZoneId is a region with a full rulebook (offsets + when DST flips). A ZoneOffset is just a fixed gap from UTC with no rules.

// Region IDs come from the IANA tz database — always "Area/City", never "EST"
ZoneId nyc   = ZoneId.of("America/New_York");
ZoneId tokyo = ZoneId.of("Asia/Tokyo");
ZoneId utc   = ZoneOffset.UTC;
ZoneId sys   = ZoneId.systemDefault();          // the JVM's zone (avoid relying on it)

// attach a zone to a LocalDateTime → a real moment
LocalDateTime ldt = LocalDateTime.of(2026, 6, 10, 9, 0);
ZonedDateTime nycTime = ldt.atZone(nyc);        // 09:00 in New York

// SAME INSTANT, different wall clock — what you want for "show me this in Tokyo"
ZonedDateTime tokyoTime = nycTime.withZoneSameInstant(tokyo);   // 22:00 same day

// SAME WALL CLOCK, different instant — rarely what you want
ZonedDateTime literal  = nycTime.withZoneSameLocal(tokyo);      // 09:00 in Tokyo

// to/from the timeline
Instant instant = nycTime.toInstant();          // collapse to UTC point
ZonedDateTime back = instant.atZone(nyc);       // expand back into a zone
⚠️ Don't use 3-letter zone abbreviations
"EST", "PST", "IST" are ambiguous (IST = India? Israel? Ireland?) and ignore DST. Always use IANA region IDs like America/New_York or Asia/Kolkata. The offset for a region changes with DST — that's the whole point of a ZoneId.
📌 Offset vs Zone, for APIs
Sending a timestamp over JSON/HTTP? Prefer OffsetDateTime (2026-06-10T09:00-04:00) or an Instant in UTC. Don't ship a bare LocalDateTime — the receiver can't know which zone it meant.

6 Daylight Saving Time — gaps & overlaps

Twice a year the wall clock jumps. ZonedDateTime handles both cases for you — but you should know what it picks.

ZoneId nyc = ZoneId.of("America/New_York");

// --- GAP: 2026-03-08, clocks skip 02:00→03:00, so 02:30 doesn't exist ---
LocalDateTime gap = LocalDateTime.of(2026, 3, 8, 2, 30);
ZonedDateTime fixed = gap.atZone(nyc);
// fixed == 2026-03-08T03:30-04:00  (auto-shifted forward by 1h, now in EDT)

// --- OVERLAP: 2026-11-01, clocks repeat 01:00→01:59, so 01:30 happens twice ---
LocalDateTime overlap = LocalDateTime.of(2026, 11, 1, 1, 30);
ZonedDateTime earlier = overlap.atZone(nyc);                      // -04:00 (EDT), the default
ZonedDateTime later   = earlier.withLaterOffsetAtOverlap();       // -05:00 (EST)

// --- Period vs Duration across the spring-forward day ---
ZonedDateTime start = LocalDateTime.of(2026, 3, 8, 0, 30).atZone(nyc);
ZonedDateTime plusDay   = start.plus(Period.ofDays(1));     // 2026-03-09T00:30  (same wall time, 23h later)
ZonedDateTime plus24h   = start.plus(Duration.ofHours(24)); // 2026-03-09T01:30  (24h real time, clock +1h)
✅ What to remember about DST
  • Do zone-aware math on ZonedDateTime — it applies DST rules automatically.
  • Do elapsed-time math on Instant — no zone, no DST, always linear UTC.
  • Gaps shift forward; overlaps default to the earlier offset.
  • Never bake an offset (like -05:00) into stored data for a future event in a DST zone — store the ZoneId and resolve later, because the rules can change.

7 Formatting & parsing

// Built-in ISO formatters (no pattern needed)
LocalDate.now().format(DateTimeFormatter.ISO_LOCAL_DATE);   // 2026-06-10

// Custom pattern
DateTimeFormatter f = DateTimeFormatter.ofPattern("EEE, dd MMM yyyy  HH:mm")
        .withLocale(Locale.US);
String s = LocalDateTime.now().format(f);   // "Wed, 10 Jun 2026  14:05"

// Parse with the same formatter
LocalDateTime back = LocalDateTime.parse("Wed, 10 Jun 2026  14:05", f);

// Formatting an Instant REQUIRES a zone (an Instant has no local fields)
DateTimeFormatter withZone = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm z")
        .withZone(ZoneId.of("America/New_York"));
String shown = withZone.format(Instant.now());

⚠️ The classic pattern bugs
YYYY instead of yyyy silently breaks the last/first week of the year. mm vs MM swaps minutes and months. DD vs dd gives day-of-year. Always lowercase-d day, lowercase-m minute, uppercase-M month, lowercase-y year.

8 Talking to legacy Date / Calendar

You'll still meet old APIs. Convert at the boundary, then work in java.time.

// java.util.Date  <->  Instant
Date legacy   = Date.from(Instant.now());
Instant fromLegacy = legacy.toInstant();

// java.sql types
java.sql.Date   sqlDate = java.sql.Date.valueOf(LocalDate.now());
LocalDate fromSql       = sqlDate.toLocalDate();

// Calendar (avoid; convert out fast)
ZonedDateTime z = ((GregorianCalendar) Calendar.getInstance())
        .toZonedDateTime();
⚠️ Things to retire
  • java.util.Date — mutable, no zone, half its methods deprecated.
  • Calendar — mutable, 0-based months, clumsy.
  • SimpleDateFormat — not thread-safe; a shared static instance corrupts under load. DateTimeFormatter replaces it and is thread-safe.
  • Joda-Time — was the gold standard pre-Java-8; java.time is its official successor by the same author. New code uses java.time.

9 Testing time — inject a Clock

The single most useful trick: never call now() with no argument inside business logic. Pass a Clock (or a fixed "today") so tests are deterministic.

// Production wiring uses the real clock
Clock clock = Clock.systemDefaultZone();

// Tests freeze time — now() becomes 100% reproducible
Clock fixed = Clock.fixed(
        Instant.parse("2026-06-10T00:00:00Z"), ZoneOffset.UTC);

LocalDate today = LocalDate.now(fixed);          // always 2026-06-10
Instant   stamp = Instant.now(fixed);            // always that instant

// Inject it, don't hardcode now() deep in a method:
class BirthdayService {
    private final Clock clock;
    BirthdayService(Clock clock) { this.clock = clock; }
    boolean isBirthdayToday(LocalDate bday) {
        LocalDate today = LocalDate.now(clock);   // testable!
        return MonthDay.from(bday).equals(MonthDay.from(today));
    }
}
✅ Also handy
Clock.offset(base, Duration.ofHours(2)) shifts time, and Clock.tick(...) truncates resolution — both useful for simulating schedules in tests.

📌 The golden rule
Persist in UTC (an Instant or timestamptz), convert to the user's zone only at the edges (display, input). The one exception: a future wall-clock event in a specific zone (a 9 AM meeting next year) — store the local time + the ZoneId, because if the government changes DST rules, "9 AM local" must still mean 9 AM.

11 Lesser-known types worth knowing

MonthDay

month + day, no year — perfect for recurring birthdays
MonthDay bday = MonthDay.of(2, 29);
LocalDate occ = bday.atYear(2027); // throws! 2027 not leap
// → catch DateTimeException, fall back to Feb 28

YearMonth

year + month — card expiry, billing periods
YearMonth ym = YearMonth.of(2026, 6);
int len = ym.lengthOfMonth();   // 30
LocalDate end = ym.atEndOfMonth();

TemporalAdjusters

"next Friday", "last day of month"
import static java.time.temporal.TemporalAdjusters.*;
LocalDate d = LocalDate.now()
    .with(next(DayOfWeek.FRIDAY));
LocalDate eom = LocalDate.now()
    .with(lastDayOfMonth());

Year / DayOfWeek / Month

tiny but type-safe
boolean leap = Year.of(2028).isLeap(); // true
DayOfWeek d = LocalDate.now().getDayOfWeek();
boolean weekend = d == DayOfWeek.SATURDAY
                || d == DayOfWeek.SUNDAY;
📌 Need more?
The ThreeTen-Extra library (same author) adds Interval, YearWeek, DayOfYear, and more — only if the JDK types don't cover you. The JDK's java.time handles ~99% of needs.

12 Top gotchas — quick scan

⚠️ The ones that bite
  • LocalDateTime is not a moment. Without a zone it can't be ordered globally or stored as a timestamp.
  • millis ÷ 86,400,000 for day-gaps → wrong across DST. Use ChronoUnit.DAYS.between.
  • 3-letter zones ("EST") are ambiguous & DST-blind. Use IANA Area/City.
  • SimpleDateFormat shared statically → data races. Use DateTimeFormatter.
  • YYYY / DD / mm in patterns → week-year / day-of-year / minutes. Mind the case.
  • Feb 29 + 1 year throws via atYear() — handle leap years explicitly.
  • LocalDate.now() inside logic → untestable. Inject a Clock.
  • Storing an offset for a future zoned event → breaks if DST rules change. Store the ZoneId.
  • Period vs Duration aren't interchangeable: calendar days ≠ 24-hour blocks across DST.
