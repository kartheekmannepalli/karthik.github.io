🧨 Exceptions

Everything throwable inherits from Throwable. The only split that matters day-to-day: checked (compiler forces you to handle or declare) vs unchecked (RuntimeException — your code's bugs, free to propagate).

try / catch / finally — the flow 
try {
    riskyIO();                  // may throw
} catch (FileNotFoundException e) {  // specific first
    log(e);
} catch (IOException e) {            // broader after
    throw new UncheckedIOException(e); // wrap & rethrow
} finally {
    cleanup();   // ALWAYS runs — even on return/throw
}

Order matters: a broader catch above a narrower one is a compile error. finally runs no matter what (except System.exit / JVM death).

try-with-resources — the modern cleanup 
try (BufferedReader r = Files.newBufferedReader(p)) {
    return r.readLine();
}   // r.close() called automatically, even on throw

Anything implementing AutoCloseable goes in the parentheses. Replaces 90% of finally blocks. Multiple resources close in reverse order.

Writing a custom exception — the right way 
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(String msg) {
        super(msg);              // getMessage() for free
    }
    public OrderNotFoundException(String msg, Throwable cause) {
        super(msg, cause);       // keep the cause chain!
    }
}

Pass the message to super() — never store your own mutable message field. Always offer a (msg, cause) constructor so stack traces stay connected.

Classic pitfalls
  • ✘ catch (Exception e) {} — swallowing silently
  • ✘ Catch-log-rethrow at every layer → duplicate noise
  • ✘ throw new X(e.getMessage()) — loses the cause; pass e itself
  • ✘ Exceptions for control flow — they're ~1000× slower than an if
  • ✔ Catch late, throw early, handle once

🧵 Threads & Synchronization

A Thread is the worker; a Runnable is the task. Keep them separate: implement Runnable (or use a lambda), hand it to a Thread or — better — an executor.

Creating threads ✓ preferred 
// task = Runnable (lambda), worker = Thread
Runnable task = () -> System.out.println(
        Thread.currentThread().getName());

Thread t = new Thread(task, "worker-1");
t.start();   // NOT t.run() — run() executes on the CURRENT thread!
t.join();    // wait for it to finish

implements Runnable beats extends Thread: keeps your superclass slot free, separates the task from the machinery, and works with executors.

The #1 beginner bug 
t.run();    ✘ runs synchronously on the caller
t.start();  ✔ JVM creates a new OS thread → calls run()
  • 🔹 start() can be called once per Thread object
  • 🔹 Daemon threads (setDaemon(true)) die when main exits
  • 🔹 No join() → main may finish before workers

🔒 synchronized — one lock per object

Every Java object has one built-in lock (its monitor). synchronized means "acquire that lock first". Only one thread can hold a given monitor at a time — everyone else queues.

Canonical example — a safe counter 
class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
    public synchronized int  get()       { return count; }
}
// without synchronized: count++ is read→add→write,
// two threads interleave and updates get lost (race condition)
Remember
  • 🔑 Lock is on the object, never on the method — two synchronized methods of one object block each other
  • 🔑 static synchronized locks the Class object — a different lock entirely
  • 🔑 synchronized gives mutual exclusion + visibility; volatile gives visibility only
  • 🔑 Deadlock recipe: two threads acquiring two locks in opposite order — always lock in a consistent order
  • 🔑 Often skip all this: AtomicInteger, ConcurrentHashMap

⏸️ sleep · wait · join · interrupt

Four ways a thread pauses — they look similar but live in different worlds: sleep/join are Thread methods, wait/notify are Object methods tied to the monitor lock.

Belongs toNeeds the lock?Releases the lock?Wakes up whenTypical use
sleep(ms)Thread (static)No✘ keeps it!timer expires / interruptthrottle, retry backoff
wait()Object✔ must hold it✔ releases itnotify() / timeout / interruptwait for a condition
join()Thread (instance)No—that thread terminateswait for a worker to finish
yield()Thread (static)No—just a scheduler hintalmost never — don't rely on it

💡 The interview classic: sleep keeps the lock, wait releases it. That's why wait() must be on Object — it's part of the monitor mechanics, not the thread.

wait / notify — the canonical shape 
synchronized (queue) {                // MUST hold the lock
    while (queue.isEmpty())            // while, NEVER if
        queue.wait();                  // releases lock, parks
    item = queue.remove();
}

synchronized (queue) {                // producer side
    queue.add(item);
    queue.notifyAll();                 // safer than notify()
}

Three iron rules: ① call inside synchronized on the same object or get IllegalMonitorStateException ② loop on the condition — spurious wakeups are real ③ prefer notifyAll(). In practice: just use BlockingQueue and skip all this.

join & interrupt 
Thread worker = new Thread(task);
worker.start();
worker.join(5000);          // wait ≤5s for it to die

worker.interrupt();          // polite stop request —
                             // just sets a flag
// inside the worker:
while (!Thread.currentThread().isInterrupted()) {
    try { doChunk(); Thread.sleep(100); }
    catch (InterruptedException e) {
        Thread.currentThread().interrupt();  // restore flag
        break;
    }
}

There is no safe "kill thread" in Java (stop() is deprecated for good reason). Interruption is cooperative: blocking calls (sleep, wait, join) throw InterruptedException and clear the flag — restore it before swallowing.

🧰 Concurrency toolbox

Visibility, atomicity, and the java.util.concurrent classes that replace hand-rolled wait/notify code.

👁️ volatile vs synchronized vs Atomic

volatile 
private volatile boolean running = true;
// writer: running = false;
// reader loop sees it immediately

Visibility only — not atomic. Perfect for flags. volatile int count++ is still a race (read+add+write).

Atomic* 
AtomicInteger hits = new AtomicInteger();
hits.incrementAndGet();      // lock-free CAS
hits.compareAndSet(5, 10);

Visibility + atomicity for a single variable, no locks (compare-and-swap). Also AtomicLong, AtomicReference, LongAdder for hot counters.

synchronized / Lock 
synchronized (this) {
    balance -= amt;        // multi-step
    audit.add(entry);      // invariant across fields
}

Visibility + atomicity for compound actions spanning multiple variables. The heavyweight option — use when invariants involve more than one field.

🔐 ReentrantLock — synchronized with superpowers

private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try { doCriticalWork(); }
finally { lock.unlock(); }   // ALWAYS in finally

// what synchronized can't do:
if (lock.tryLock(2, TimeUnit.SECONDS)) { … }  // give up
lock.lockInterruptibly();                       // cancellable

When to upgrade from synchronized

  • ⏲️ tryLock with timeout — avoid waiting forever (deadlock escape hatch)
  • 🛑 lockInterruptibly — waiting thread can be cancelled
  • ⚖️ Fairness — new ReentrantLock(true) = FIFO, no starvation
  • 📖 ReadWriteLock — many concurrent readers, exclusive writer
  • 🔔 Condition — lock.newCondition(): multiple wait-sets per lock (wait/notify allows only one)

Default to synchronized; reach for ReentrantLock only when you need one of these.

🚦 Coordination utilities — stop hand-rolling wait/notify

CountDownLatch — "wait until N things happen" 
CountDownLatch ready = new CountDownLatch(3);
// 3 workers each call:  ready.countDown();
ready.await();   // main unblocks when count hits 0
// one-shot: cannot be reset
CyclicBarrier — "everyone meets here" 
CyclicBarrier barrier = new CyclicBarrier(3,
        () -> merge());      // runs when all arrive
// each worker: barrier.await();
// reusable — resets after each round
Semaphore — "at most N at a time" 
Semaphore permits = new Semaphore(10);
permits.acquire();           // blocks if 10 in use
try { callRateLimitedApi(); }
finally { permits.release(); }
BlockingQueue — producer/consumer, solved 
BlockingQueue<Job> q = new ArrayBlockingQueue<>(100);
q.put(job);     // blocks when full  (producer)
Job j = q.take(); // blocks when empty (consumer)
// all the wait/notify logic, built in & correct

💀 Deadlock — the circular wait

🔍
Diagnosing a live deadlock

jstack <pid> (or jcmd <pid> Thread.print) prints all stacks and literally says "Found one Java-level deadlock" with the lock cycle. Related diseases: livelock (threads keep reacting, no progress) and starvation (low-priority thread never gets the lock — fair locks fix it).

⚙️ ExecutorService

Creating a thread per task is expensive (~1 MB stack each, OS calls). An executor keeps a pool of reusable threads pulling tasks off a queue. You submit tasks; it handles the threads.

The standard pattern 
ExecutorService pool = Executors.newFixedThreadPool(8);
try {
    for (int i = 0; i < 100; i++)
        pool.execute(() -> doWork());   // fire & forget
} finally {
    pool.shutdown();                      // graceful
    if (!pool.awaitTermination(30, TimeUnit.SECONDS))
        pool.shutdownNow();               // force
}
// Java 19+: try (var pool = …) { } — auto shutdown+await
Pool flavors
FactoryBehavior
newFixedThreadPool(n)n threads, unbounded queue — the default choice
newCachedThreadPool()grows on demand, kills idle threads — bursty short tasks
newSingleThreadExecutor()1 thread — tasks run in order
newScheduledThreadPool(n)delayed / periodic tasks
newVirtualThreadPerTaskExecutor()Java 21+ — a cheap virtual thread per task, great for blocking I/O
📏
Sizing rule of thumb

CPU-bound work → pool ≈ number of cores. I/O-bound work → much larger (threads mostly wait), or just use virtual threads on Java 21+.

⚠️
Gotcha: execute() swallows nothing — it crashes the thread

An exception in execute() kills the worker (pool replaces it) and prints to stderr. With submit() the exception is captured inside the Future and is silent until you call get(). Always retrieve your futures.

🔮 Callable + Future

Runnable can't return anything. Callable<V> returns a value and may throw. submit() gives you back a Future<V> instantly — a claim ticket 🎟️ you redeem later with get().

Runnable
void run()

No result, no checked exceptions. Use with execute().

Callable<V>
V call() throws Exception

Returns a value, may throw. Use with submit().

Future<V>
get() · get(timeout)
cancel() · isDone()

The handle to a pending result.

Fan-out / fan-in — the classic use 
List<Callable<Integer>> jobs = urls.stream()
        .map(u -> (Callable<Integer>) () -> fetchSize(u))
        .toList();

// submit ALL, wait for ALL:
List<Future<Integer>> results = pool.invokeAll(jobs);

int total = 0;
for (Future<Integer> f : results)
    total += f.get();   // all done already — no waiting

Submit everything first, then collect. Calling get() right after each submit() serializes the work — a classic mistake.

CompletableFuture — when blocking hurts 
CompletableFuture
    .supplyAsync(() -> fetchUser(id))      // async
    .thenApply(user -> enrich(user))        // chain
    .thenAccept(u -> render(u))             // consume
    .exceptionally(ex -> { log(ex); return null; });

Plain Future.get() blocks a thread. CompletableFuture lets you chain callbacks instead — compose, combine, recover, no blocking.

⚠️
get() pitfalls to remember

Always prefer get(timeout, unit) — a hung task otherwise hangs you forever. ExecutionException wraps the real error (getCause()). On InterruptedException, restore the flag: Thread.currentThread().interrupt().

🗺️ Which one when

30-second recall

  • 🧨 Checked = compiler makes you deal with it; unchecked = RuntimeException, usually a bug
  • 🧨 Custom exception = super(msg, cause), nothing else
  • 🧵 start() spawns; run() doesn't · prefer Runnable over extends Thread
  • 🔒 Lock lives on the object; synchronized method ≡ synchronized(this)
  • ⏸️ sleep keeps the lock, wait releases it · wait in a while loop · join = wait for death
  • 🛑 interrupt() is a request, not a kill — restore the flag after catching
  • 👁️ volatile = visibility · Atomic = one-variable atomicity · synchronized = compound actions
  • 🚦 Latch = wait for N · Barrier = meet up · Semaphore = at most N · BlockingQueue = producer/consumer
  • ⚙️ Executor = queue + reusable threads · shutdown + awaitTermination
  • 🔮 Callable returns, Future is the ticket, get() blocks — submit all, then collect

Modern Java upgrades (since this code was written)

  • ☕ Lambdas: pool.execute(() -> work()) — no more one-class-per-task
  • ☕ try-with-resources on executors (19+) — auto shutdown
  • ☕ Virtual threads (21+) — Thread.ofVirtual(), millions of cheap threads
  • ☕ CompletableFuture (8+) replaces most raw Future juggling
  • ☕ Thread.getId() deprecated → threadId() (19+)
