Creational Patterns

How objects come into existence. Hide construction complexity, decouple clients from concrete classes, control instance lifecycle.

🏭 Factory Method Must Know
Defines an interface for creating an object but lets a factory method (often overridden by subclasses) decide which concrete class to instantiate. Reach for it when the right concrete class depends on runtime context — region, tenant, config — and clients shouldn't have to know about that decision.
⚙️ Implementation 
public interface CarrierFactory {
  Carrier create(String region);
}
class USCarrierFactory implements CarrierFactory {
  public Carrier create(String r) {
    return new USPSAdapter();
  }
}
▶ How it's called 
CarrierFactory factory = factoryFor(req.region());
Carrier carrier = factory.create(req.region());
RateQuote quote = carrier.quoteRates(req);
eBay: Region-driven carrier selection — US gets USPS/FedEx, EU gets DHL/Hermes — without callers knowing the mapping.
🏢 Abstract Factory Common
Creates families of related objects that must work together, without specifying their concrete classes. Each concrete factory produces a coordinated set of products — switching factories swaps the whole family at once, guaranteeing they're compatible.
⚙️ Implementation 
public interface RegionFactory {
  Carrier carrier();
  TaxCalculator taxes();
  AddressValidator addresses();
}

class USRegionFactory implements RegionFactory {
  public Carrier carrier()         { return new USPSAdapter(); }
  public TaxCalculator taxes()    { return new USSalesTax(); }
  public AddressValidator addresses() { return new USPSValidator(); }
}

class EURegionFactory implements RegionFactory {
  public Carrier carrier()         { return new DHLAdapter(); }
  public TaxCalculator taxes()    { return new VATCalculator(); }
  public AddressValidator addresses() { return new EUAddressValidator(); }
}
▶ How it's called 
RegionFactory region = order.isEU()
    ? new EURegionFactory()
    : new USRegionFactory();

Money tax = region.taxes().compute(order);
Address valid = region.addresses().normalize(order.address());
Label label = region.carrier().generateLabel(order);
// Guaranteed: all 3 are compatible with the chosen region
eBay: Regional bundles. Picking EU mode gives you DHL + VAT + EU-format addresses together — impossible to accidentally mix US tax rules with a DHL shipment.
⚠️ Don't reach for it if the products are truly independent. Factory Method × N is simpler when there's no coordination requirement between them.
🏗️ Builder Must Know
Constructs complex objects step-by-step with a fluent API, separating construction from representation. Eliminates telescoping constructors when an object has many optional fields, and the build step naturally validates invariants before producing an immutable result.
⚙️ Implementation 
@Builder
public record Shipment(
  Address from, Address to,
  double weight, Service service,
  boolean insured, boolean signatureRequired) {}
// Lombok generates the builder. Or hand-roll a static inner class.
▶ How it's called 
Shipment s = Shipment.builder()
    .from(origin)
    .to(destination)
    .weight(2.5)
    .service(PRIORITY)
    .insured(true)
    .build();
shippingService.dispatch(s);
eBay: Building shipping requests, search queries, REST DTOs with 8+ optional fields. Reads top-to-bottom in code reviews.
🔒 Singleton Use Carefully
Guarantees a class has exactly one instance and provides a global access point. In Spring, you almost never write this by hand — every bean is a singleton by default. Hand-rolled singletons are usually a code smell: they hurt testability and hide concurrency assumptions.
⚙️ Implementation 
// Spring way (preferred — singleton by default)
@Service
class RateCache { /* ... */ }

// Hand-rolled (last resort, e.g. utility config)
public enum AppConfig {
  INSTANCE;
  public String get(String key) { /* ... */ }
}
▶ How it's called 
// Spring way — DI gives you the singleton
@Service
class Quoter {
  private final RateCache cache;
  Quoter(RateCache cache) { this.cache = cache; }
}

// Hand-rolled access
String region = AppConfig.INSTANCE.get("region");
⚠️ Gotcha: Hand-rolled singletons hurt testability (can't substitute fakes) and hide concurrency bugs. Prefer DI almost always.
🐑 Prototype Niche
Creates new objects by cloning an existing prototype — useful when building from scratch is expensive but cloning is cheap. Largely superseded in modern Java by records with "with-methods" (functional updates that return new instances).
⚙️ Implementation 
public record RateTemplate(
    String service, double base, double fuelSurcharge) {

  public RateTemplate withBase(double b) {
    return new RateTemplate(service, b, fuelSurcharge);
  }
}
▶ How it's called 
RateTemplate standard = RateTemplate.standard();
RateTemplate discounted = standard.withBase(standard.base() * 0.9);
// Original 'standard' is untouched; discounted is a fresh instance
eBay: Copy-on-write for rate templates and immutable config snapshots that need slight per-tenant variations.
🧱

Structural Patterns

How objects compose. Bridge incompatible interfaces, add behavior dynamically, hide complexity behind clean facades.

🔌 Adapter Must Know
Wraps an incompatible third-party or legacy interface so it conforms to one your code already expects. The translator between your clean domain and a messy external SDK — keeps the external system's quirks from leaking into your business logic. The #1 pattern for integration work.
⚙️ Implementation 
interface Carrier { RateQuote quote(Req r); }

class FedExAdapter implements Carrier {
  private final FedExClient client; // 3rd-party SDK

  public RateQuote quote(Req r) {
    var resp = client.getRates(toFedExReq(r));
    return toRateQuote(resp);
  }
}
▶ How it's called 
Carrier fedex = new FedExAdapter(fedExClient);
Carrier ups   = new UPSAdapter(upsClient);

List<Carrier> all = List.of(fedex, ups);
all.forEach(c -> log.info(c.quote(req)));
// Caller never touches FedExClient or UPSClient directly
eBay: Every carrier integration on the Shipping team. USPS, FedEx, UPS, DHL each get an adapter conforming to the same Carrier interface.
🎨 Decorator Must Know
Wraps an object to add behavior without modifying the wrapped class or other wrappers around it. Each layer adds exactly one responsibility — composable, unlike inheritance which forces fixed combinations. Powerful for layering cross-cutting concerns like caching, metrics, and resilience.
⚙️ Implementation 
class CachingCarrier implements Carrier {
  private final Carrier delegate;
  private final Cache cache;
  public RateQuote quote(Req r) {
    return cache.get(r, () -> delegate.quote(r));
  }
}
▶ How it's called 
Carrier raw = new FedExAdapter(client);
Carrier carrier = new MetricsCarrier(
    new CachingCarrier(
        new CircuitBreakerCarrier(raw)));

RateQuote q = carrier.quote(req);
// Routes through metrics -> cache -> circuit breaker -> raw call
eBay: Wrap a carrier adapter with metrics + caching + circuit breaker. Compose like Russian dolls; each layer is testable in isolation.
🏛️ Facade Must Know
Hides a complex subsystem behind a single high-level interface. The caller doesn't need to know about the 4 services or the orchestration logic underneath — they just call buy(). Reduces coupling between layers and gives you one place to evolve the orchestration.
⚙️ Implementation 
@Service
class ShippingFacade {
  public LabelResult buyAndPrint(Order o) {
    var rates  = rateService.quote(o);
    var picked = rateService.cheapest(rates);
    payments.charge(o.seller(), picked.cost());
    return labels.generate(o, picked);
  }
}
▶ How it's called 
@RestController
class SellerController {
  private final ShippingFacade shipping;

  @PostMapping("/orders/{id}/ship")
  LabelResult ship(@PathVariable Long id) {
    return shipping.buyAndPrint(orderRepo.find(id));
  }
}
eBay: One endpoint orchestrates rate quote + payment + label gen + notification. Controllers stay thin; the facade owns the choreography.
🪞 Proxy Common
Stand-in for the real object that controls access — for lazy loading, access control, remote calls, or AOP cross-cutting concerns. Spring is built on proxies: every @Transactional, @Cacheable, or @Async annotation generates a dynamic proxy at runtime.
⚙️ Implementation 
// Spring auto-creates the proxy
@Service
class OrderService {

  @Transactional
  public void place(Order o) {
    orderRepo.save(o);
    inventory.reserve(o);
    // commits or rolls back as one txn
  }
}
▶ How it's called 
@Autowired OrderService orders;  // Actually a Spring proxy

orders.place(order);
// Proxy: begin txn -> real place() -> commit (or rollback on throw)
⚠️ Self-invocation bypasses the proxy! Calling this.place() from another method in the same class skips @Transactional entirely. Extract to a separate bean if you need this.
🌳 Composite Niche
Treats individual objects and groups of objects uniformly through a shared interface. Useful for tree structures where a node can be either a leaf or a container of more nodes, and clients shouldn't care which.
⚙️ Implementation 
interface Validator<T> {
  Result check(T t);
}
class CompositeValidator<T> implements Validator<T> {
  private final List<Validator<T>> children;
  public Result check(T t) {
    return children.stream()
        .map(v -> v.check(t))
        .reduce(Result.ok(), Result::merge);
  }
}
▶ How it's called 
Validator<Shipment> all = new CompositeValidator<>(List.of(
    new WeightValidator(),
    new AddressValidator(),
    new CarrierCompatValidator()));

Result r = all.check(shipment);  // runs all 3
eBay: Shipment validation chains, fraud rule trees, hierarchical category trees in search.
🎭

Behavioral Patterns

How objects interact and distribute responsibility. Algorithms, communication flows, state management.

🎯 Strategy Must Know
Encapsulates interchangeable algorithms behind a common interface and lets clients pick one at runtime. The dependency-injection version of polymorphism — when you "inject an interface" in Spring, you're using Strategy. The most common pattern in modern Java code, usually unnamed.
⚙️ Implementation 
interface PricingStrategy {
  double price(Shipment s);
}
class FlatRatePricing    implements PricingStrategy { ... }
class WeightBasedPricing implements PricingStrategy { ... }

class Quoter {
  private final PricingStrategy strategy;
  Quoter(PricingStrategy s) { this.strategy = s; }
  public double price(Shipment s) { return strategy.price(s); }
}
▶ How it's called 
PricingStrategy strategy = req.isPremium()
    ? new WeightBasedPricing()
    : new FlatRatePricing();

double cost = new Quoter(strategy).price(shipment);
// Swap algorithms without touching Quoter
eBay: Pricing strategies per region/SLA, search-ranking algorithms, fraud-scoring models. Pluggable behavior is everywhere.
👀 Observer / Pub-Sub Must Know
Decouples producers from consumers — one state change notifies many subscribers without the producer knowing who they are. In-process via Spring ApplicationEventPublisher; across services via Kafka or SNS. Same shape, different scale.
⚙️ Implementation 
@Component
class OrderService {
  @Autowired ApplicationEventPublisher events;

  void ship(Order o) {
    // ... ship logic ...
    events.publishEvent(new OrderShipped(o.id()));
  }
}

@Component
class NotificationListener {
  @EventListener
  void handle(OrderShipped e) { sendEmail(e); }
}
▶ How it's called 
// Producer just fires the event
orderService.ship(order);

// All registered @EventListener methods get invoked.
// Producer doesn't know about NotificationListener,
// AnalyticsListener, FraudListener, etc.
eBay: Tracking events fan out to notifications, analytics, fraud detection, search re-indexing — all decoupled via Kafka.
📜 Command Common
Wraps a request as an object, decoupling who asks for something from who performs it. Enables queuing, retrying, logging, and undoing — useful any time a unit of work needs to be persisted, scheduled, or audited.
⚙️ Implementation 
interface Command { void execute(); }

class VoidLabelCmd implements Command {
  private final String labelId;
  private final CarrierClient client;
  public void execute() { client.voidLabel(labelId); }
}
▶ How it's called 
Command voidIt = new VoidLabelCmd(labelId, carrierClient);
queue.submit(voidIt);
// Worker thread pulls and runs it later.
// Can be retried on failure, logged for audit, persisted across restarts.
eBay: Async job queue — every action (void label, refund, send notification) wrapped as a Command for retryable, auditable execution.
🔗 Chain of Responsibility Common
Passes a request along a chain of handlers, each free to process or forward. Filter chains, middleware, and validation pipelines all use this pattern — each handler does its slice without knowing what comes before or after.
⚙️ Implementation 
interface Handler {
  Response handle(Req r, Handler next);
}
class AuthHandler implements Handler {
  public Response handle(Req r, Handler next) {
    if (!authed(r)) return Response.deny();
    return next.handle(r, next);
  }
}
▶ How it's called 
Handler chain = build(
    new AuthHandler(),
    new RateLimitHandler(),
    new FraudHandler(),
    new BusinessLogicHandler());

Response resp = chain.handle(request, null);
// Each handler runs in order; any can short-circuit the chain
eBay: Spring Security filter chains. Servlet filters. Fraud pipelines (rate limit → auth → KYC → ML score → decision).
📋 Template Method Common
Defines the skeleton of an algorithm in a base class and lets subclasses override specific steps. Useful when 80% of the algorithm is fixed but a few steps vary. Often a worse choice than Strategy — inheritance is rigid; composition adapts.
⚙️ Implementation 
abstract class CarrierBase implements Carrier {
  public final RateQuote quote(Req r) {
    var validated = validate(r);
    var rates     = fetchRates(validated);   // hook
    return applyMargin(rates);
  }
  protected abstract List<Rate> fetchRates(Req r);
}

class FedExCarrier extends CarrierBase {
  protected List<Rate> fetchRates(Req r) { /* ... */ }
}
▶ How it's called 
Carrier fedex = new FedExCarrier();
RateQuote q = fedex.quote(req);
// Runs the base's validate -> fetchRates(subclass) -> applyMargin
eBay: Standardize the carrier-call lifecycle (validate → fetch → transform → emit metrics) while letting each subclass customize only the fetch step.
🚦 State Must Know
Encodes valid state transitions in code so illegal transitions become compile-time or fast runtime errors. Critical for money flows and lifecycle objects — prevents bugs like double-charging or voiding an already-used label.
⚙️ Implementation 
enum LabelState {
  REQUESTED, PURCHASED, GENERATED,
  USED, VOIDED, REFUNDED;

  boolean canVoid() {
    return this == PURCHASED || this == GENERATED;
  }
  boolean canUse() { return this == GENERATED; }
}
▶ How it's called 
if (!label.state().canVoid()) {
  throw new IllegalStateException(
    "Cannot void label in state " + label.state());
}
label.transitionTo(VOIDED);
// Same check protects against double-void, double-refund
eBay: Shipping label state machine — prevents double-charging, double-voiding, refunding a used label. Order lifecycle works the same way.
🔄 Iterator Built-in
Provides a way to traverse a collection without exposing its underlying structure. Java gives you this for free via Iterable and streams — but worth knowing for cursor-based APIs that lazily fetch over remote data.
⚙️ Implementation 
class PagedShipments implements Iterable<Shipment> {
  private final ShipmentApi api;
  private final Long sellerId;

  public Iterator<Shipment> iterator() {
    return new CursorIterator(api, sellerId);
  }
}
▶ How it's called 
PagedShipments shipments = new PagedShipments(api, sellerId);

for (Shipment s : shipments) {  // fetches one page at a time
    process(s);
}
// Never loads 10M shipments into memory at once
eBay: Cursor-based pagination over millions of shipments. Generator-style traversal of huge tracking-event archives.
🎪 Visitor Niche
Lets you perform many unrelated operations on a stable object hierarchy without modifying the objects. Largely superseded in modern Java by sealed interfaces + switch pattern matching, which is far less ceremony and just as exhaustive.
⚙️ Implementation 
sealed interface Event
  permits PickedUp, InTransit, Delivered {}

record PickedUp(Instant at) implements Event {}
record InTransit(String location) implements Event {}
record Delivered(String signedBy) implements Event {}
▶ How it's called 
String describe(Event e) {
  return switch (e) {
    case PickedUp p  -> "Picked up at " + p.at();
    case InTransit t -> "In transit near " + t.location();
    case Delivered d -> "Delivered to " + d.signedBy();
  };
}
// Compiler enforces exhaustiveness — add a new permits and it won't compile
eBay: Processing tracking event types. Modern Java pattern matching beats classical Visitor on every dimension.

Concurrency Patterns

Critical for Staff-level Java interviews. These come up in code rounds, not just design. Master CompletableFuture, immutability, and the JDK concurrency primitives.

🧊 Immutable Objects Must Know
Object state cannot change after construction. Thread-safe by definition, safe to share across threads and cache layers without locks. Modern Java's record gives you immutability, equals, hashCode, toString, and accessors in one line.
⚙️ Implementation 
public record RateQuote(
  String carrier,
  String service,
  Money price,
  Duration eta
) {
  public RateQuote withPrice(Money p) {
    return new RateQuote(carrier, service, p, eta);
  }
}
▶ How it's called 
RateQuote q = new RateQuote("FedEx", "GROUND",
    Money.usd(12.50), Duration.ofDays(3));

RateQuote discounted = q.withPrice(q.price().multiply(0.9));
// Original q is untouched. Safe to pass to caches, other threads, etc.
eBay: All DTOs, value objects (Money, Address, Weight), and events. Pass safely across threads without defensive copying.
🔮 CompletableFuture Must Know
Async composition primitive — chain operations, fan out in parallel, apply timeouts, fall back on error. Required vocabulary for backend interviews; expected fluency at the Staff level for any non-trivial async Java code.
⚙️ Implementation 
// Fan-out with per-task timeout + fallback
List<CompletableFuture<Quote>> futures = carriers.stream()
    .map(c -> CompletableFuture
        .supplyAsync(() -> c.quote(req), pool)
        .orTimeout(200, MILLISECONDS)
        .exceptionally(ex -> Quote.empty()))
    .toList();
▶ How it's called 
List<Quote> results = futures.stream()
    .map(CompletableFuture::join)
    .filter(Quote::nonEmpty)
    .toList();
// Block once at the end. Get whatever returned in time.
// Slow carriers drop out; fast ones contribute.
eBay: Parallel carrier rate lookups. Compose downstream calls with strict per-call timeouts to keep p99 under SLO.
📦 Producer-Consumer Common
Decouples production rate from consumption rate via a bounded queue. Producers can spike without blocking; consumers process at their own pace. The queue provides natural backpressure when it fills up.
⚙️ Implementation 
private final BlockingQueue<Event> queue =
    new LinkedBlockingQueue<>(10_000);

// Worker thread, started at boot
void worker() {
  while (running) {
    Event e = queue.take();  // blocks if empty
    process(e);
  }
}
▶ How it's called 
// Producer (e.g., webhook handler)
@PostMapping("/webhook")
void receive(@RequestBody Event e) {
  if (!queue.offer(e, 1, SECONDS)) {
    // queue full -> drop or reject with 503
  }
}
eBay: Tracking-event ingestion. Webhook receivers produce; worker pool consumes; queue absorbs bursts during peak shipping hours.
🏊 Thread Pool / Executor Must Know
Reuses a fixed pool of threads instead of creating one per task. Never spawn raw threads in production — always submit to an executor sized for your workload (CPU-bound vs I/O-bound). Java 21+ virtual threads change the math for I/O-heavy code.
⚙️ Implementation 
// I/O bound — many threads OK
ExecutorService ioPool = Executors.newFixedThreadPool(200);

// CPU bound — match cores
ExecutorService cpuPool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors());

// Virtual threads (Java 21+)
ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor();
▶ How it's called 
Future<Quote> f = ioPool.submit(() -> carrier.quote(req));
Quote q = f.get(500, MILLISECONDS);
// Or with CompletableFuture:
CompletableFuture.supplyAsync(() -> carrier.quote(req), ioPool);
⚠️ Staff-level rule: N_threads ≈ N_cpu × (1 + wait_time/cpu_time). For I/O-heavy code on Java 21+, virtual threads let you forget the sizing entirely.
🔐 Read-Write Lock Common
Allows many concurrent readers but exclusive writer access. StampedLock with optimistic reads is the modern choice — readers don't block each other or block on the writer, only validate at the end. Perfect for read-heavy hot paths.
⚙️ Implementation 
private final StampedLock lock = new StampedLock();
private Map<String, Rate> data = new HashMap<>();

public Rate read(String key) {
  long stamp = lock.tryOptimisticRead();
  Rate r = data.get(key);
  if (!lock.validate(stamp)) {
    stamp = lock.readLock();
    try { r = data.get(key); }
    finally { lock.unlockRead(stamp); }
  }
  return r;
}
▶ How it's called 
RateCache cache = new RateCache();
Rate r = cache.read("US-CA-2lb");  // many threads concurrent
cache.refresh(newRates);          // exclusive, readers briefly retry
eBay: Rate-card cache — refreshed once a day, read millions of times per minute. Optimistic reads keep p99 fast.
⚛️ Atomic + Lock-Free Common
Uses CPU-level compare-and-swap (CAS) instructions to update shared state without locks. Faster than synchronization for simple operations — counters, flags, single-reference swaps. LongAdder beats AtomicLong under high contention.
⚙️ Implementation 
private final LongAdder requestCount = new LongAdder();
private final AtomicReference<Config> config =
    new AtomicReference<>(Config.defaults());
▶ How it's called 
// Increment from any thread, no lock contention
requestCount.increment();
long total = requestCount.sum();

// Atomic swap of immutable config
Config old = config.get();
Config updated = old.withTimeout(Duration.ofMillis(500));
config.compareAndSet(old, updated);  // retry-if-stale pattern
eBay: Per-carrier request counters, hot-path config swaps without locking readers, lock-free flag-driven feature toggles.

Distributed Systems Patterns

The Staff-level differentiator. These come up in every system design round. Be fluent enough to recommend, sketch, and discuss tradeoffs without thinking.

⚡ Circuit Breaker Must Know
Tracks failures from a downstream dependency and "opens the circuit" once a threshold is breached, failing fast instead of compounding latency. Periodically tries again to detect recovery. Prevents cascading failure across services.
⚙️ Implementation 
@Service
class RateService {

  @CircuitBreaker(name = "fedex", fallbackMethod = "fallback")
  public Quote getRate(Req r) {
    return fedex.quote(r);
  }
  public Quote fallback(Req r, Exception e) {
    return Quote.empty();
  }
}
// States: CLOSED -> OPEN -> HALF_OPEN -> CLOSED
▶ How it's called 
@Autowired RateService rates;

Quote q = rates.getRate(req);
// If FedEx is healthy: real call.
// If breaker is OPEN: fallback runs immediately, no FedEx call.
// If HALF_OPEN: limited probe calls test recovery.
eBay: One circuit breaker per carrier. A slow FedEx doesn't take down the entire rate-quote service.
🔄 Retry with Exponential Backoff Must Know
Retries failed operations with exponentially increasing delays plus jitter. Only safe for idempotent operations — never blindly retry POSTs that could double-charge. Jitter prevents thundering-herd retry storms.
⚙️ Implementation 
@Retryable(
  retryFor = {IOException.class, TimeoutException.class},
  maxAttempts = 3,
  backoff = @Backoff(
    delay = 100,        // 100ms, then 200ms, then 400ms
    multiplier = 2,
    random = true      // jitter
  )
)
public Result call() { return client.invoke(); }
▶ How it's called 
@Autowired CarrierClient client;

try {
  Result r = client.call(req);  // transparently retried
} catch (RetryExhaustedException e) {
  // All 3 attempts failed — handle definitively
}
⚠️ Staff-level: Don't retry — 4xx (won't change), POSTs without idempotency keys (double-charge!), or things behind your own circuit breaker (compounds load).
🚧 Bulkhead Common
Isolates resource pools so failure in one dependency can't starve the others. Separate thread pools and connection pools per downstream — when FedEx slows, UPS calls still go through. Named after ship compartments that prevent total flooding.
⚙️ Implementation 
Map<String, ExecutorService> pools = Map.of(
    "fedex", Executors.newFixedThreadPool(20),
    "ups",   Executors.newFixedThreadPool(20),
    "usps",  Executors.newFixedThreadPool(20));
▶ How it's called 
ExecutorService pool = pools.get(carrier.name());
CompletableFuture<Quote> f =
    CompletableFuture.supplyAsync(() -> carrier.quote(req), pool);
// Slow FedEx exhausts its 20 threads. UPS pool stays unaffected.
eBay: Per-carrier thread + connection pools. Critical for preventing one bad dependency from cascading into total outage.
🔑 Idempotency Key Must Know
Client tags each side-effectful request with a unique key. Server stores (key → result); repeated submissions return the cached result instead of executing again. Non-negotiable for any operation touching money or generating external state.
⚙️ Implementation 
public Label generate(Req r, String idemKey) {
  var existing = store.find(idemKey);
  if (existing.isPresent()) return existing.get();
  var label = doGenerate(r);
  store.save(idemKey, label, Duration.ofDays(7));
  return label;
}
▶ How it's called 
// Client side: same key for retries of the same logical request
String key = UUID.randomUUID().toString();

Label l1 = service.generate(req, key);  // network blip...
Label l2 = service.generate(req, key);  // retry, same key

assert l1.id().equals(l2.id());  // same label, no double-charge
eBay: Every label-buy request carries a UUID from the seller. Retry on network blip → same label, no double-charge.
📖 Saga (Compensating Tx) Staff-Level
Coordinates a multi-step transaction across services without distributed transactions. Each forward step has a compensating action that undoes it if a later step fails. The standard replacement for 2PC at scale.
⚙️ Implementation 
try {
  reserveInventory(o);    // compensate: releaseInventory
  chargePayment(o);       // compensate: refund
  generateLabel(o);       // compensate: voidLabel
  sendConfirmation(o);
} catch (Exception e) {
  runCompensators(o, e);  // in reverse order
}
▶ How it's called 
// Or with a saga orchestrator framework:
SagaOrchestrator.start(order)
    .step(this::reserveInventory).compensate(this::releaseInventory)
    .step(this::charge).compensate(this::refund)
    .step(this::generateLabel).compensate(this::voidLabel)
    .execute();
eBay: Multi-step purchase flow. If label gen fails after payment succeeds, auto-refund. Orchestration-based (one coordinator) or choreography (events) variants.
📤 Transactional Outbox Staff-Level
Solves the dual-write problem — when you need to both persist state and publish an event but they live in different systems. Write both to the same DB transaction; a separate poller reads the outbox table and emits to the message broker. Guarantees exactly-once event publish.
⚙️ Implementation 
@Transactional
public void ship(Order o) {
  shipmentRepo.save(new Shipment(o));
  outboxRepo.save(new OutboxEvent(
    "ShipmentCreated", o.id(), toJson(o)));
}
// Both rows commit together — or both roll back.
▶ How it's called 
// Caller doesn't care about outbox plumbing
shippingService.ship(order);

// Meanwhile, a separate poller (different process):
// 1. SELECT * FROM outbox WHERE sent_at IS NULL
// 2. publish each row to Kafka
// 3. mark sent_at = now()
eBay: Guarantees "shipment was created" event reaches Kafka exactly when the shipment row commits. No lost events from dual-write races.
📊 CQRS Staff-Level
Separates the model used for writes (normalized, transactional) from the model used for reads (denormalized, query-optimized). Eventual consistency is the price — pay it when read and write workloads diverge enough that one model can't serve both well.
⚙️ Implementation 
// Write side - normalized, transactional
@Transactional
void placeOrder(Order o) {
  orderWriteRepo.save(o);
}

// Async projector updates read model
@EventListener
void on(OrderPlaced e) {
  orderSearchIndex.upsert(toReadModel(e));
}
▶ How it's called 
// Writes go to Postgres
orderService.placeOrder(order);

// Reads hit Elasticsearch (denormalized for query)
List<OrderSummary> recent =
    orderSearchService.findRecentByBuyer(buyerId);
eBay: Listings written to Oracle/Postgres; search reads from Solr/Elasticsearch projections. Eventual consistency between them is acceptable for search.
📜 Event Sourcing Niche/Powerful
Stores every state change as an immutable event; current state is derived by replaying the event stream. Powerful for audit-heavy domains but complex — only adopt when "what was the state at time T" is a real product requirement. Often paired with CQRS.
⚙️ Implementation 
// Events as source of truth
eventStore.append(new LabelPurchased(id, ...));
eventStore.append(new LabelPrinted(id, ...));
eventStore.append(new LabelVoided(id, reason));

// State derived from event stream
LabelState current = eventStore.stream(id)
    .reduce(LabelState.initial(), LabelState::apply);
▶ How it's called 
// Current state
LabelState now = labelService.currentState(labelId);

// Historical state — the killer feature
LabelState at = labelService.stateAt(labelId, lastWeek);
// Audit query: "what was the state when the seller complained?"
⚠️ Tradeoff: Powerful but heavy. Schema evolution is hard; snapshotting is required at scale. Reserve for domains where audit/replay is core, not as default.
🪟 Rate Limiting Must Know
Caps how many operations a tenant or client can perform in a time window. Token bucket is the typical choice — allows controlled bursts, easy to reason about. Critical for protecting against abuse and fair resource sharing.
⚙️ Implementation 
// Bucket4j — token bucket per seller
private Bucket bucketFor(SellerId id) {
  return Bucket.builder()
    .addLimit(Bandwidth.simple(
        100, Duration.ofMinutes(1)))
    .build();
}
▶ How it's called 
@PostMapping("/labels")
ResponseEntity<?> create(@RequestBody Req r, @Auth Seller s) {
  if (!bucketFor(s.id()).tryConsume(1)) {
    return ResponseEntity.status(429).build();
  }
  return ResponseEntity.ok(labelService.create(r));
}
eBay: Per-seller request limits on label generation. Per-carrier limits to respect their API quotas. Per-IP at the gateway.
🪦 Strangler Fig Staff-Level
Replaces a legacy system incrementally by routing some traffic to the new one and growing that slice over time. The safest way to migrate production systems — no big-bang cutover, easy rollback at any percentage. Named after a fig tree that strangles its host.
⚙️ Implementation 
@Service
class ShippingRouter {
  public Result ship(Order o) {
    if (flags.isEnabled("new-shipping", o.seller())) {
      return newShippingService.ship(o);
    }
    return legacyShippingService.ship(o);
  }
}
▶ How it's called 
// Callers don't know there are two backends
shippingRouter.ship(order);
// Week 1: 1% sellers on new system
// Week 4: 10%
// Week 12: 100% — delete legacy when traffic = 0
eBay: Migrating legacy Java monolith services to microservices. Roll forward seller-by-seller, region-by-region, over months.
🚪 API Gateway Common
Single entry point for clients in a microservices world. Handles auth, rate limiting, routing, request shaping, and response aggregation. BFF variant (Backend For Frontend) shapes responses per client type — mobile, web, partner.
⚙️ Implementation 
// Often a separate product:
// Kong, AWS API Gateway, Spring Cloud Gateway

// Or a thin BFF service per client type:
@RestController
class MobileBFF {
  @GetMapping("/orders/{id}")
  MobileOrderDTO get(@PathVariable Long id) {
    var order = orderSvc.get(id);
    var ship  = shipSvc.get(order.shipmentId());
    return mobileMapper.compose(order, ship);
  }
}
▶ How it's called 
// Mobile client hits BFF gateway, not raw services
GET https://mobile-bff.ebay.com/orders/123

// BFF fans out to OrderSvc + ShipmentSvc + PaymentSvc,
// composes one mobile-optimized JSON response.
eBay: Mobile app, seller hub, and partner APIs each have different needs. BFF gives each a tailored response without bloating shared services.
🚀 Cache-Aside Must Know
Application checks the cache first; on miss, loads from source-of-truth and populates the cache. The most common cache pattern — simple, lazy, and easy to reason about. Variants: write-through, write-behind, refresh-ahead for stricter consistency.
⚙️ Implementation 
public Rate getRate(String key) {
  Rate cached = redis.get(key);
  if (cached != null) return cached;

  Rate rate = db.findRate(key);
  redis.set(key, rate, Duration.ofHours(1));
  return rate;
}
▶ How it's called 
Rate r = rateService.getRate("US-CA-2lb");
// First call: cache miss -> DB query -> populate cache -> return
// Next calls (1hr): cache hit -> return immediately
// After TTL: refresh on next request
⚠️ Staff-level: Know variants — write-through (sync write to both), write-behind (async DB write), refresh-ahead (preemptive reload). Pick by consistency requirements.

Spring & Web Patterns

Spring is eBay's stack. Be fluent in idiomatic Spring patterns — interviewers test this directly.

💉 Dependency Injection Must Know
Objects receive their dependencies from outside instead of constructing them. Constructor injection with final fields is the right default — testable, immutable, fails fast if a dependency is missing at startup. Field injection is an anti-pattern.
⚙️ Implementation 
@Service
public class QuoteService {
  private final List<Carrier> carriers;
  private final RateCache cache;

  // Spring auto-injects; @Autowired optional with single ctor
  public QuoteService(List<Carrier> carriers, RateCache cache) {
    this.carriers = carriers;
    this.cache = cache;
  }
}
▶ How it's called 
// Other beans get it injected too — Spring resolves the graph
@Service
class OrderService {
  private final QuoteService quotes;
  OrderService(QuoteService quotes) { this.quotes = quotes; }
}

// In tests — wire fakes directly, no Spring needed
var svc = new QuoteService(List.of(fakeCarrier), fakeCache);
⚠️ Avoid: Field injection (@Autowired on fields). Blocks testing without Spring, hides dependencies, allows non-final state.
📦 Repository Must Know
Abstracts data access behind a domain-facing interface. Business code talks to the repository, not to JPA/JDBC/HTTP directly — making it easy to swap implementations for testing or to migrate storage backends.
⚙️ Implementation 
public interface ShipmentRepository
    extends JpaRepository<Shipment, Long> {

  List<Shipment> findBySellerId(Long sellerId);

  @Query("SELECT s FROM Shipment s WHERE s.state = :state")
  List<Shipment> findByState(@Param("state") State state);
}
▶ How it's called 
@Autowired ShipmentRepository shipments;

List<Shipment> open = shipments.findByState(OPEN);
Shipment saved = shipments.save(new Shipment(...));
shipments.findById(123L).ifPresent(this::process);
eBay: Hides whether data lives in Oracle, Postgres, Cassandra, or a remote service. Swappable for unit tests with in-memory fakes.
📨 DTO / Mapper Must Know
Transports data across boundaries (HTTP, queue messages) without exposing internal entities. Never serialize JPA entities directly — leaks internals, breaks on schema changes, can serialize lazy-loaded relations into infinite JSON. MapStruct generates mappers at compile time.
⚙️ Implementation 
public record ShipmentDTO(String id, String status, String trackingNo) {}

@Mapper(componentModel = "spring")
public interface ShipmentMapper {
  ShipmentDTO toDto(Shipment s);
  Shipment toEntity(ShipmentDTO d);
}
▶ How it's called 
@RestController
class ShipmentController {
  private final ShipmentRepository repo;
  private final ShipmentMapper mapper;

  @GetMapping("/shipments/{id}")
  ShipmentDTO get(@PathVariable Long id) {
    return mapper.toDto(repo.findById(id).orElseThrow());
  }
}
⚠️ Why: Entities reflect DB schema; DTOs reflect API contract. Coupling them creates breaking changes whenever you refactor the schema.
🎯 AOP / Interceptors Common
Applies cross-cutting concerns (logging, metrics, security, transactions) declaratively via annotations or pointcuts. Keeps domain code clean of boilerplate. Don't overuse — runtime magic can surprise debuggers.
⚙️ Implementation 
@Aspect
@Component
class MetricsAspect {

  @Around("@annotation(Timed)")
  public Object time(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.nanoTime();
    try { return pjp.proceed(); }
    finally {
      metrics.record(pjp.getSignature().getName(),
                     System.nanoTime() - start);
    }
  }
}
▶ How it's called 
@Service
class QuoteService {
  @Timed  // metrics auto-emit via the aspect
  public Quote quote(Req r) {
    return doQuote(r);
  }
}
eBay: Auto-emit metrics for every @Timed method. Security checks via @PreAuthorize. Transactions via @Transactional. Caching via @Cacheable.
🛡️ Global Exception Handling Must Know
Centralizes the mapping of exceptions to HTTP responses so controllers stay free of try/catch boilerplate. Pairs well with RFC 7807 Problem Details for consistent error shapes. Frequently asked at eBay interviews.
⚙️ Implementation 
@RestControllerAdvice
public class GlobalExceptionHandler {

  @ExceptionHandler(RateLimitException.class)
  public ResponseEntity<Error> rateLimit(RateLimitException e) {
    return ResponseEntity.status(429)
        .body(new Error("RATE_LIMIT", e.getMessage()));
  }

  @ExceptionHandler(IllegalArgumentException.class)
  public ResponseEntity<Error> badReq(IllegalArgumentException e) {
    return ResponseEntity.status(400)
        .body(new Error("BAD_REQ", e.getMessage()));
  }
}
▶ How it's called 
@PostMapping("/labels")
LabelDto create(@RequestBody Req r) {
  return service.create(r);  // no try/catch needed
}
// Exceptions propagate to GlobalExceptionHandler -> consistent JSON
eBay: Consistent error response shape across all controllers. Trace IDs, structured error codes, no leaked stack traces.
📋 Spring Profiles Common
Activates different bean configurations based on environment (dev, staging, prod). Same code, different wiring — real carrier APIs in prod, stubs in dev. Commonly asked in eBay interviews because it's everyday operational tooling.
⚙️ Implementation 
@Configuration
class CarrierConfig {

  @Profile("prod")
  @Bean
  Carrier fedex() { return new FedExLive(prodApiKey); }

  @Profile({"dev", "test"})
  @Bean
  Carrier fedexStub() { return new FedExStub(); }
}
▶ How it's called 
# application.yml or env var
spring.profiles.active=prod

// At runtime, only the matching @Profile beans wire up
@Autowired Carrier fedex;
// In prod: FedExLive. In dev: FedExStub. Same calling code.
eBay: Real carrier APIs in prod, sandbox/mock APIs in dev. Profiles also gate database connection details, feature flags, monitoring config.

DDD & Architectural Patterns

Domain-driven design vocabulary signals senior-to-staff thinking. You don't have to "do DDD" — but using these terms correctly in interviews instantly elevates the conversation.

🏛️ Aggregate Staff-Level
A cluster of related objects treated as a single unit, with one root entity guarding all invariants. Transactions never span aggregate boundaries — this is how you keep consistency boundaries explicit and avoid distributed-transaction nightmares.
⚙️ Implementation 
// Order is the aggregate root. Items and Shipment are inside.
class Order {
  private final List<OrderItem> items;
  private Shipment shipment;
  private OrderState state;

  public void ship(Carrier c) {
    if (!canShip())
      throw new IllegalStateException();
    this.shipment = new Shipment(this, c);
    this.state = SHIPPED;
  }
}
▶ How it's called 
Order order = orderRepo.findById(id).orElseThrow();
order.addItem(item);   // through the root — invariants checked
order.ship(carrier);   // state transition guarded
orderRepo.save(order); // whole aggregate atomically
eBay: Order owns OrderItems + Shipment + Payment state. External code never mutates them directly — always through the root.
💎 Value Object Must Know
Defined entirely by its values, not by identity — two Money(10, USD) instances are equal. Always immutable, often enforces invariants in its constructor (no negative weights, valid currencies). Use records.
⚙️ Implementation 
public record Money(BigDecimal amount, Currency currency) {
  public Money {
    if (amount.signum() < 0)
      throw new IllegalArgumentException("negative");
  }
  public Money plus(Money other) {
    if (!currency.equals(other.currency))
      throw new CurrencyMismatch();
    return new Money(amount.add(other.amount), currency);
  }
}
▶ How it's called 
Money price = Money.usd(12.50);
Money taxed = price.plus(tax);  // new Money, original untouched
if (price.equals(other)) { ... }  // equality by value

Address dest = new Address(
    "123 Main", "Bellevue", "WA", "98004");
// Constructor validates format/checksum
⚠️ Anti-pattern: Using double for money or String for everything. Value objects encode invariants in the type system — let the compiler help.
📢 Domain Event Staff-Level
A record of "something significant just happened" in the domain. Decouples the action from its downstream consequences — anyone interested can subscribe, the originator doesn't need to know who. Foundational for event-driven architectures.
⚙️ Implementation 
public record ShipmentDelivered(
  String shipmentId,
  Instant deliveredAt,
  String signedBy
) implements DomainEvent {}

// Published when state transitions
shipment.markDelivered(signedBy);
events.publish(new ShipmentDelivered(
    shipment.id(), Instant.now(), signedBy));
▶ How it's called 
// Subscribers anywhere in the system:
@EventListener
void completeOrder(ShipmentDelivered e) { ... }

@EventListener
void releaseEscrow(ShipmentDelivered e) { ... }

@EventListener
void requestReview(ShipmentDelivered e) { ... }
eBay: "ShipmentDelivered" fans out to: complete order, release escrow, request seller review, send buyer notification, update analytics.
🗺️ Bounded Context Staff-Level
Defines the boundary within which a domain model has a single, consistent meaning. "Shipment" means different things in Shipping vs Payments vs Search — and that's fine. Microservice boundaries should align with bounded contexts.
⚙️ Implementation 
// In Shipping context — rich model
class Shipment {
  Carrier carrier;
  List<Package> packages;
  TrackingEvents events;
}

// In Payments context — same name, different model
class Shipment {
  Money shippingCost;
  SellerId chargeTo;
}
▶ How it's called 
// Each service owns its model of the same concept
shippingService.createShipment(orderId, carrier, packages);
paymentsService.recordShippingCost(orderId, cost);

// They communicate via events, NOT shared DB tables
events.publish(new ShipmentCreated(...));
// Payments translates to its own model on receive
eBay: Microservices align with bounded contexts. Shipping service ≠ Order service ≠ Payments service, even though they all touch "shipments."
🚗 Anti-Corruption Layer Staff-Level
Translates between your clean domain model and a messy external system (legacy or third-party), keeping their concepts out of your code. Contains the chaos at the edge — your domain stays clean. A specialized form of Adapter at the service boundary.
⚙️ Implementation 
// FedEx returns XML, snake_case, dollars-as-strings, weird date formats
@Component
class FedExACL {
  public RateQuote translate(FedExResp raw) {
    return new RateQuote(
      raw.getCarrCode(),
      Money.of(new BigDecimal(raw.getAmt()), USD),
      Duration.ofDays(raw.getDays())
    );
  }
}
▶ How it's called 
@Autowired FedExClient rawClient;
@Autowired FedExACL acl;

FedExResp raw = rawClient.getRates(...);
RateQuote clean = acl.translate(raw);
// Rest of code only sees RateQuote — FedEx's XML stays at the edge
eBay: Carrier APIs each have quirks (XML, SOAP, weird date formats). ACL keeps the chaos contained at the boundary.
🏠 Hexagonal / Ports & Adapters Staff-Level
Domain logic depends only on its own "ports" (interfaces); infrastructure "adapters" implement them. Lets you test the domain with fakes and swap real infrastructure without touching business code. The architectural backbone of clean / onion architectures.
⚙️ Implementation 
// Domain layer — defines the port
interface CarrierPort {
  RateQuote quote(Shipment s);
}

// Infrastructure — provides the adapter
@Component
class FedExAdapter implements CarrierPort { ... }

// Test — provides fake adapter
class InMemoryCarrierAdapter implements CarrierPort { ... }
▶ How it's called 
// Domain logic NEVER imports FedEx SDK directly
@Service
class ShippingService {
  private final CarrierPort carrier;
  public Quote quote(Order o) {
    return carrier.quote(toShipment(o));
  }
}
// In prod: FedExAdapter. In tests: InMemoryCarrierAdapter.
eBay: Domain logic for "calculate shipping" never imports FedEx SDK. Swappable at runtime and at test time.

Staff-Level Takeaways

Senior engineers know patterns. Staff engineers know when not to use them, and can articulate tradeoffs in 2 sentences.

🎯 The 10 Patterns Most Likely to Come Up in Your eBay Interview

1. Adapter — every carrier integration
2. Circuit Breaker — protecting against downstream failure
3. Idempotency Key — every money operation
4. Strategy — pluggable algorithms (pricing, routing, ranking)
5. Cache-Aside — rate cards, profile data, tracking status
6. State Machine — label lifecycle, order lifecycle
7. Observer / Pub-Sub — events fanning out via Kafka
8. Retry + Backoff — transient failure handling
9. Saga — multi-service order placement
10. Transactional Outbox — atomic DB-write + event publish

🧠 Staff Mindset: Pattern Selection

Senior: "I'd use the Observer pattern."
Staff: "In-process events would work, but at our scale we'd want Kafka pub-sub for replayability and to decouple consumers from producer deploys. The tradeoff is operational complexity vs. simpler in-process events — at 100M events/day, Kafka wins."

The shift: always voice what you considered and rejected, not just what you picked.

⚠️ Pattern Anti-Patterns to Avoid Naming in Interviews

Don't say "Singleton": In Spring, every bean is one by default. Saying "I'll make it a singleton" sounds like 2005.
Don't reach for Visitor in modern Java: Sealed interfaces + pattern matching beat it on every dimension.
Don't propose Event Sourcing as a default: It's powerful but very heavy. Use only when audit trail is core to the domain.
Don't add a Factory just to have one: If construction is simple, just use new. Factories pay off when there's actual variation to abstract.
Don't say "2PC": At distributed-systems scale, 2-phase commit doesn't scale. Use Saga instead.
Don't propose Abstract Factory casually: Only reach for it when the products genuinely need coordination. Otherwise it's Factory Method × N with extra ceremony.

📐 The Staff Engineer's Tradeoff Vocabulary

Consistency vs. Availability — CAP theorem. Eventual consistency is fine for most marketplace data; strong consistency for money.
Latency vs. Throughput — batch for throughput, cache for latency. Different solutions.
Coupling vs. Cohesion — services that change together should live together; services with different scaling needs should split.
Sync vs. Async — sync for low latency + simple UX; async for resilience + decoupling.
Pull vs. Push — pull is deterministic but wasteful; push is fresh but messy. Often hybrid wins.
Stateless vs. Stateful — stateless services scale horizontally trivially; stateful needs careful sharding.

✅ How to Sound Like a Staff Engineer in Code Reviews / Interviews

• Name the pattern, then immediately the tradeoff ("Adapter here, but the cost is one more class per carrier — worth it because adding a new carrier touches nothing else.")
• Reference failure modes when picking patterns ("Saga because 2PC won't scale and we need compensators when payment succeeds but label gen fails")
• Mention observability alongside any new pattern ("Adding a circuit breaker — I'd emit state-transition metrics so we can alert on flap rate")
• Push back on patterns when they're overkill ("Event sourcing is powerful but it's a big lift. Do we really need to query historical state, or just the latest?")
• Connect patterns to team leverage ("If we standardize this adapter interface, the on-call team can add new carriers without a code review from us")
