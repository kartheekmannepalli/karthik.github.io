🔖 Cursor Pagination — Visual Explainer

A cursor is a bookmark, not a page number. Instead of "give me page 3," you say "give me the items after this one." That one change is what keeps pages stable while data shifts underneath.

1 The problem with offset pagination

Offset = "skip N, take M" (LIMIT 10 OFFSET 20). Simple — until the list changes between page loads. A new item shifts everything down by one, so the next page repeats a row you already saw (or an deletion makes you skip one).

2 The cursor idea: bookmark the last item

Instead of "skip 3 positions," remember the sort key of the last item you returned and say "give me items after that key." The cursor is a pointer to a specific row, not a count — so inserts/deletes elsewhere don't move it.

✅ The core idea in one line
Offset asks "how many to skip" (a moving target). A cursor asks "after which row" (a fixed anchor). Anchors survive insertions and deletions; counts don't.

3 Why a stable sort order is non-negotiable

The cursor says "resume after this key." If two calls sort the list differently, "after e3" lands somewhere different each time → overlaps or skips. That's why the code comment shouts STABLE, deterministic order.

⚠️ The hidden requirement
Your sort must be total and deterministic — every element strictly ordered, ties broken by a unique key (e.g. the event id). If you sort only by "distance" and two events tie, their relative order can flip between calls and pagination corrupts. This is exactly why the Q2 design added .thenComparing(Event::id).

4 The code, line by line

public Page<Event> recommendPage(Customer c, String cursor, int limit) {
    // 1. Build the FULL list in one stable, deterministic order (same every call).
    List<Event> ranked = rankedFor(c);

    // 2. Where do we start?
    //    First page (cursor == null) → 0.
    //    Otherwise → the index just AFTER the row the cursor points to.
    int start = (cursor == null) ? 0 : indexAfter(ranked, cursor);

    // 3. Take `limit` items from start, clamped so the last page can't run past the end.
    List<Event> slice = ranked.subList(start, Math.min(start + limit, ranked.size()));

    // 4. Is there more after this slice?
    //    Yes → next cursor = key of the LAST item we just returned.
    //    No  → null, meaning "this was the last page".
    String next = (start + limit < ranked.size())
            ? cursorOf(slice.get(slice.size() - 1)) : null;

    // 5. Hand back the page + the bookmark for the next call.
    return new Page<>(slice, next);
}

📌 The caller loop
The client just repeats: call with the last nextCursor, render the items, stop when nextCursor is null. It never deals with page numbers or offsets. 
String cursor = null;
do {
    Page<Event> page = recommendPage(c, cursor, 10);
    render(page.items());
    cursor = page.nextCursor();
} while (cursor != null);

📌 In a real database
This in-memory subList demo mirrors the SQL pattern: instead of OFFSET 30 you write WHERE (sort_key, id) > (:lastKey, :lastId) ORDER BY sort_key, id LIMIT 10. The cursor encodes (lastKey, lastId) — often base64'd so clients treat it as opaque. The index on (sort_key, id) makes it O(log n) to locate, not a scan.
⚠️ Watch out for
  • Unstable sort key → overlaps/skips. Always end the sort with a unique tiebreaker.
  • Bad / expired cursor → decide a policy: treat as start-of-list, or reject. Don't crash.
  • Unbounded limit → clamp it (e.g. max 100) so a caller can't request a million.
  • Opaque cursors → encode/encrypt so clients can't forge offsets into your data.
