01

ACID — the four guarantees

A

Atomicity

All writes in a transaction commit together, or none do. No partial state.

Mechanism: write-ahead log + rollback.

C

Consistency

Every commit moves the DB from one valid state to another — constraints, FKs, triggers hold.

Mechanism: constraints + your invariants.

I

Isolation

Concurrent transactions don't step on each other. Strength is tunable.

Mechanism: locks / MVCC.

D

Durability

Once committed, survives crash / power loss.

Mechanism: fsync'd WAL, replication.

Interview hook: Atomicity ≠ Isolation. A transaction wrapper gives you all-or-nothing (A); it does not by itself stop two concurrent transactions from racing — that's Isolation (I), which you choose separately.
02

Transactions

basic Atomic multi-write

Wrap dependent writes so they commit or roll back as one unit.

BEGIN;
  UPDATE users SET balance = balance - :amt
    WHERE id = :id;
  INSERT INTO ledger(user_id, delta, type)
    VALUES (:id, -:amt, 'redeem');
COMMIT;  -- both land, or neither
On any error → ROLLBACK; the UPDATE is undone.

pattern Guard predicate (atomic check)

Push the invariant into the WHERE so "check" + "write" are one step. Inspect rows-affected.

UPDATE users SET balance = balance - :amt
  WHERE id = :id AND balance >= :amt;

-- rows == 1 → ok, proceed
-- rows == 0 → insufficient / lost race → reject
No read-then-write window for a race to slip into.
03

Isolation levels & anomalies

Higher isolation = fewer anomalies, less concurrency. Postgres default = Read Committed.

LevelDirty readNon-repeatablePhantom
Read Uncommittedpossiblepossiblepossible
Read Committednopossiblepossible
Repeatable Readnonopossible*
Serializablenonono

Dirty read

You read another tx's uncommitted write that may roll back.

Non-repeatable

Same row, read twice in one tx, different values (someone committed an UPDATE between).

Phantom

Same query, run twice, different row count (someone INSERTed matching rows).

Note: Postgres' MVCC makes Repeatable Read block phantoms in practice (*). Serializable lets the DB abort one of two conflicting tx — you retry the loser. 
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- ... if it conflicts, Postgres raises 40001
COMMIT;  -- on 40001 → retry with backoff
04

Locks — optimistic vs pessimistic

optimistic Version / CAS

Assume no conflict. Detect it at write time via a version column; retry if it moved.

SELECT balance, version FROM users WHERE id=:id;
-- app computes new balance...
UPDATE users
   SET balance=:new, version=version+1
 WHERE id=:id AND version=:read_version;
-- rows==0 → someone won the race → retry

Best for: low contention, short tx. No lock held.

pessimistic SELECT … FOR UPDATE

Lock the row on read; concurrent writers queue behind you.

BEGIN;
  SELECT balance FROM users
    WHERE id=:id FOR UPDATE;  -- 🔒
  -- safe: no one else can write this row
  UPDATE users SET balance=:new WHERE id=:id;
COMMIT;  -- 🔓 lock released

Best for: high contention, complex read→write logic.

Shared (S)

Many readers, no writer. FOR SHARE.

Exclusive (X)

One writer, blocks all. FOR UPDATE.

Deadlock

A waits on B, B waits on A. Fix: lock rows in a consistent order; DB auto-aborts a victim.

05

Distributed transactions

When one logical operation spans multiple services / databases, you can't use a single local transaction.

2PC Two-Phase Commit

A coordinator asks every participant to prepare (lock + vote), then tells all to commit or abort.

PHASE 1Coordinator → "prepare?"
→
VOTEAll reply "yes" (locked)
→
PHASE 2Coordinator → "commit"
→
DONEAll commit & release
Weakness: blocking. If the coordinator dies after "prepare", participants hold locks indefinitely. Strong consistency, poor availability.

saga Compensating transactions

Break into local tx per service. On failure, run compensating actions to undo prior steps. Eventually consistent.

// order saga
1. reserveInventory()   // ↩ release
2. chargePayment()      // ↩ refund
3. createShipment()
// step 3 fails →
   refundPayment(); releaseInventory();

Two flavors: choreography (events) vs orchestration (central coordinator).

outbox Transactional Outbox

Write business row and an event to an outbox table in the same local tx. A relay publishes it to Kafka after commit. Solves "dual write".

BEGIN;
  INSERT INTO orders(...) VALUES(...);
  INSERT INTO outbox(topic, payload)
    VALUES('order.created', :json);
COMMIT;
-- relay polls outbox → publishes → marks sent

Guarantee: event fires iff the DB write committed.

06

Distributed locks

redis SET NX + TTL

Acquire a lock key only if absent; auto-expire so a dead holder never blocks forever.

# acquire — atomic, with 30s safety TTL
SET lock:resource <token> NX PX 30000

# release — only if WE still hold it (Lua, atomic)
if redis.call('get',KEYS[1])==ARGV[1] then
  return redis.call('del',KEYS[1])
end

Token check on release stops you from deleting a lock that expired and was re-taken by someone else.

safety Fencing tokens

A TTL lock can expire mid-work (GC pause) → two holders. Fix: monotonic token; resource rejects stale writes.

// lock service hands out increasing tokens
client A → token 33  (then GC pauses)
client B → token 34  (lock expired, B acquires)

// storage enforces:
if incoming_token < last_seen_token:
    reject  // A's token 33 is stale

The real guarantee lives at the resource, not the lock service.

Tools: Redis / RedlockZooKeeper (ephemeral znodes)etcd (leases)Postgres advisory locks — Prefer not needing one: idempotency keys + unique constraints often remove the need for a distributed lock entirely.

Bigger box — more CPU/RAM/IOPS. Simplest, zero code change.

Sharding strategies

Hash

shard = hash(key) % N. Even spread, kills hotspots. But range scans hit every shard, and changing N reshuffles everything.

Contiguous key ranges per shard. Great for range scans / time queries — but newest data = one hot shard.

resize Consistent hashing

Map nodes + keys onto a ring. Adding/removing a node moves only ~1/N of keys, not all of them. Virtual nodes smooth the distribution.

// naive modulo: N 4→5 reshuffles ~80% of keys 😱
// consistent hash: only ~20% move 🙂
ring.add(node);  // neighbors hand off a slice

pitfall What breaks at scale

Hot shard: celebrity user / latest-time range. Mitigate with composite keys or salting.

Cross-shard joins/tx: avoid; denormalize or co-locate related data on the same shard (shard by the join key).

Rebalancing: plan it before you need it.

Pick the shard key first. It dictates everything: balance, query locality, and whether you ever need cross-shard transactions. Choose a key that co-locates the data you read together (e.g. userID for a per-user ledger).
09

CAP & consistency models

C — Consistency

Every read sees the latest write.

A — Availability

Every request gets a (non-error) response.

P — Partition tolerance

Survives dropped messages between nodes.

The rule: networks will partition, so P is non-negotiable. The real choice during a partition is C or A. A financial ledger picks CP (refuse rather than serve wrong data); a shopping cart often picks AP.

Strong

Reads always see latest. Costs latency / availability.
