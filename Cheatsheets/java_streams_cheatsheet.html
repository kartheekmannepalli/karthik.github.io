🌊 Java Streams Cheatsheet

java.util.stream — declarative data pipelines over collections. Build a chain of operations, run it once. Each op is lazy until a terminal op pulls the data through.

Lazy pipelinesmap vs flatMapCollectorsJava 8+

★ The pipeline model

Every stream is three stages. Intermediate ops are lazy (they just describe work); nothing runs until the terminal op fires. A stream is single-use — consume it once.

source→ 0+ intermediate ops→ 1 terminal op= result 
List<Event> result = events.stream()      // source
    .filter(e -> e.cityId().equals("NYC")) // intermediate (lazy)
    .sorted(comparing(Event::date))         // intermediate (lazy)
    .limit(10)                              // intermediate (lazy)
    .toList();                              // terminal → runs the whole chain
📌 Three things to remember
Intermediate ops return a new Stream (chainable, lazy). Terminal ops return a value/collection and end the pipeline. A stream can't be reused — call .stream() again for a fresh one.

2 Intermediate ops (lazy)

OpUse when you want to…
filter(pred)keep only elements matching a condition
map(fn)transform each element 1-to-1
flatMap(fn)transform 1-to-many and flatten nested streams into one
mapToInt/Long/Doubleconvert to a primitive stream (unlocks sum/average)
distinct()drop duplicates (uses equals/hashCode)
sorted() / sorted(cmp)sort naturally or by a comparator
limit(n) / skip(n)take the first n / drop the first n
takeWhile / dropWhiletake/drop from the start until a predicate flips (Java 9+)
peek(action)debug/log mid-pipeline — not for real side effects
List<String> out = events.stream()
    .filter(e -> e.price() < 100)            // narrow
    .map(Event::name)                         // 1-to-1 transform
    .distinct()                               // dedup
    .sorted()                                 // order
    .limit(5)                                 // first 5
    .toList();

// flatMap: each recommender returns a List<Event> → flatten to one stream
List<Event> all = recommenders.stream()
    .flatMap(r -> r.recommend(customer).stream())  // .stream() → flatMap needs a Stream
    .distinct()
    .toList();
⚠️ map vs flatMap
map = 1-to-1 (returns one element each). If your fn returns a List, you get a nested Stream<List<T>>. flatMap = 1-to-many; it flattens one level, so a List per element becomes a single flat stream. Its fn must return a Stream — hence the inner .stream().

3 Terminal ops (eager — run the pipeline)

OpReturns / use for
collect(collector)general "gather into something" (list/map/string)
toList()quick unmodifiable List (Java 16+)
toArray()an array
forEach(action)do something per element (order loose in parallel)
reduce(...)fold all elements into one value
count()how many elements (long)
min(cmp) / max(cmp)extreme element → Optional
anyMatch/allMatch/noneMatcha boolean; short-circuits
findFirst() / findAny()one element → Optional (findAny faster in parallel)
sum() / average()aggregate — primitive streams only
long cheap   = events.stream().filter(e -> e.price() < 50).count();
boolean any  = events.stream().anyMatch(e -> e.cityId().equals("NYC"));
Optional<Event> first = events.stream().filter(...).findFirst();
int total    = events.stream().mapToInt(Event::seats).sum();      // primitive stream
String names = events.stream().map(Event::name)
                     .collect(Collectors.joining(", "));
// reduce: fold to one value (identity + accumulator)
int seatSum  = events.stream().reduce(0, (acc, e) -> acc + e.seats(), Integer::sum);
✅ Prefer specifics over reduce
For sums/counts/averages, a primitive stream (mapToInt(...).sum()) reads better than a hand-rolled reduce. Reach for reduce only for genuinely custom folds.

4 Collectors (the argument to collect)

CollectorProduces
toList() / toSet()a List / Set
toMap(keyFn, valFn)a Map (add a merge fn for key clashes)
groupingBy(classifier)Map<K, List<V>> — bucket by key
partitioningBy(pred)Map<Boolean, List<V>> — split true/false
joining(sep)one concatenated String
counting() / summingInt(fn)counts/sums, usually downstream of groupingBy
// group events by city → Map<String, List<Event>>
Map<String, List<Event>> byCity = events.stream()
    .collect(Collectors.groupingBy(Event::cityId));

// count per city → Map<String, Long>
Map<String, Long> countByCity = events.stream()
    .collect(Collectors.groupingBy(Event::cityId, Collectors.counting()));

// index by id → Map<String, Event> (keep first on duplicate id)
Map<String, Event> byId = events.stream()
    .collect(Collectors.toMap(Event::id, e -> e, (a, b) -> a));

// split cheap vs pricey → Map<Boolean, List<Event>>
Map<Boolean, List<Event>> split = events.stream()
    .collect(Collectors.partitioningBy(e -> e.price() < 100));
⚠️ toMap throws on duplicate keys
toMap(Event::id, e -> e) throws IllegalStateException if two elements share a key. Always pass the 3rd merge arg (a, b) -> a when keys might collide.

5 Gotchas — quick scan

⚠️ The ones that bite
  • Streams are single-use. Reusing a consumed stream throws IllegalStateException — make a new one.
  • Intermediate ops do nothing alone. Without a terminal op the pipeline never runs (lazy).
  • No side effects in map/filter. Keep them pure; use forEach for effects, not peek.
  • Infinite streams need limit or they never terminate.
  • toList() (Java 16) is unmodifiable; collect(toList()) historically isn't guaranteed either way — don't mutate the result.
  • Parallel streams are rarely worth it — only for large, CPU-bound, stateless work. Default to sequential.
  • Primitive vs object: use IntStream/mapToInt for numeric aggregation to avoid boxing and get sum/average.
