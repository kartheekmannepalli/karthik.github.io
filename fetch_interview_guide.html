🤖 Round 1: CoderPad Live Build Interview Your Next Round

This is Fetch's first live technical round — conducted entirely inside CoderPad with AI assistance enabled. Unlike traditional LeetCode-style screens, Fetch expects you to build a small working application from a prompt, iteratively, in real time. Think of it as a simulated work session, not a puzzle contest.

⚡ What Makes This Round Different

Fetch uses CoderPad's AI-enabled environment — meaning you can and should use the built-in AI assistant (typically ChatGPT or Claude via CoderPad's AI Chat tab). You are evaluated not just on whether the app works, but on how you direct, verify, and extend AI-generated code. The interviewer wants to see you in the driver's seat — decomposing the problem, catching AI mistakes, and iterating toward production-quality output.

📋 Format — What to Expect (from Glassdoor reports + CoderPad docs)

  • Duration: ~60 minutes live with an interviewer watching in real time
  • Setup: You receive a link, join as a guest or with your name, and land in the shared editor — no installs needed
  • AI: CoderPad's AI Chat tab is available (ChatGPT/Claude). Use it. Not using it is not an advantage.
  • Style: Collaborative pair-programming — the interviewer may give hints, tighten scope, or add requirements mid-session
  • Run your code: CoderPad has a built-in executor — run early and often; don't wait until the end
  • Language: Choose your strongest. Backend: Go or Python. Mobile: Kotlin/Swift. Full-stack: TypeScript/React. Confirm with recruiter.
  • Confirmed Fetch theme: Build an app that fetches data from an API, processes/filters it, and displays or returns the result cleanly
🧪 How the Interview Typically Flows
⏱️ Minutes 0–5 · Problem Setup
Interviewer shares the prompt. Read it twice. Ask 2–3 clarifying questions before writing a single line.
💡 Confirm: expected input/output format, error handling expectations, whether tests are required, and any constraints on libraries. Candidates who ask zero questions and dive straight in often miss hidden requirements.
⏱️ Minutes 5–15 · Plan + Scaffold with AI
Verbally outline your approach, then use the AI to scaffold boilerplate (project structure, imports, API call setup). Review every line the AI generates before keeping it.
💡 Good AI prompt: "Generate a Go/Python function that calls [endpoint], handles a 4xx error gracefully, and returns a list of [items] sorted by [field]." Then read the output critically — AI commonly ignores null checks and edge cases.
⏱️ Minutes 15–40 · Build & Iterate
Implement the core logic. Run the code. Read the output. Fix bugs out loud. The interviewer is evaluating your debugging process, not just the final result.
💡 Narrate constantly: "I'm seeing a null pointer here — I think the API is returning an empty list when there are no results, so I'll add a guard clause." Silence kills your score in CoderPad rounds.
⏱️ Minutes 40–55 · Extension & Follow-ups
Interviewer will extend the requirements: add pagination, a new filter, error handling for a new case, or a user token. Extend cleanly without breaking what you've built.
💡 Confirmed by multiple Glassdoor reports: Fetch's live technical round always adds requirements mid-session. Structure your code from the start so extensions are easy — a monolithic function is hard to extend cleanly.
⏱️ Minutes 55–60 · Wrap-up & Questions
Interviewer asks what you'd improve with more time. Have a real answer ready — mention tests, error handling, performance, or documentation.
💡 "I'd add unit tests for the edge cases I mentioned, extract the API client into a separate module, and add retry logic for transient network failures" is a strong close that signals production thinking.
📋 Practice Problems — Close to Fetch's Actual Prompts
🧾 Practice 1 · Receipt Item API (Most Confirmed)
Given this URL: https://fetch-hiring.s3.amazonaws.com/hiring.json — build an app that fetches the list of items, groups them by listId, sorts by listId then by name, and filters out any item where name is blank or null.
💡 This is the confirmed Fetch mobile take-home prompt, widely reported across Android, backend, and iOS Glassdoor reports. Likely variations exist for the live CoderPad round. Practice this one exactly — it covers grouping, sorting, filtering, and API calling all in one.
🌦️ Practice 2 · Weather/Geocoding Utility (Confirmed 2024)
Given the OpenWeather Geocoding API, write a utility that takes a city name, state, or zip code and returns the latitude, longitude, place name, and other relevant data. Use both the "Coordinates by location name" and "Coordinates by zip/post code" endpoints.
💡 Directly confirmed in a Glassdoor report from Sep 2024. This tests: API key handling, multi-endpoint logic, input validation (city vs. zip vs. state), and clean return types. Practice error handling when the city isn't found.
📱 Practice 3 · Single-Screen App from API
Build a one-screen app (console app or simple UI) that fetches a list of products from a public API (e.g., dummyjson.com/products), displays them sorted by price descending, and lets the user filter by category via a command-line argument or query param.
💡 Based on the Glassdoor Nov 2024 report: "build a one-screen app which was meant to take around 5 hours." In the live CoderPad version, scope is smaller (~60 min) but the pattern is identical. Filtering + sorting + API call = the core skill set.
🏪 Practice 4 · Points Calculator (Domain-Specific)
Given a JSON list of purchase transactions (brand, amount, date), write a function that calculates loyalty points per user (e.g., 1 point per $1 spent, 2x for partner brands). Group results by user, sort by total points descending, and return the top 10.
💡 Not confirmed directly, but highly likely given Fetch's domain. Tests: data transformation, conditional logic, grouping/aggregation, and clean function design — all core to Fetch engineering work. Great live-extension candidate: "now add a tier multiplier."
🔌 Practice 5 · REST API Endpoint (Backend Roles)
Build a simple REST API endpoint (POST /receipts/process) that accepts a JSON receipt, validates required fields (retailer, purchaseDate, items, total), and returns a unique receipt ID. Add a GET /receipts/{id}/points endpoint that returns the calculated points for that receipt.
💡 Classic Fetch backend pattern — directly mirrors their receipt scanning product. Practice in Go (Gin) or Python (FastAPI). Focus on: input validation, error responses (400 vs 404 vs 500), and clean route organization.
🔄 Common Follow-Up Questions After Your App Works
🔧 Extension 1 · Add User Context
"Now associate each receipt scan with a user token passed in the request header. Store the user's scans in memory and add an endpoint to retrieve all receipts for a given user."
💡 Confirmed in Glassdoor reports. Tests: header parsing, in-memory data structures (map/hashmap keyed by token), and extending an existing codebase without breaking it.
🔧 Extension 2 · Handle Edge Cases
"What happens if the API returns a 500? What if an item has a null price? What if the same receipt ID is submitted twice?"
💡 Very common at Fetch. They want to see you think defensively. Add retry logic, null guards, and idempotency handling. Answer verbally first ("I'd add a check here for...") before coding.
🔧 Extension 3 · Performance & Scalability
"If this endpoint receives 10,000 requests per second, what would break and how would you fix it?"
💡 Not always a coding task — sometimes just a verbal discussion. Have a ready answer: in-memory map becomes a bottleneck → move to Redis; synchronous HTTP calls → async/goroutines; no caching → cache the offer catalog. Shows you think beyond the toy problem.
🔧 Extension 4 · Testing
"Can you write a unit test for the points calculation logic? What cases would you cover?"
💡 Fetch values production-quality code. Be ready to write at least one test. Cases to mention: normal input, empty items list, zero total, max boundary, null fields, duplicate submission. Even if you can't write them all, naming them demonstrates mature engineering instincts.
🔧 Extension 5 · Design Discussion
"How would you refactor this to support multiple receipt formats (grocery vs. restaurant vs. gas station)?"
💡 Tests OOP and extensibility thinking. Answer: interface/abstract base for receipt types, separate parsers per format, factory pattern for selecting the right parser. This is the OOP/interface design block bleeding into the live coding round.

🔑 CoderPad-Specific Preparation Tips (3 Days Out)

  • Practice in CoderPad's sandbox today: Go to coderpad.io/sandbox and code in it for 30 minutes. Get comfortable with the editor, running code, and the output panel. The UI is different from your usual IDE.
  • Practice with AI as a pair: Open Claude or ChatGPT alongside a CoderPad sandbox. Simulate the session: give yourself a prompt, use AI to scaffold, then critically review and extend the output. This is the exact muscle Fetch is testing.
  • Build the receipt item app from Practice 1 right now: It's the most confirmed Fetch prompt. Time yourself — can you build, run, and clean it up in under 20 minutes? That's the target pace for the live round.
  • Talk out loud while you code: Record yourself for 10 minutes solving a problem. Watch it back. Are you narrating your reasoning? If there are silences longer than 30 seconds, that's where you lose points in a live CoderPad session.
  • Clear the output panel between runs: CoderPad's output panel doesn't auto-clear. Always check you're reading the freshest output before deciding on your next step.
  • Treat AI output as a draft, not a solution: AI commonly misses null checks, ignores error handling, and hallucinates API method names. Always read the generated code line by line. Saying "let me review this before I run it" out loud signals engineering maturity.
🗂️ AI-Assisted Session Workflow

Follow this exact order every time. Deviating — especially skipping steps 1–3 — is the most common reason candidates build the wrong thing confidently.

🎯Step 1 · Clarify Requirements
  • Listen to the full problem before touching the editor
  • Ask about input source, shape, and nullable fields
  • Ask about expected output format and sort/filter rules
  • Ask which error cases matter vs. can be ignored
  • Ask about scale — 100 items or 10 million?
  • Write a 3–5 line summary and read it back: "So to confirm…"
📄Step 2 · Paste & Trim AGENT.md
  • Have your AGENT.md pre-written — don't write it from scratch live
  • Paste it into CoderPad as a comment block at the top
  • Trim any irrelevant sections for this specific problem
  • Takes under 2 minutes — do not let this slow you down
🗺️Step 3 · Ask for Plan Only
  • Prompt: "Do not write any code yet. Give me a component diagram and bullet list of what you'll build."
  • Plan should include: data flow diagram, components list, edge cases
  • Plan should be under 20 lines — no paragraphs
  • Do not proceed until plan is confirmed
🔍Step 4 · Review Plan Out Loud
  • Narrate your review to the interviewer — they're scoring this
  • Check: are all edge cases covered? Is error handling accounted for?
  • Check: does the structure match the requirements you clarified?
  • Request targeted updates — not a full replan
  • Get verbal confirmation before moving to code
🏗️Step 5 · Build Layer by Layer
  • Build and review one layer at a time: model → service → controller
  • Read every line of AI-generated code before accepting it
  • Run the code after each layer — don't wait until the end
  • Narrate what you're reviewing and why you're changing things
  • Catch AI mistakes out loud: "It missed a null check here, fixing that"
🧪Step 6 · Edge Case Walkthrough
  • Before running tests, spend 60 seconds asking: what breaks this?
  • Empty list, null field, duplicate ID, max size input, bad API response
  • Add missing test cases or flag them verbally to the interviewer
  • This step alone separates good solutions from great ones
✅Step 7 · Run Tests → Demo
  • Run unit tests first — fix all failures before moving on
  • Run integration tests second
  • Run the app itself if time allows — a live demo beats green tests alone
  • Close with: "With more time I'd add retry logic, load tests, and extract config to env vars"
✅ Implementation Checklist — Things to Consider

Run through this mentally before and during the session. You won't implement everything in 60 minutes — but naming what you'd add signals production maturity.

📥Input / Output
  • Exact shape of input — JSON, query params, headers?
  • Which fields are nullable or optional?
  • Output format — JSON body, list, paginated response?
  • Is output order deterministic? (same input → same order)
  • Field naming conventions — camelCase vs snake_case?
  • Max payload size to handle?
🛠️Language & Framework
  • Pick what you debug fastest in — not the theoretically best choice
  • Kotlin + Spring Boot for REST APIs; stdlib for scripts
  • Confirm allowed libraries with interviewer before importing
  • Avoid heavy frameworks for a 60-min scope — keep it lean
  • Use functional style: map, filter, fold over imperative loops
⚠️Error Handling
  • Distinguish expected errors (404, empty) from unexpected (500, malformed)
  • Use a sealed Result<T> type — never throw raw exceptions from services
  • Define HTTP status code contract: 400, 404, 422, 500
  • Handle partial failures — fail all or return partial results?
  • Null/blank field guards before processing begins
  • Idempotency — same request twice should not double-process
  • Never expose stack traces in API responses
🧪Testing
  • Unit tests: pure logic — sorting, filtering, points calculation
  • Integration tests: full request → response cycle per endpoint
  • Mock external APIs with WireMock — no real network in tests
  • Edge cases: empty list, null field, duplicate ID, max size
  • Error paths: bad input, upstream 500, missing required field
  • Idempotency: same request twice returns consistent result
  • Name tests descriptively: should_returnEmpty_when_nameIsNull()
📋Logging & Observability
  • Use SLF4J — structured JSON logs in prod, plain in dev
  • INFO: request in, key business event, external call + latency
  • WARN: recoverable issues, retries, fallbacks
  • ERROR: unhandled exceptions, upstream failures
  • Attach a correlation ID to every request via MDC
  • Log every outbound call: URL, status code, response time
  • Never log tokens, passwords, or PII
  • Metrics to mention: error rate, p50/p95/p99 latency
⚡Performance & Latency
  • What's the acceptable response time SLA?
  • I/O-bound vs CPU-bound — different optimization strategies
  • Avoid N+1 — batch API calls, don't loop and call
  • Cache read-heavy, low-churn data (offer catalog, brand list)
  • Sort/filter server-side, not in memory for large datasets
  • Use async/concurrent calls when fetching multiple sources
  • Mention cold start cost if serverless (Lambda) is in scope
🔒Security
  • Validate and sanitize all inputs before processing
  • API keys via environment variables — never hardcoded
  • Rate limiting — prevent single caller from flooding endpoint
  • Token validation — not just presence, verify it's legitimate
  • Don't return more fields than the caller needs
  • Sanitize error messages — no internal paths or stack traces
⚙️Configuration
  • No hardcoded values — URLs, timeouts, keys go in config
  • Use typed config via @ConfigurationProperties
  • Separate configs per environment (local, prod)
  • Document every config key and its default in README
  • In interview: say "I'd move this to env var" even if you hardcode temporarily
🏛️Code Structure
  • Separate layers: controller → service → repository / util
  • Interfaces for services and repositories only — not everywhere
  • Max function length ~20 lines — extract if longer
  • Prefer data classes + copy() over mutation
  • Comments only for non-obvious logic — never for self-explanatory code
  • One responsibility per class — if you can't name it, split it
📝Documentation
  • README: what it does, how to run it, config values, known gaps
  • Inline comments only for non-obvious algorithms or workarounds
  • Document API contract: endpoints, request/response shape, error codes
  • Use TODO comments to flag intentionally deferred work
  • Fetch explicitly grades take-homes on README quality

🎁About Fetch Rewards

Founded in 2013 in Madison, Wisconsin, Fetch is America's #1 rewards app. Users earn points by scanning grocery and retail receipts (in-store or digital), shopping online through the app, playing mobile games, and spinning daily wheels. Points redeem for gift cards from hundreds of brands. Fetch has raised $772M and serves tens of millions of active users. Their engineering teams build the receipt scanning pipeline, rewards recommendation engine, brand partnership data layer, and mobile apps (iOS/Android).

In the Super Day, the behavioral interview is conducted by a non-technical interviewer (often from People Ops or a business team). They're evaluating culture fit, communication, and values alignment — not technical depth. Keep answers concise, human, and grounded in real examples. This block follows 3 technical rounds so energy management matters — arrive sharp.

✅Do
  • Show genuine product curiosity — mention using the app
  • Demonstrate ownership ("I led…" not "the team…")
  • Connect your values to Fetch's startup culture
  • Be specific with outcomes — numbers, speed, impact
  • Ask smart, engaged questions during the recruiter call
❌Avoid
  • Vague stories with no quantifiable outcome
  • Answers heavy on "we" with no personal ownership
  • Criticizing past employers — especially about pace or ambiguity
  • Saying you've never heard of or used the app
  • Over-formal or rehearsed delivery — Fetch culture is relaxed

💻 Coding Round

Fetch's coding interviews happen at two stages: the take-home project (assessed async) and a live coding round during Super Day. The live round is LeetCode easy-to-medium difficulty, plus an OOP/data modeling block. Communication and code quality matter as much as correctness.

📋 Format (from Glassdoor backend & frontend candidates)

  • Take-Home: Build a small production-ready application (receipt processing, API endpoint, or data pipeline). Submit with README and docs. Time: 1–5 hours.
  • Take-Home Review (1 hr): Walk through your solution live, make real-time modifications, explain all design choices.
  • Super Day — Live Coding (1 hr): LeetCode easy/medium equivalent. Focus on arrays, hashmaps, and data manipulation.
  • Super Day — OOP/Data Modeling (1 hr): Design classes, interfaces, or data schemas. Think receipt structure, user loyalty models, brand partner schemas.
  • Language: Role-dependent. Backend: Go or Python. Mobile: Kotlin (Android) or Swift (iOS). Full-stack: TypeScript/React.
📋 Example Questions (from Glassdoor + Blind + DEV community)
🧾 Take-Home — Receipt Processing (Most Common)
Build an API or function that processes a JSON list of receipt items. Group by a field (e.g., "listId"), sort items within groups, and filter out items with blank or null names.
💡 Confirmed across Android, backend, and data roles. The core challenge is clean data handling + production-level code quality. Add error handling, config management, and a solid README — they expect "shippable" work.
🔢 Live Coding — Data Manipulation
Given a list of transactions or shopping events, compute aggregate summaries (totals, counts, group-by brand). Expect variations with filtering conditions and edge cases.
💡 Directly tied to Fetch's domain. Practice hashmap-based aggregation patterns — they map naturally to receipt/offer data. Think: "count purchases per brand", "total points per user per week".
🏗️ OOP / Interface Design

🔄 Code Refactoring / Extension
During the take-home review, you may be asked to live-extend your project: e.g., "now add support for a user token to associate receipt scans with a specific user account and track their points."
💡 Candidate reports confirm this pattern. Practice modifying your own take-home code live. Write it cleanly the first time so extensions are easy — messy initial code becomes a trap.
📊 SQL & Data Pipeline (Data Roles)
Write a SQL query to find the top 5 brands by total points awarded last week. Join user receipt scans with brand offer tables, filter by date range, aggregate, and rank.
💡 Confirmed for data engineer and analyst roles via InterviewQuery. Fetch's brand partnership model means SQL skills are core. Practice window functions, CTEs, and GROUP BY aggregations on transactional data.

🏗️ System Design Round

The system design block is a dedicated 1-hour round in the Super Day. Interviewers evaluate your ability to design scalable, real-world systems — with particular emphasis on data modeling, API design, and distributed system tradeoffs relevant to a high-volume consumer rewards platform.

📋 Format (from Glassdoor backend candidates)

  • 1 hour, typically one interviewer (senior or staff engineer)
  • Often starts with: "Design the Fetch receipt scanning and points system" or a scaled variant
  • May also revisit architectural aspects of your take-home project
  • Interviewer evaluates: approach, tradeoffs, scalability reasoning, data modeling depth
  • AWS familiarity is a plus — Fetch is an AWS shop. Know S3, SQS, Lambda, and RDS/Aurora patterns.
📋 Example Questions (from Glassdoor + InterviewQuery)
🧾 Receipt Processing Pipeline
Design a system to ingest millions of receipt photos per day, extract structured data (store, items, prices), match items to brand offers, and award loyalty points to the correct user account.
💡 This is the core Fetch engineering problem. Cover: async job queue (SQS), OCR/parsing service, offer matching service, idempotency (no double-points), and a points ledger DB. Discuss eventual consistency tradeoffs.
📈 Scalability — Peak Traffic
How would you ensure the Fetch platform handles a 20x traffic spike during Super Bowl Sunday (when millions of users scan snack receipts simultaneously)?
💡 Cover: horizontal scaling, queue-based decoupling (SQS/Kafka), read replicas for PostgreSQL, Redis caching for offer lookups, graceful degradation, and pre-scaling via Lambda reserved concurrency.
🗄️ Data Model Design
Design the database schema for the Fetch rewards system: users, receipts, receipt line items, brand offers, offer matches, points transactions, and gift card redemptions.
💡 PostgreSQL is likely their primary DB. Show normalized relationships, use of foreign keys, indexing strategy for high-frequency receipt scans, and how you'd handle the audit trail of a points ledger (append-only events vs. mutable balance).
🔌 Offer Matching API
Design an API for matching scanned receipt items to active brand offers. A receipt has 30 line items; Fetch has 10,000+ active brand offers. How do you make matching fast, accurate, and maintainable?
💡 Think about: inverted index or trie for product lookup, fuzzy matching for OCR errors, caching active offer catalog in Redis, and batch vs. real-time matching tradeoffs. This is core Fetch IP.
🔔 Notification & Personalization System
How would you design a system to deliver personalized offer notifications to 17M users — showing each user the most relevant brand offers based on their purchase history?
💡 Cover: user segmentation, offline batch scoring (Lambda + S3), delivery via push notification (FCM/APNs), frequency capping, and A/B testing infrastructure. Fetch's business model depends on offer relevance.

🔑 Preparation Tips

  • Think in receipts and offers: Every system design at Fetch ultimately relates to: ingest receipt → parse items → match to offers → award points → redeem rewards. Keep this pipeline in mind.
  • Know AWS fundamentals cold: S3 (image storage), SQS (async queuing), Lambda (serverless processing), RDS/Aurora (relational data), ElastiCache (Redis), CloudFront (CDN). Fetch is an AWS shop.
  • Points ledger is tricky: Loyalty points require ACID guarantees. Be ready to discuss: event sourcing, idempotency keys, double-entry bookkeeping patterns, and why a mutable balance field is dangerous.
  • Talk through your tradeoffs: SQL vs. NoSQL for receipts, sync vs. async processing, eventual vs. strong consistency. Fetch interviewers care about your reasoning, not a single "right" answer.
  • Defend your take-home architecture: The Super Day may include questions about architectural decisions in your take-home. Know why you made every choice.

"Where is Fetch's backend architecture today — more monolith, microservices, or event-driven? What's been the biggest architectural evolution as you've scaled past 10M users?"

💡 Demonstrates you've thought deeply about Fetch's core technical challenge beyond the surface level. Very few candidates ask this — it's memorable and shows genuine engineering curiosity.

💡 Signals you understand the data flywheel that makes Fetch's business defensible. Also surfaces how integrated the data science and engineering orgs actually are.
