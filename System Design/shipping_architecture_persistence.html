How to read this document

The code structure IS the high-level design here — each package is an architectural layer with one responsibility, and dependencies flow in one direction (API → service → carrier abstraction → providers; everything reads/writes through the domain + repo layer). The second half maps the persistence layer: four tables anchored on a shipment aggregate root, with the relational schema, keys, indexes, and the JPA entity mapping that backs each one.

High-Level Design — the runtime shape

A single Spring Boot service exposes a small REST API, orchestrates in one service layer, and talks to three carriers through one uniform provider interface. The aggregator (EasyPost) gives breadth; FedEx + UPS direct give better rates on heavy lanes. All state persists to Postgres; carriers push tracking back via webhooks.

🎯One interface, many providers

Adding or removing a carrier never touches business logic — it's a new class implementing CarrierProvider. The service layer only knows the interface.

🌐Aggregator + direct hybrid

EasyPost covers 100+ carriers, international, and customs. FedEx/UPS direct avoid aggregator markup on high-volume lanes. Both sit behind the same seam.

⚡Async fan-out at quote time

The service calls all selected providers in parallel with a per-provider timeout, so the buyer gets all rates in ~1 round-trip even though 3 systems are queried.

Code structure = the layers

Each package under com.marketplace.shipping is one architectural layer with a single responsibility. Dependencies point downward only: the edge depends on the service, the service depends on the carrier abstraction and the domain/repo — never the reverse. This is what keeps the carrier seam clean.

The carrier seam — how the abstraction holds

This is the most important LLD decision: one interface, namespaced rate IDs for routing, and a Strategy policy for selection. Together they mean carriers are plug-in modules.

🔗CarrierProvider — the one interface
interface CarrierProvider {
  String name();                       // "easypost"|"fedex"|"ups"
  boolean supports(Address f, Address t); // geo filter
  List<CarrierRate> getRates(CarrierShipment s);
  CarrierLabel  buyLabel(CarrierShipment s, String rateId);
  CarrierTracking track(String trackingNumber);
}

Each provider is an Adapter: it maps the neutral CarrierShipment/CarrierRate types to and from that carrier's wire format.

🔑Namespaced rate IDs → routing

Every rate ID is prefixed with its provider: easypost:rate_xyz, fedex:STANDARD_OVERNIGHT, ups:03.

On purchase, CarrierRegistry.providerFor(rateId) splits on ":" to route the buy back to the exact provider that issued the quote. Registry + namespaced IDs pattern.

🎯Routing policy — Strategy

A YAML-driven ConfigurableRoutingPolicy decides, per (fromRegion, toRegion), which providers to query and in what priority order — with state-level overrides (e.g. HI/AK/PR exclude UPS).

Swap in a MachineLearnedRoutingPolicy later without touching ShippingService.

Why NOT Abstract Factory for regions (a deliberate call in the plan)

  • Abstract Factory produces families of related objects whose concrete types vary by context. Here every region returns the same type — CarrierProvider — just a different subset.
  • That's a filter/Strategy problem, not a factory problem. Adding Abstract Factory would be indirection without payoff.
  • Revisit only if regions need different object families together (region-specific RateFormatter + CustomsBuilder + LabelRenderer all varying as a set).

Request flows — how a call moves through the layers

The two core operations. Notice each one touches the layers top-to-bottom and persists at well-defined points — quote writes the shipment + rates, purchase writes the label and advances state.

💬POST /quotes — async fan-out (Scatter–Gather)
1. Controller validates DTO, hands QuoteRequest to ShippingService
2. AddressValidator checks from/to (postal regex per country)
3. INSERT shipment row, status = QUOTED
4. CarrierRoutingPolicy.resolve(from,to) → ordered provider list
5. getRates() called on each provider in PARALLEL
       CompletableFuture.allOf + per-future orTimeout(3s), partial-ok
6. de-dupe (prefer FedEx direct over the same service via EasyPost)
7. INSERT rate rows (one per returned rate)
8. return QuoteResponse {shipmentId, status, rates[]}
🏷️POST /shipments/{id}/purchase
1. load Shipment by id (must be in QUOTED)
2. CarrierRegistry.providerFor(rateId) → the issuing provider
3. if international → CustomsService builds HS-code payload
4. provider.buyLabel(shipment, rateId) → real carrier API call
       ← label url/bytes + tracking number
5. INSERT label row, advance shipment status → PURCHASED
6. return LabelDto

Tracking arrives asynchronously: carriers POST to /webhooks/{provider}; the service verifies the HMAC signature, idempotently upserts a tracking_event, and advances shipment.status on terminal events.

Persistence layer — how it's structured

The persistence layer is a thin, deliberate stack: domain entities ↔ Spring Data JPA repositories ↔ Hibernate ↔ Postgres, with Flyway owning the schema. The shape mirrors the domain: one aggregate root with child collections.

🧱The stack
  • domain/ — JPA @Entity classes (the object model)
  • repo/ — JpaRepository interfaces (no hand-written CRUD SQL)
  • Hibernate — the JPA provider doing the actual O/R mapping
  • Flyway — V1__init.sql owns DDL; ddl-auto: validate so Hibernate never mutates schema
  • Postgres — 4 tables + jsonb for embedded value objects
🏛️Aggregate shape

Shipment is the aggregate root. Everything else is reached through it and cascades from it:

  • Shipment 1 ──< Rate (many quotes per shipment)
  • Shipment 1 ── 0..1 Label (at most one)
  • Shipment 1 ──< TrackingEvent (many over time)
  • Address, Parcel, Customs — embedded as jsonb, not separate tables
💡Relational + jsonb hybrid

Structured, queried-on data (status, provider, amounts, FKs) is columns. Free-form, never-queried-individually data (addresses, parcel dims, customs, raw webhook bodies) is jsonb — flexible without a table explosion.

This is the access-pattern-driven store decision applied within one database.

🧩How an entity maps to a table (JPA)
@Entity @Table(name = "shipment")
class Shipment {
  @Id UUID id;
  UUID sellerId;
  @Enumerated(STRING) ShipmentStatus status;   // state machine

  @JdbcTypeCode(JSON) Address fromAddr;        // → jsonb column
  @JdbcTypeCode(JSON) Address toAddr;
  @JdbcTypeCode(JSON) Parcel  parcel;

  @OneToMany(mappedBy="shipment", cascade=ALL) List<Rate> rates;
  @OneToOne(mappedBy="shipment", cascade=ALL)  Label label;
  @OneToMany(mappedBy="shipment", cascade=ALL) List<TrackingEvent> events;
}

The @OneToMany/@OneToOne mappings are exactly the 1:N / 1:1 lines in the ER diagram; the jsonb embeds are the Address/Parcel value objects that don't earn their own tables.

Shipment state machine

The status column is driven by a state machine enforced in ShippingService — illegal transitions throw. Quote creates QUOTED; purchase advances to PURCHASED; webhooks drive the rest.

  ┌──────────┐  purchase()   ┌────────────┐  webhook    ┌────────────┐  webhook   ┌───────────┐
  │ QUOTED   │ ─────────────▶│ PURCHASED  │ ──────────▶ │ IN_TRANSIT │ ─────────▶ │ DELIVERED │
  └────┬─────┘               └─────┬──────┘             └──────┬─────┘            └───────────┘
       │                           │ cancel()                 │ exception
       │ expire(24h)                ▼                          ▼
       ▼                      ┌────────────┐            ┌────────────┐
  ┌──────────┐                │ CANCELLED  │            │ EXCEPTION  │
  │ EXPIRED  │                └────────────┘            └────────────┘
  └──────────┘

A QUOTED shipment that's never purchased expires after 24h. PURCHASED can be cancelled; in-transit shipments can land in EXCEPTION on a carrier problem.

Design takeaways — why this structure holds up

🔌The seam is the whole point

Carriers are plug-ins behind one interface. Adding DHL-direct = one new Adapter class + a routing rule. Business logic, controllers, and the schema don't change.

📐Layers enforce direction

api → service → carrier → domain/repo. DTOs at the edge, entities at the core, neutral carrier models in the middle. Nothing carrier-specific leaks upward.

🗄️Schema mirrors the aggregate

One root (shipment) + child tables with cascade. Columns for queried/structured data, jsonb for free-form. Money in integer cents. Tracking append-only with bigserial.

🧭Patterns chosen, not sprinkled

Adapter, Strategy (routing), Registry (namespaced IDs), Scatter–Gather (fan-out), State Machine. Abstract Factory explicitly rejected with a reason — that judgment is the staff signal.

🛡️Flyway owns DDL

ddl-auto: validate means Hibernate verifies but never mutates the schema. Migrations are versioned and reviewable — no surprise schema drift in prod.

⚠️Honest v1 gaps

No idempotency key on purchase yet (a money-flow must-have), single-parcel only, platform carrier accounts only, payments out of scope. All explicitly deferred — known, not missed.
