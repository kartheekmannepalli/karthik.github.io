System Design · Rate Limiting

The Token Bucket, explained.

A small amount of state, one elegant formula, and a fast shared store. That's the whole trick to letting bursts through while holding a steady long-run rate.

01The core idea

Picture a bucket that holds tokens. Every request must take one token to proceed. A refiller drips new tokens in at a fixed rate — say 10 per second — up to a maximum capacity. If the bucket has a token, the request is allowed and a token is removed. If it's empty, the request is rejected with a 429 Too Many Requests.

Capacity controls how big a burst you tolerate. Refill rate controls the sustained throughput.

That single property — burst capacity decoupled from steady rate — is why token bucket is the default answer in interviews. A fixed-window counter can't absorb a legitimate burst; a leaky bucket smooths output but won't let bursts through at all. Token bucket gives you both knobs.

Reject when empty, not when full

A common mix-up: here you reject when the bucket runs empty. That feels backwards only because you're picturing the leaky bucket — the two hold opposite things.

Token bucket
Holds tokens (permission). Requests spend them; refill tops them up.
full → great, burst awayempty → reject
Leaky bucket
Holds requests (water). Requests fill it; it drains at a fixed rate.
full → overflow, rejectempty → fine

Same word, opposite contents. In token bucket, tokens only fall per request and rise on refill — and refill is capped at min(capacity, …), so overflow is impossible by construction. The only failure mode is running out.

02The "lazy refill" formula

You never run a background thread dripping tokens into millions of buckets — that doesn't scale. Instead you store only two numbers per bucket and reconstruct the token count on the fly each time a request arrives, based on how much time has passed.

# on every request for a given key
now      = current_time()
elapsed  = now − last_refill
# top up by what *would* have dripped in, capped at capacity
tokens   = min(capacity, tokens + elapsed × refill_rate)
last_refill = now

if tokens >= 1:
    tokens −= 1
    return ALLOW      # 200
else:
    return REJECT     # 429

No timers, no cron, no per-token bookkeeping. The math does the dripping. This is the part worth saying out loud in an interview — it shows you understand why the naive "thread that adds tokens" design falls over.

03Modeling a bucket as data

The key is whatever you're limiting on — user:123, an API key, a client IP, or a composite like ip + endpoint. Choosing the key is the policy. The values are tiny, so even tens of millions of buckets cost very little memory.

State vs. policy — where capacity & rate live

Notice the bucket stores only tokens and last_refill. Capacity and refill_rate are deliberately not in the row — they're a different kind of thing, and the limiter feeds them into the calculation (that's why the Lua script takes them as ARGV, not from the bucket).

Policy usually sits in a small tier→limits map — a config file, env vars, a config service, or a tiny table — cached in memory on each app server since it changes rarely:

free       = { capacity: 10,    refill_rate: 5/sec   }
pro        = { capacity: 1000,  refill_rate: 100/sec }
enterprise = { capacity: 10000, refill_rate: 2000/sec }

So each request is two lookups: resolve policy (what tier is user:123? → free → {10, 5/s}), then run the bucket with those numbers against the stored state. A million free users share one {10, 5/s} — duplicating it into every row would waste memory and turn a limit change into a million-row rewrite. Change it once, it applies everywhere.

Per-key overrides

Need one enterprise customer on a custom limit? Resolution becomes per-key override → tier default → global default, and only that one key carries its own numbers. Everyone else still shares the tier config.

Who defines the refill rate?

The team that owns the API, as a deliberate capacity-planning and product decision. The rate must sit under what the DB, downstream services, and infra can sustain (the engineering ceiling), it enforces fairness so one client can't starve the rest, and it encodes business tiers — the SLA you advertise is a refill rate (100 req/min = ~1.67/sec). Refill rate is sustained throughput; capacity is how much burst you'll forgive on top of it. Both are chosen by humans, then handed to the algorithm per request.

04Where Redis comes in

A rate limiter sits on the hot path of every single request, and in any real system there are many app servers behind a load balancer. That combination dictates the storage. Redis fits because of four properties:

Speed

It's in-memory, so a read-modify-write is sub-millisecond. You can't add 20ms of disk latency to every request just to check a limit.

A shared source of truth

If each app server kept its own in-memory bucket, a user hitting 5 servers would get 5× the intended limit. One central Redis means the limit is global no matter which server answers.

Native data structure + auto-expiry

A Redis hash stores both fields under one key, and a TTL garbage-collects buckets for clients who go quiet — no cleanup job required.

HSET rl:user:123 tokens 7.4 ts 1717632000.218
EXPIRE rl:user:123 60   # bucket disappears if idle

Atomic execution

This is the one that bites people — see below.

05The atomicity gotcha

The interview trap

If you do GET → compute in your app → SET, two concurrent requests can both read "1 token left," both decide ALLOW, and both write back. You just served two requests on one token. The read-modify-write must be atomic.

The clean fix is a Lua script. Redis runs it single-threaded and atomically — the whole refill-check-decrement happens as one indivisible step, and it's a single network round trip instead of three.

-- KEYS[1]=bucket  ARGV: rate, capacity, now, cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or ARGV[2]   -- new bucket starts full
local ts     = tonumber(b[2]) or ARGV[3]

-- lazy refill, capped at capacity
tokens = math.min(ARGV[2], tokens + (ARGV[3] - ts) * ARGV[1])

local allowed = tokens >= ARGV[4]
if allowed then tokens = tokens - ARGV[4] end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('EXPIRE', KEYS[1], math.ceil(ARGV[2] / ARGV[1]))
return allowed

Same logic as section 2, but now race-free and one round trip. (INCR + EXPIRE can do a simpler fixed-window limiter, but token bucket's refill math wants the script.)

06Say these in the interview

why bucket?
Capacity = burst, rate = sustained. It absorbs spikes while bounding the long-run average — fixed windows and leaky buckets each give you only one of those.
why lazy?
Store 2 numbers, compute refill on read. Avoids per-token background work, scales to millions of keys.
why redis?
Sub-ms, shared across servers, hash + TTL, atomic Lua. The shared-state point is the real reason — local counters multiply the limit by your server count.
scaling it?
Shard by key so each bucket lives on one node; the hot key is naturally spread. A single Redis is a SPOF — mention replication or a cluster.
trade-off?
Accuracy vs. latency. Strict global limits need that central round trip. For extreme scale, some allow small local buckets that sync periodically — sloppier, but cheaper per request.
