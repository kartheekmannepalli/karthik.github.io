00

The trap in the prompt

Async decomposition is table stakes. The interviewer is separating candidates on points-correctness. And there's a hard product tension hiding in it:

// you can have at most TWO of these three
⚡ fast ack (<100ms) 🔎 content-based dedup ⏱ immediate duplicate rejection
Content dedup needs the extracted text → needs OCR. OCR is slow → must be async to keep the ack fast. Therefore duplicate detection is necessarily asynchronous. The user learns "this was a duplicate" via status / notification a few seconds later — not at POST time.
01

Architecture & data flow

Two swim-lanes: a synchronous ingest that acks in <100ms, and an asynchronous processor that does the slow, risky work. The single source of truth (DB) is written by both — once provisionally, once on award.

happy path idempotency-critical write bytes / cache feed ⛨ guarded & atomic

04

No double-awarding — defense in depth

There is no single trick. Duplicates arrive in four different shapes, each needing its own guard — plus a safety net that assumes one slipped through anyway.

1
Content-derived dedup keycanonicalize → hash
catchesthe same receipt, re-photographed — different bytes, same purchase. Keyed on extracted content, never image bytes.
2
Atomic conditional writePutItem · attribute_not_exists
catchesconcurrent identical uploads racing a read-check-write. First writer wins; the second fails the condition.
3
Atomic status transitionUPDATE … WHERE status=received
catchesqueue redelivery after a crash (at-least-once). Already-processed → the update matches nothing → no-op.
4
Idempotent points ledgerledger entry keyed by receiptId
catchesbalance drift on a replayed award. The balance write — not the receipt row — is the non-idempotent op everyone forgets.
⛨
Reconciliation jobnightly sweep + alert
safety netIn a points system, detecting drift matters as much as preventing it. Sweep for double/missing awards and alert.

Why userId scope? Two strangers with identical carts must not collide. The residual hole — two users farming one physical receipt — closes only with the transaction #. With four fields alone you cannot tell "same receipt twice" from "two identical carts," so user-scope is the safe default and txn# is the real fix.
06

A redelivered message is a no-op

The headline failure: Processor awards points, then crashes before acking. The queue redelivers. Here's why it doesn't double-award.

✕ Without the guard

1OCR + match → +500 pts written
2balance updated · ledger += 500
3💥 crash before ACK
4queue redelivers same message
5balance += 500 again → 1000 pts

✓ With atomic transition + ledger

1guard flips received → processed
2ledger insert keyed by receiptId
3💥 crash before ACK
4queue redelivers same message
5status≠received → 0 rows → no-op ✓
UPDATE receipt SET status='processed', points=:p WHERE receiptId=:id AND status='received'; -- 0 rows on replay
