Tracking Event Ingestion — High-Level Design

High-throughput webhook ingestion pipeline + live buyer-facing tracking reads. Hundreds of millions of events/day across all carriers.

"Carriers send us tracking events via webhook — package picked up, in transit, out for delivery, delivered, etc. We get hundreds of millions of events per day across all carriers. Design the ingestion pipeline. Users see live tracking on the buyer-facing page."

📋 Sections

The shape of this problem in one line

This is a write-heavy ingestion pipeline with a latency-sensitive read path bolted on. The whole design turns on four moves: (1) a tiny receiver that acks in milliseconds and does nothing else, (2) a durable log (Kafka) that decouples ingest from processing and absorbs spikes, (3) handling that events arrive out of order and duplicated, and (4) splitting reads into a hot "latest status" path and a cold "full history" path. Get those right and the scale takes care of itself.

Capacity math (drives every choice)

Turning "hundreds of millions" into numbers that justify the architecture — fast ack, a log buffer, and a wide-column store.

# Write side (ingest)
300,000,000 events/day ÷ 86,400 s   ≈  3,500 events/sec average
peak burst (morning scan dumps, holidays) ~10×  ≈  35,000 events/sec peak
   → receiver must be tiny + horizontally scaled; a log (Kafka) absorbs the burst so
     downstream processors aren't sized for peak, only for sustainable drain rate.

# Storage
~0.5 KB/event × 300M/day      ≈  150 GB/day raw  (×3 replication ≈ 450 GB/day)
   → append-only, time-ordered, keyed by tracking number → wide-column store (Cassandra).
     Tier to cold storage (S3) after delivery + retention window.

# Read side (buyer page)
mostly "where is my package NOW" (1 row) >> full timeline reads
   → serve latest status from Redis (hot), full history from the event store (cold-ish).

The peak/average gap is the entire argument for putting a durable log between the receiver and the processors — you size the processors for ~sustained load and let Kafka soak the spikes.

Components

📥Webhook Receiver

The most important latency constraint in the system. Does the bare minimum and returns 200 fast — if it's slow, carriers treat it as failed and retry-storm you, multiplying load.

  • Verify per-carrier HMAC signature
  • Light shape validation only
  • Publish raw event to Kafka, then ack
  • Unverifiable / malformed → DLQ, still ack 200
statelessautoscaledack <50ms
🪵Kafka (the buffer)

Decouples ingest from processing and absorbs the 10× peak burst. Replayable, so a downstream outage doesn't lose data.

  • Partition by tracking_number → all events for one shipment land on one partition, in order
  • Retain ~7 days for replay/reprocessing
  • Processors scale by adding consumers up to partition count
⚙️Stream Processor

The brain. Consumes partitions in parallel and does the real work, idempotently.

  • Dedupe resent events (same carrier+tracking+status+time)
  • Normalize each carrier's status codes → one canonical enum
  • Upsert into the event store; conditionally advance current-status
  • Write-through the Redis latest-status cache
  • Emit terminal events (DELIVERED / EXCEPTION) to a notifications topic
🗄️Event store — Cassandra

Full append-only history. Wide-column fits the access pattern: massive writes, partitioned by tracking_number, read back time-ordered.

  • Partition = (carrier, tracking_number); clustered by occurred_at
  • Dedup built into the primary key — resends upsert the same row
  • No joins, no transactions needed — pure key-driven
⚡Latest-status store + Redis

The buyer page mostly asks "where is it now" — one row. Served from a small current-status table fronted by Redis for the hot path.

  • One row per shipment, overwritten on each newer event
  • Redis keyed by tracking_number, write-through on update
  • Cache miss → read current table → repopulate
👁️Tracking Read API

Buyer-facing reads. Two endpoints, two backends — latest from Redis, timeline from Cassandra.

  • GET /tracking/{id} → latest status (Redis)
  • GET /tracking/{id}/events → full timeline (event store)
  • Read path is fully decoupled from ingest — independent scaling
👁️

The two read paths (key insight)

"Users see live tracking" is really two different reads with opposite cost profiles. Serving both from one store would either be slow (scan the event partition every page load) or wasteful. Split them.

🔥 Latest status — the hot path

  • What the buyer page shows 95% of the time: "Out for delivery"
  • A single row per shipment, read constantly
  • Redis keyed by tracking_number → latest status JSON, write-through from the processor
  • Fallback to the tracking_current table on cache miss
  • O(1), milliseconds, survives most of the read load

🧊 Full timeline — the cold-ish path

  • The expandable "show all events" view — read far less often
  • All events for the shipment, in chronological order
  • Cassandra partition = tracking_number, clustered by occurred_at → one efficient partition scan
  • No cache needed; it's a bounded, infrequent query
  • Out-of-order arrivals sort correctly because the clustering key is the event time
🔀

Key design decisions

The non-obvious calls that separate a working pipeline from a correct one.

🔀Events arrive out of order

Carrier infra is messy — a late "in transit" can land after "delivered." Order by event time, never arrival time.

  • Event store clusters on occurred_at, so history sorts itself
  • Current-status updates are conditional: advance only if the new event's occurred_at > last_event_at
  • Prevents a stale late event from overwriting "Delivered" with "In transit"
🔑Dedup via the primary key

Carriers resend; at-least-once delivery from Kafka means we'll see duplicates. Instead of a separate dedup table, make the PK itself idempotent.

  • PK = ((carrier, tracking_number), occurred_at, status)
  • A resend of the same event upserts the same row — a no-op
  • No extra lookup, no race; the store enforces it
🧮Partition by tracking_number

One choice solves two problems: ordering and load spread.

  • All events for a shipment hit one Kafka partition → in-order processing per shipment
  • Millions of tracking numbers → load spreads evenly across partitions and Cassandra nodes
  • Watch for hot keys (a viral package) — mitigation below
⏱️Ack fast, process later

The receiver must never call Cassandra or do heavy work inline. Validate → enqueue → ack.

  • Sub-50ms response keeps carriers from retry-storming
  • All real work happens async in the processor
  • Durability comes from Kafka, not from finishing the work before acking
🔁Push primary, pull backstop

Webhooks are the main feed, but they drop/lag. A periodic poll for shipments with no recent events reconciles gaps.

  • Push = fresh, low latency
  • Pull = catches missed webhooks for in-flight shipments
  • Both feed the same pipeline through the receiver
🏷️Normalize to a canonical status

Every carrier names statuses differently. Map them once, in the processor, to a single enum the buyer page understands.

  • Keep the raw status too (audit / re-mapping later)
  • Canonical set: LABEL_CREATED · PICKED_UP · IN_TRANSIT · OUT_FOR_DELIVERY · DELIVERED · EXCEPTION · RETURNED

🧩Why these stores (access-pattern driven)
tracking_event   → massive append, time-ordered reads, key-driven, no joins
                   = wide-column (Cassandra / Scylla / Bigtable / DynamoDB)
tracking_current → tiny, one row per shipment, read-very-often
                   = same store keyed for O(1), fronted by Redis
cache            → the buyer-page header read path
                   = Redis, write-through, TTL'd
dead_letter      → low volume, inspected by humans
                   = a topic or a small relational table

No relational DB on the hot path — there are no joins, no multi-row transactions, just key-by-tracking-number access at very high write volume. That's the textbook wide-column case.

Failure modes & operability

What breaks at 35K/sec — and the mitigation

  • Receiver too slow → carrier retry storm. Keep it to verify-publish-ack; never touch the DB inline. Autoscale on request rate.
  • Hot tracking number (a viral / heavily-watched package). Redis hot key → use a local in-process cache layer or read replicas for that key.
  • Consumer lag → buyer page goes stale. Alert when lag > ~30s; scale consumers up to partition count; that's why the page is "seconds-fresh," not real-time.
  • Downstream store outage. Kafka's 7-day retention means we replay once it recovers — nothing is lost.
  • Carrier signature secret rotation. Per-carrier secret store with overlap windows so rotation doesn't reject valid events.
  • Poison events. Route to the DLQ and keep going — one bad payload never blocks a partition.
🔭Observability
  • Receiver ack-latency p99 (the carrier-storm guard)
  • Ingest rate & error rate per carrier
  • Kafka consumer lag (alert > 30s)
  • Dedup rate & DLQ rate
  • Redis hit rate; terminal-event → notification latency
📈Scaling levers
  • Receivers scale on request rate (stateless)
  • Throughput bounded by Kafka partition count → over-partition early
  • Cassandra scales by adding nodes; tracking_number spreads load
  • Read API scales independently of ingest
🧊Retention & cost
  • Hot event data in Cassandra for the active + recent window
  • Archive to S3 after delivery + N months (compliance)
  • Kafka retains 7 days for replay, then ages out
  • Redis holds only active shipments via TTL
