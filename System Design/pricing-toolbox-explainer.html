Inside the Pricing Toolbox Agentic Architecture

How a Slack message becomes an MCP tool call and back — with hotel-tax-mcp standing in as the Hollow MCP server. Built for explaining out loud in interviews.

Tool Executor = MCP client LLM never speaks MCP JSON-RPC ↔ function calling

01The Mental Model

The system is a brain (the LLM, which can only read and write text), a pair of hands (the Tool Executor, which actually touches external systems), and a nervous system (the Orchestrator + Agentic Loop, which carries messages between them until the job is done).

The single most important fact: the LLM never makes a network call. It only ever asks for a tool to be run by emitting structured JSON. Everything that actually executes — MCP calls, SQL, API hits — happens in the Tool Executor.

02What Each Component Does

Color-coded to match the diagram's groupings.

Entry points

Slack App · Pricing Toolbox UI · API User

Three front doors, one brain. Each channel just delivers a user message + identity to the Orchestrator. Keeping them thin means new channels (email, CLI) can be added without touching agent logic.

"We decoupled channels from the agent — the Orchestrator is channel-agnostic."
Control plane

Orchestrator

The traffic controller. Receives the user message, pulls in team-specific skills/context, asks the Tool Executor what tools exist right now, assembles message + context + tool definitions, and hands that to the LLM Service. It also owns the session and returns the final answer.

"The Orchestrator owns the conversation; the LLM is stateless between calls."
Knowledge injection

Team-specific Skills / Context

Prompt assets per team — Taskforce, On-Call, Price Mismatch playbooks. Injected into the system prompt so the same infrastructure behaves like a specialist for each team. This is config, not code.

"Skills let us ship new team behaviors as prompt/context changes, no deploy."
Execution plane

Tool Executor

The MCP client of the whole system. Two jobs: (1) discovery — at session start it calls tools/list on every registered MCP server and aggregates the catalog into one tool menu; (2) invocation — when the LLM asks for a tool, it routes the call to the right server, speaks the right protocol (MCP JSON-RPC for Hollow/Trino/Github…, plain REST for LPAS), enforces timeouts/auth/retries, and normalizes the result.

"The Tool Executor is a protocol adapter + router: LLM function-call JSON in, MCP JSON-RPC out, and back."
Execution plane

Agentic Loop

The while-loop around the LLM: call model → if it requested tools, execute them → append results to the conversation → call model again. Repeats until the model answers in plain text (or hits a max-iteration guard).

"It's literally: while (response.has_tool_calls) { execute; append; re-prompt; }"
LLM service

Context Manager

Builds the exact prompt payload: system prompt + skills, conversation history, tool results so far, and the tool schemas — trimmed to fit the context window (truncation/summarization policies live here).

"Context Manager decides what the model sees; it's our token budget owner."
LLM service

LLM Gateway → GenAI Proxy

Gateway picks a model and normalizes to one internal API. The GenAI Proxy is the enterprise chokepoint to Claude / GPT / Gemini: auth, rate limits, cost tracking, logging, failover. Cursor Agent reuses the same gateway from the IDE.

"One proxy means model swaps and cost controls happen in one place."
Tool layer

MCP Servers (Trino, Github, Atlassian, Slack/Glean, Hollow)

Each wraps one domain behind the standard MCP contract: tools/list + tools/call over Streamable HTTP (POST /mcp). Hollow MCP here = your hotel-tax-mcp: a Spring AI server exposing @Tool methods. The executor doesn't know or care what's behind it.

"MCP gives every tool the same shape — adding a server is registration, not integration."
Tool layer

LPAS Troubleshooter (Non-MCP)

The exception that proves the design: a legacy REST/RPC service. The Tool Executor wraps it in a tool definition by hand, so the LLM sees it identically to MCP tools. Adapters hide heterogeneity.

"Non-MCP services get hand-written adapters; to the model everything is just a tool."

03The Two JSON Dialects — and Who Translates

"Will the LLM receive the MCP response as JSON?" — Almost. The model never sees MCP's JSON-RPC envelope. The Tool Executor strips it and the result re-enters the conversation as a tool-result message whose content is text — usually JSON-stringified data. The model reads it like any other text in its context.

LLM World — "function calling"

model API format (Anthropic/OpenAI/Gemini)

{
  "type": "tool_use",
  "id": "toolu_01A",

}

    \"taxes\":78.0,\"fees\":45.0,
    \"grandTotal\":723.0,
    \"currency\":\"USD\"}"

MCP World — JSON-RPC 2.0

POST /mcp on Hollow (hotel-tax-mcp:8080) 
// executor → MCP server
{
  "jsonrpc": "2.0", "id": 7,
  "method": "tools/call",
  "params": {
    "name": "calculate_total_cost",
    "arguments": {
      "hotelId": "H001",
      "nightlyRate": 200,
      "nights": 3 }
  }
}

// MCP server → executor
{
  "jsonrpc": "2.0", "id": 7,
  "result": {
    "content": [{ "type": "text",
      "text": "{\"subtotal\":600.0,…}" }],
    "isError": false
  }
}
The precise interview answer:

"The MCP server returns a JSON-RPC envelope with a result.content array. The Tool Executor unwraps it and the orchestration layer appends it to the conversation as a tool_result message. The LLM consumes that as plain text tokens that happen to contain JSON — there's no special JSON channel into the model. That's also why concise, well-shaped tool output matters: the model has to read it, and every byte costs context tokens."

06Likely Interview Questions

Q: Why does the Tool Executor exist — why not let the LLM call MCP servers directly?
LLMs can't make network calls; they only emit text. Beyond that, centralizing execution gives you one place for auth, rate limiting, timeouts, retries, audit logging, and allow-listing — you never want a model output to translate into an unmediated network call. It also decouples protocols: models speak function-calling, tools speak MCP or REST, and neither needs to know about the other.
Q: How does the LLM know which tools exist?
At session start the executor aggregates tools/list from every MCP server. Each tool's name, description, and JSON Schema are placed into the model request. The model "knows" tools the same way it knows anything else in its prompt — the descriptions you wrote in @Tool(description=…) are literally what the model reads to decide when to call it.
Q: Is the tool response JSON when it reaches the model?
The wire response is JSON-RPC; the executor unwraps it to the inner payload; the model receives it as a tool_result message containing text — typically stringified JSON. The model parses it "by reading," not with a JSON parser. Implication: tool outputs should be compact and well-labeled, because they consume context tokens and the model must interpret them reliably.
Q: What happens when a tool fails?
MCP distinguishes protocol errors (JSON-RPC error) from tool-level failures (result.isError: true with an explanatory message). The executor passes tool failures back into the conversation so the model can recover — retry with different arguments, pick another tool, or tell the user. In hotel-tax-mcp, throwing IllegalArgumentException("Unknown hotel") becomes exactly such an isError result.
Q: Why MCP at all, instead of hand-wiring each integration?
Without MCP every tool×agent pairing is custom glue (M×N problem). MCP standardizes discovery (tools/list), invocation (tools/call), schemas, and transports — so adding the 7th server to this diagram is registration, not integration. The LPAS box shows the counterfactual: non-MCP services need bespoke adapter code in the executor.
Q: How would you scale / harden this?
Streamable HTTP MCP servers are stateless-friendly → horizontal scale behind a load balancer. Add per-tool timeouts and circuit breakers in the executor, parallel tool execution where calls are independent, max-iteration caps on the agentic loop, schema validation before dispatch, and an allow-list per team so the On-Call skill can't invoke pricing-mutation tools.
