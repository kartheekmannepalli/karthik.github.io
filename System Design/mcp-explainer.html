01The Protocol Stack

MCP is not a new wire format — it's JSON-RPC 2.0 messages with MCP-defined methods, carried over a transport. Your server uses the Streamable HTTP transport: one endpoint, POST /mcp.

MCP Semanticsinitialize · tools/list · tools/call
JSON-RPC 2.0{"jsonrpc":"2.0", "method":…, "id":…}
Streamable HTTPPOST /mcp → JSON or SSE stream back
HTTP/1.1 · TCPport 8080, embedded Tomcat

Each layer wraps the one below it. The client never calls your Java methods directly — it sends JSON-RPC envelopes that Spring AI translates into method calls.

07Streamable HTTP vs SSE — What's Actually Happening

SSE (Server-Sent Events) is not a separate protocol from HTTP — it's a normal HTTP response that the server keeps open and writes to over time, instead of replying once and closing. "Returning an SSE" means: same request, but the answer arrives as a stream of events.

NORMAL HTTP RESPONSEone shot
HTTP/1.1 200 OK
Content-Type: application/json

{ "jsonrpc":"2.0", "id":7, "result":{…} }

← body complete, connection done.
SSE RESPONSEstays open, drip-feeds events
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: message
data: {"method":"notifications/progress",…}

…seconds pass, connection still open…

event: message
data: {"jsonrpc":"2.0","id":7,"result":{…}}

← final result delivered, server closes stream.

An SSE body is just lines of event: / data: separated by blank lines. It's one-directional: server → client only. The client can never send data up an SSE stream — it always uses a new POST for that.

How /mcp decides: JSON or SSE?

Every client POST declares Accept: application/json, text/event-stream — meaning "I can handle either." The server picks per request:

POST /mcp  arrives with a JSON-RPC request
Does the server need to send anything before the final result?
NO — quick tool call
Reply with plain JSON Content-Type: application/json
Single response body, connection closes. This is what your fast tax-lookup tools get.
YES — progress / long-running
Upgrade the response to SSE Content-Type: text/event-stream
Stream progress notifications as events, finish with the JSON-RPC result, then close. Same connection, same request.

Key insight: in Streamable HTTP, SSE is not a separate channel — it's an optional response format for a single POST. The keep-alive-interval: 30s in your YAML sends heartbeat pings so proxies don't kill idle streams.

The three verbs of /mcp

One endpoint, three behaviors depending on HTTP method:

POST /mcp

Client → Server messages

Every request, response, and notification the client sends. Server replies with JSON or an SSE stream (above). This is the workhorse — a basic server needs nothing else.

GET /mcp

Standing listening stream (optional)

Client opens a long-lived SSE stream so the server can push unsolicited messages anytime — e.g. tools/list_changed notifications or sampling requests. Not tied to any POST.

DELETE /mcp

End session

Client sends its Mcp-Session-Id header to terminate the session and let the server free resources.

Streamable HTTP vs the legacy "HTTP+SSE" transport

The old transport's confusing trait: you POSTed to one URL but the answer came back on a different, permanently-open SSE connection. Streamable HTTP fixed this.

🟢 Streamable HTTP (yours, spec 2025+)

connection #1 opens
→POST /mcp  {tools/call}
←response (JSON or SSE)
connection #1 closes
connection #2 opens
→POST /mcp  {tools/call}
←response
connection #2 closes

Request and response share one connection. Stateless-friendly → works behind load balancers, serverless, easy to scale.

🟠 HTTP + SSE (legacy, deprecated)

SSE connection opens at startup… stays open for the whole session
→GET /sse
←event: endpoint (where to POST)
←response to call #1  (!)
←response to call #2  (!)
→POST /mcp/message {call #1} ← 202 Accepted, empty
→POST /mcp/message {call #2} ← 202 Accepted, empty

Two endpoints; all results arrive on the separate SSE channel. Server must hold one open connection per client forever → hard to scale, breaks on reconnect.

The trade-off axis: annotation-driven frameworks (Spring AI, Quarkus, FastMCP) hide the protocol and generate schemas for you, while raw SDKs give control at the cost of boilerplate. The wire protocol is identical in every case — clients can't tell them apart.
