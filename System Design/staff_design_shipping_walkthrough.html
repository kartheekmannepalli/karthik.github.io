Staff-Level Design Walkthrough

Shipping rate-quote & label service · what the same boxes look like once you add the decision layer · CodeSignal / system-design round

"eBay needs a service that lets sellers get shipping rate quotes and generate labels across multiple carriers — USPS, FedEx, UPS, DHL, and regional carriers. Design this system. Focus on backend. Walk me through how you'd build it."

⚡ The one idea this whole doc is built on

A senior diagram and a staff diagram can have identical boxes. The difference is that the senior presents each choice as inevitable, while the staff candidate makes the forks visible — names the alternative considered and rejected, ties it to a number or a requirement, and states what they'd revisit at 10× scale. The artifact barely changes; the reasoning around it is the entire level difference. Everything below is that reasoning layer, slotted onto the components you already drew.

~45 min

Step 2 — Capacity math that drives the architecture

The senior move is to write "10K quotes/sec" and move on. The staff move is to derive the consequence and let it justify every later decision.

# Quotes
10,000 quotes/sec  ×  ~4 carriers per quote   = 40,000 downstream carrier calls/sec  (uncached)
   → no carrier API tolerates that; they'd rate-limit us instantly. Caching is MANDATORY, not nice-to-have.
With ~80% cache hit (traffic is lane-skewed)   = ~8,000 live calls/sec ≈ 2,000 / carrier
   → still high for the big carriers → this is the seed of "ingest rate cards" (Fork 1, option C).

# Labels
1,000 labels/sec  =  1 carrier call + 1 charge + 1 durable write each
   → Postgres at ~1K writes/sec is fine with the right indexes; the hard part is correctness, not throughput.

# Storage
labels ≈ 1 KB/row.  Peak 1K/sec, but daily AVERAGE far lower.
   → archive to cold storage (S3) after N months; keep hot rows in Postgres for void/refund window.

Saying "40K/sec, which is why caching isn't optional" out loud is worth more than any box. You derived a constraint from your own number.

Step 5 — The fork points (the actual staff signal)

At each of these, a senior states the answer; you state the menu, then choose and justify. Seven forks this prompt naturally contains.

FORK 1How do we get rates at all?
A · Live every time

Call all carriers on every request. Dies at 40K/sec, carriers rate-limit, p99 is hostage to the slowest carrier.

B · Cache quote responses ✓ start here

Cache-aside on the rate-basis key. ~80% hit on hot lanes. Stale up to TTL — fine, a quote is an estimate.

C · Ingest rate cards

Pull carrier rate tables nightly, compute locally. Most robust, no live dep. Cost: a daily pipeline + replicating dim-weight/surcharge logic.

Decision: Start with B for time-to-market; it survives the stated 10K/sec. Move toward C for the high-volume carriers as cost/scale grows — likely a hybrid: rate-card ingestion for the big 4, live+cache for the long-tail regionals whose cards we don't want to replicate.
Say: "Full addresses look uncacheable, but carriers price on ZIP3-derived zones, not street addresses — so I cache on the rate basis, not the address. Traffic is lane-skewed, so hot lanes give the hit rate; the tail misses and falls through, which is fine."
FORK 2Is a stale cached quote a correctness problem?
A · Cache everything incl. price charged

Simple, fast — but you can charge a seller a stale/wrong price. Unacceptable for a money flow.

B · Cache the quote, never the charge ✓

The browse-time number is cached; the purchase does a fresh authoritative call and re-validates via quoteId.

Decision: The cache lives entirely on the quote (estimate) side of the consistency boundary. The label purchase is never cached — it re-prices fresh and binds to the quoteId so the seller is charged what they were shown, even if the cache was stale. This is the system's core correctness invariant.
FORK 3Sync or async label generation?
A · Sync happy path ✓

Carrier label APIs are typically sub-2s and the seller is waiting. Best UX. Make them wait on the common case.

B · Async + durable backbone

Not the default — the fallback. For timeouts after charge, you need a durable record + reconciliation so a charged label is never lost.

Decision: Sync happy path, async/durable backbone. The driver for async isn't latency — it's that this is a charged operation that can't be left in an unknown state. Persist PENDING before the carrier call; hard-timeout the sync wait at ~5s; past that the client gets "processing, we'll notify you" and the reconciler resolves it.
Say: "Sync because the seller's waiting and the API is fast — but I back it with a durable PENDING record and a reconciliation job, because if the carrier call times out after I've authorized payment, I can't leave that ambiguous. That'd be a double-charge or a charged-but-no-label bug."
FORK 4Charge before or after the carrier confirms? (the saga)
A · Capture charge, then generate

If generate fails you owe a refund — slower, more visible to the seller, reconciliation-heavy.

B · Authorize → generate → capture ✓

Reserve funds first, generate the label (the irreversible carrier-side cost), then capture. If generate fails, just release the auth — cheaper than a refund.

2PC across services

Distributed transaction across Payments + Carrier doesn't scale and most carriers can't participate. Don't.

Decision: A saga with compensators, ordered auth → generate → capture. Each step has an undo: release the payment auth, or void the label via the carrier's void API. The carrier-side label generation is the expensive irreversible step, so payment brackets it (reserve before, capture after).
FORK 5Direct carrier integration or an aggregator?
A · Direct to every carrier

Full control, no per-label middleman fee. Cost: N integrations to build + maintain, each with its own SOAP/XML/auth quirks.

B · Aggregator (EasyPost/Shippo)

One integration, they absorb carrier quirks. Cost: per-label fee, you inherit their downtime, less control.

C · Split by volume ✓

Direct for the big 4 (volume justifies the build; aggregator fees would be enormous at our scale). Aggregator for the long-tail regionals (not worth N bespoke integrations).

Decision: Hybrid by volume. The connector interface is identical either way, so an "aggregator connector" slots in behind the same Carrier port as the direct ones — the routing layer doesn't care. That's the Adapter pattern earning its keep.
FORK 6What's the failure blast radius?
A · One pool, shared fate

A slow FedEx exhausts shared threads → every carrier's quotes hang. One dependency sinks the whole service.

B · Isolate per carrier + per region ✓

Bulkhead (own pool) + circuit breaker per carrier; partition by region. DHL down → only EU degrades, and only to "fewer options."

Decision: The failure domain is the carrier-within-region, not the service. Degrade gracefully: a quote with 3 of 4 carriers is still a useful quote. The circuit breaker is just the mechanism — the decision is "I'd rather return partial results than fail the request."
Say: "If DHL's API is down, EU sellers see fewer carrier options for a few minutes; US sellers are completely unaffected because I isolate per region. I'd rather degrade to fewer options than fail the whole quote."
FORK 7Which data store for which job?
Labels → Postgres ✓

Money + state machine + void/refund window need transactions and strong consistency. Relational, indexed on idem_key + shipper.

Quote cache → Redis ✓

Ephemeral, fast, TTL'd. Losing it is harmless — it just repopulates.

Rate cards → read-optimized store ✓

If/when Fork 1-C lands: bulk-loaded daily, read-heavy, no transactions needed.

Decision: Store choice follows access pattern, not a single house DB. Strong-consistency money data is relational; the disposable hot cache is Redis; the daily bulk rate data is a read store. (Tracking-event ingestion, if it were in scope, would be a 4th: high write volume → Cassandra.)

The label must-haves (don't ship without these)

These aren't "staff vs senior" — they're correctness table-stakes for a money flow. Get them on the page early so the interviewer doesn't have to fish for them.

🔁Idempotency key
  • Client sends a key per logical purchase; LabelService checks it first
  • Seen before → return the existing label, don't regenerate or re-charge
  • Stored in the same txn as the label row so the check is atomic
  • Survives double-click, retry, network blip — the #1 money-bug guard
🚦Label state machine
enum LabelStatus {
  REQUESTED,          // row created
  PAYMENT_AUTHORIZED, // funds reserved
  GENERATED,          // carrier returned label
  USED, VOIDED, REFUNDED
}
// transitions guarded — can't void a USED label,
// can't refund twice, can't generate from REFUNDED

Step 6 — The scale curve (owning the trajectory)

Senior designs for a point. Staff designs for a curve and says what changes at the next order of magnitude — even if you don't build it now.

📍Today · 10K quotes/sec
  • Cache-aside in Redis (Fork 1-B)
  • Direct connectors for big 4, aggregator for tail (Fork 5-C)
  • Sync label happy path + reconciler (Fork 3)
  • Postgres for labels, single region per data residency
🚀10× · 100K quotes/sec — what changes
  • Rate-card ingestion becomes mandatory (Fork 1-C) — can't live-call even with caching
  • Two-tier cache: in-process L1 near-cache + Redis L2 to cut round-trips
  • Connectors become per-carrier services so teams own them independently — the multiplier move
  • Label workers scale horizontally off the queue; Postgres shards by shipper or region
🔭Observability (the sentence most skip)
  • Latency p50/p95/p99 per carrier, tagged by carrier name
  • Carrier error rate; alert >5%. Cache hit rate; alert <60%
  • Circuit-breaker state transitions logged + alerted on flap
  • Label success rate per carrier; nightly reconciliation for orphans
  • Correlation ID propagated quote → label → carrier call
✅

The litmus test before you call it done

Ask yourself these — they're how the interviewer is scoring you

  • Could a competent senior have drawn this exact diagram? Probably yes. So the boxes aren't the signal.
  • Did I name an alternative I rejected at every major box? If no fork was visible, it read as senior.
  • Did my scale number do work? "10K/sec" must cause a decision (caching), not just sit there.
  • Did I draw the consistency boundary? Where eventual is fine vs. where strong is mandatory is the core correctness story.
  • Did I reason about blast radius? "What breaks, who's affected, how do I degrade" — not just "add a circuit breaker."
  • Did I say what changes at 10×? Owning the multi-year trajectory is the multiplier signal.
  • Is it still concrete? Staff is senior plus the tradeoff layer — keep the connectors and the schema; don't retreat into hand-waving abstraction.
