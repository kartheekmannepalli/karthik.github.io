Coding / Build Round

Build a working feature or small app with AI assist. Use the workflow + implementation checklist below.

🏗️

System Design Round

Design an architecture or data model. Use the design workflow + design checklist further down.

🧑 Human first, AI second

Clarify requirements with the interviewer before you touch the AI. That conversation is your ambiguity-handling signal — the single thing they're watching for. Leading with a pre-baked prompt reads as a script.

🔁 AI = junior engineer

Don't hand it a full spec and wait. Keep a tight loop: ask for one small unit → review in 30s → ask for the next. Review time should roughly equal generation time.

📝 AI output is a draft

Read every line. AI commonly misses null checks, skips error handling, hallucinates API methods, and over-engineers. Saying "let me review this before I run it" out loud signals maturity.

AI-Assisted Session Workflow

Coding Round

Follow this order every time. Skipping the clarify step, or letting the AI build everything in one shot, is the most common reason candidates build the wrong thing confidently. Times assume a ~60-min session — scale down proportionally for shorter ones.

1
Listen & clarify — with the interviewer
0–5 min
  • Hear the full problem before touching the editor
  • Ask: input source & shape (API / file / stdin), nullable or optional fields + defaults
  • Ask: output format, sort/filter rules, whether order must be deterministic
  • Ask: which error cases matter vs. can be ignored; what scale (100 items or 10M?)
  • Write a 3–5 line summary and read it back
Say: "So to confirm — I'm reading from X, transforming by Y, filtering out blanks, returning JSON sorted by Z. Anything I'm missing?"
2
Bring in the AI — paste your instructions
< 2 min
  • Have an instructions block (AGENT.md) pre-written — never write it live
  • Paste it as a comment at the top of the editor, or as your first message to the AI panel
  • End it with: "Acknowledge with 'Ready' and wait for requirements."
  • Then send your clarified requirements as the second message
3
Ask for the plan only — no code
~3 min
  • Constrain the format hard so it's reviewable in 30 seconds, not 3 minutes
  • If it ignores the constraint and writes paragraphs, interrupt mid-generation
Prompt: "Don't write code yet. Give me the plan as 1 ASCII flow diagram + max 8 bullets. No prose, no headers."
If it rambles: send a new message immediately — "Stop. Shorter. Just the diagram and bullets."
4
Review the plan out loud
~3 min
  • Go line by line against your own mental model, narrating to the interviewer
  • Flag what the AI missed — this narration is worth more points than the plan itself
Say: "Data flow looks right. I'd split the external client into its own class instead of the service. And it missed the empty-string case, not just null. Let me add that."
5
Build chunk by chunk
~25 min
  • One unit per prompt: models → one service method → error handling → controller/handler → tests
  • No single prompt should produce more than ~30 lines. Review each chunk before the next
  • Narrate the architecture decision while the AI generates (see "Drive the AI" below)
6
Edge-case walkthrough — before running
~5 min
  • Name the cases out loud even if you can't code them all: empty input, null fields, zero/negative, max boundary, duplicate/retry
  • Naming them demonstrates mature engineering instincts and earns signal
7
Tests → demo
final ~7 min
  • Unit tests first (mock externals), then integration tests where logical
  • Run it live; clear the output panel and read the freshest output before deciding the next step
  • Wrap up: state known gaps + what you'd do with more time

Drive the AI — Chunked Prompting

Both Rounds

The core fix for slow, hard-to-review AI output: flip from "big prompt → big answer" to one small unit at a time. Each chunk generates in 10–15 seconds instead of 60–90, so you stay engaged and catch problems immediately. The wait is narration time, not dead time. Works the same whether you're generating code or drafting a design.

Prompt the AIWhat you do / say while it responds
"Define only the data models / DTOs. Nothing else."Verbally describe the shape to the interviewer
"Now the service interface + just the core method."Review & narrate the core logic
"Add error handling to that method using a typed result."Check the error model is correct
"Now the handler — thin layer only, no business logic."Verify it just delegates to the service
"Unit tests for the core method — happy path + 3 edge cases."Name the edge cases you expect before they appear

🔑 Rules of thumb for the live session

  • While it builds: narrate what you expect before it appears — "my guess is it'll propose a service + handler + a separate util; let me see if it agrees." You then review against your own model, not cold.
  • If you're waiting 3× longer than you're reviewing, your prompts are too big. Break them down.
  • Pre-read headers as code streams in and flag what you'll review first.
  • Treat every chunk as a draft — read it line by line out loud before accepting it.
  • Know the platform cold: practice in the CoderPad or CodeSignal sandbox beforehand. Output panels, the AI chat location, and run shortcuts differ — don't learn them live.

Implementation Checklist — Things to Consider

Coding Round

The dimensions to think through before and during the build. You won't hit all of them in an hour — but naming the ones you're consciously deferring (and why) is itself a strong signal. Code snippets are illustrative — adapt to your language/stack.

🔁1 · Input / Output Models
  • Exact input shape: JSON, CSV, query params, headers, body?
  • Nullable / optional fields — what's the default when missing?
  • Define the valid-vs-invalid boundary before coding
  • Output format: raw JSON, structured object, paginated?
  • Field naming convention — camelCase vs snake_case
  • Must output be deterministic (same input → same order)?
  • Max payload size to handle
🛠️2 · Language & Framework
  • Pick what you debug fastest live — not the theoretically "best"
  • Fast to scaffold: Python+FastAPI, Go+Gin, Node+Express, Java/Kotlin+Spring
  • Avoid heavy frameworks for a 60-min build — stdlib is often enough
  • Ask the interviewer: "Preferred language, or flexible?"
  • Check what's available in the CoderPad/CodeSignal environment before importing exotic libs
⚠️3 · Error Handling
  • External dependency down → timeout, retry, or fail fast?
  • Prefer a typed result/error model over scattered exceptions
  • Distinct error types: NotFound, Validation, Upstream, Parse
  • Map errors to responses in one place (global handler / middleware)
  • Handle 4xx → validation/not-found, 5xx → upstream, network → upstream
  • Never expose internal stack traces in responses
Illustrative (typed result) 
// One return type that's either success or a typed error
Result = Success(data) | Failure(AppError)
AppError = NotFound | Validation | Upstream | Parse
🧪4 · Testing
  • Unit (always): core logic in isolation, mock external deps
  • Cover: happy path, empty input, null fields, invalid input, each error branch
  • Descriptive names: returnsEmpty_whenAllNamesNull
  • Keep unit tests framework-free where possible — fast feedback
  • Integration (where logical): full request→response; stub external HTTP (e.g. WireMock / nock / responses)
  • Don't test: getters/setters, framework wiring, log statements
📋5 · Logging & Observability
  • Structured (JSON) logs, not print debugging
  • Levels: DEBUG (state) · INFO (requests, key events, external call + latency) · WARN (retries, fallbacks) · ERROR (unhandled, upstream fail)
  • Log every inbound request via middleware — not by hand per handler
  • Log every outbound call: target, status, latency
  • Correlation ID propagated through all logs of a request
  • Never log secrets, tokens, PII, or payment data
⚡6 · Performance & Latency
  • Set explicit connect + read timeouts on every external call
  • Write clear code first — don't optimize prematurely
  • Use the right structure: map for O(1) lookup vs O(n) scan
  • Pagination / streaming for large result sets
  • Async / parallel calls only where it genuinely helps
🔐7 · Security
  • Validate & sanitize all inputs; validate headers
  • Secrets / API keys from environment variables only — never committed
  • No secrets in source or logs
  • No stack traces or internal details leaked in responses
  • Auth/token check on endpoints if the prompt implies users
🔧8 · Configuration
  • All external values in config — nothing hardcoded
  • Typed config object rather than scattered string lookups
  • Separate config per environment (local / prod)
  • Secrets come from env vars, not committed files
Illustrative 
// One typed config object, loaded once
AppConfig { apiUrl, timeoutMs, maxRetries }
// values from env / config file, never inline literals
🏗️9 · Code Structure
  • Separate layers: handler/controller → service → repository / util
  • Interfaces only where they earn their keep (services, repositories) — not everywhere
  • Max function length ~20 lines — extract if longer
  • Prefer immutable data + copies over mutation; composition over inheritance
  • One responsibility per class — if you can't name it, split it
  • No business logic in handlers or data classes
📝10 · Documentation
  • README: what it does, how to run, config values, known gaps
  • Inline comments only for non-obvious logic or workarounds — never for self-explanatory code
  • Document the API contract: endpoints, request/response shape, error codes
  • TODO comments to flag intentionally deferred work
  • Many companies grade take-homes on README quality — treat docs as part of the deliverable

System Design Session Workflow

Design Round

A repeatable structure for any design prompt. If AI assist is allowed, use it to enumerate options, draft API specs/schemas, and sanity-check capacity math — but you own the architecture and must voice the tradeoffs. Don't let the AI's first answer become your design; interrogate it the same way you'd interrogate a junior's proposal.

1
Clarify requirements
~5 min
  • Functional: core use cases, who the users are, what's in / out of scope
  • Non-functional: latency target, availability, consistency needs, scale
  • Lock scope explicitly before drawing anything — Staff candidates set scope, juniors accept it
Say: "Before I design — is this read-heavy or write-heavy? Do we need strong consistency anywhere, or is eventual fine? Global or single-region?"
2
Scale & capacity estimates
~3 min
  • Back-of-envelope: QPS (peak vs average), DAU, read:write ratio
  • Storage growth/year, bandwidth, payload sizes
  • These numbers justify every later decision (cache? shard? replicas?)
3
API / contracts
~5 min
  • Define the key endpoints / interfaces: method, inputs, outputs
  • REST vs gRPC vs GraphQL — and why
  • Pagination, idempotency keys, versioning where relevant
AI assist: "Draft the REST contract for these 3 operations as a table." Then you review & correct.
4
High-level architecture
~8 min
  • Draw the boxes: clients → gateway/LB → services → data stores → queues
  • Justify each component — don't add boxes you can't defend
  • Mark sync vs async paths
5
Deep dive — 1–2 components
~10 min
  • Data model / schema: entities, relationships, indexes, partition key
  • The hard part: hot path, consistency boundary, the bottleneck
  • SQL vs NoSQL decided by access pattern, not by trend
6
Failure, scale-out, observability
~5 min
  • What breaks? node loss, network partition, dependency down, hot key
  • Mitigations: replicas, circuit breakers, retries+backoff, bulkheads
  • How you'd detect it: metrics, alerts on SLOs — most candidates skip this, don't

Design — Things to Consider

Design Round

The dimensions an interviewer scores. You don't cover all ten exhaustively — you raise them, then go deep where the problem demands it. Voicing the tradeoff you considered and rejected is the senior/staff signal.

🎯1 · Requirements
  • Functional: core use cases, explicit in/out of scope
  • Non-functional: latency, availability, consistency, durability
  • Ask 3–4 clarifying questions before drawing — set scope, don't accept it
📊2 · Scale & Estimates
  • QPS (peak vs average), DAU/MAU, read:write ratio
  • Storage/year, bandwidth, average + max payload size
  • Growth assumptions — design for 10× current, not 1000×
🔌3 · API & Contracts
  • REST / gRPC / GraphQL — and the reason
  • Endpoints, request/response shapes, status codes
  • Versioning, pagination, idempotency keys for writes
  • Rate limiting & auth at the boundary
🗄️4 · Data Model
  • Entities, relationships, access patterns first — schema follows
  • SQL vs NoSQL by access pattern, not trend
  • Indexes, partition/shard key, avoid hot keys
  • Normalization vs denormalization for read speed
📈5 · Scalability
  • Horizontal scaling + load balancing for stateless services
  • Caching: where, TTL vs event-invalidation, hit-rate target
  • Read replicas, CDN for static assets
  • Async queues to absorb spikes & decouple
🛡️6 · Reliability & Failure
  • Enumerate failures: node, network partition, dependency down, hot key
  • Circuit breakers, retries + backoff (idempotent only), bulkheads
  • Graceful degradation & fallbacks
  • Idempotency for anything money- or state-changing
⚖️7 · Consistency
  • Strong vs eventual — name where each applies
  • CAP: pick the tradeoff per data type, not globally
  • Money/inventory → strong; feeds/search/counts → eventual is fine
  • Saga / outbox for cross-service consistency (not 2PC)
🔭8 · Observability
  • Metrics: latency p50/p95/p99, error rate, throughput per dimension
  • Structured logs with correlation IDs; distributed traces across services
  • Alerts on SLOs, not raw symptoms
  • One sentence here instantly elevates you — most candidates skip it
🔐9 · Security
  • AuthN / AuthZ at the gateway and between services
  • Input validation, rate limiting, secrets management
  • Encryption in transit + at rest; PII handling
  • Principle of least privilege for service-to-service calls
🔀10 · Tradeoffs (the signal)
  • Every choice comes with the alternative you rejected and why
  • "Kafka for replayability — tradeoff is ops complexity; at this scale it's worth it"
  • Latency vs throughput · coupling vs cohesion · sync vs async · push vs pull
  • Tie decisions back to the requirements from step 1

Common Forks — Decisions to Think Through in Most Designs

Design Round

Almost every system-design prompt hides the same recurring forks. The senior move is to pick one and move on; the staff move is to name the alternatives, choose, and justify against a requirement or a number. Walk these as a mental checklist — for each, ask "does this design have to make this choice, and have I voiced why?" Each card lists the choices to weigh and the question that decides it.

⚖️1 · Strong vs Eventual Consistency
Where must data be correct-right-now vs. correct-eventually? This is usually the core correctness decision in the whole design.
AStrong — reads see the latest write. Needed for money, inventory, auth, anything a user is charged for.
BEventual — replicas converge over time. Fine for feeds, search, counts, caches, analytics.
Decide by: Pick per data type, not globally. "What's the cost of a stale read here?" If it's a wrong charge → strong. If it's a slightly-old like count → eventual.
🔄2 · Sync vs Async
Does the caller wait for the work to finish, or get an ack and a promise it'll happen?
ASync — simpler, lower latency to a result, easier client. Ties up a thread/connection for the duration.
BAsync — resilient, decoupled, absorbs spikes via a queue. Needs status tracking, polling/webhooks, reconciliation.
Decide by: How long is the work, and can it be left in-doubt? Fast + must-confirm → sync happy path. Slow, or a side-effect you can't lose → async/durable backbone behind it.
🗄️3 · SQL vs NoSQL (store per job)
What store fits this data's access pattern? Resist one-house-DB-for-everything.
ARelational (SQL) — transactions, joins, strong consistency. Money, state machines, anything needing ACID.
BDocument/KV/Wide-col (NoSQL) — massive write scale, flexible schema, denormalized reads. Events, sessions, catalogs.
Decide by: Access pattern, not trend. "How is this read and written?" High-write firehose → wide-column (Cassandra). Transactional core → relational. Often you use several.
🚀4 · Cache or Not — and Invalidation
Read-heavy data almost always wants a cache; the hard part is what key and how it goes stale.
ATTL — simple, accepts staleness up to the window. Great for data that's OK to be a bit old.
BEvent invalidation — fresh, but fragile to dropped events. For data that must reflect writes quickly.
CWrite-through / refresh-ahead — write updates cache too / preemptive reload. Stronger freshness, more moving parts.
Decide by: Pick the cache key at the right granularity (the rate-basis, not the raw input), then "how stale can this be?" Money path → don't cache; browse path → TTL is usually fine.
📬5 · Queue vs Direct Call
When service A needs B to do something — call it directly, or drop a message?
ADirect (sync RPC) — immediate result, simple to trace. A's latency/availability now depends on B.
BQueue (Kafka/SQS) — decoupled, buffers spikes, replayable, survives B being down. Adds eventual delivery + ordering concerns.
Decide by: Does the caller need the answer now, and can B keep up with A's peak? Need-it-now → direct. Fire-and-forget, spiky, or B is slow/flaky → queue. Kafka if you need replay/ordering, SQS if you just need a buffer.
🧱6 · Monolith vs Microservices
One deployable, or many? Beware reaching for microservices reflexively.
AMonolith / modular monolith — simpler ops, no network between modules, easy transactions. Scales as one unit.
BMicroservices — independent scaling + deploys + team ownership. Cost: network failure modes, distributed data, ops overhead.
Decide by: Do parts have genuinely different scaling needs or team boundaries (bounded contexts)? If not, a modular monolith is often the right call — and "I'd start monolith and carve out services as seams appear" is a strong answer.
⚡7 · Build vs Buy / 3rd-Party
Integrate directly with each provider, or use an aggregator / managed service?
ABuild / direct — full control, no per-use fee, but N integrations to build & maintain.
BBuy / aggregator — one integration, they absorb the quirks. Cost: fees, their downtime, less control.
CHybrid by volume — build for the high-volume few where it pays off; buy for the long tail.
Decide by: Volume economics + control needs. A clean adapter interface lets either slot in behind the same port — so this can stay a runtime/ops decision, not an architecture one.
📨8 · Push vs Pull
Does the source push updates to you, or do you poll for them?
APush (webhooks/stream) — fresh, low latency, no wasted polls. Messy infra: retries, ordering, signature verification.
BPull (poll) — deterministic, simple, you control rate. Wasteful and stale between polls.
Decide by: Freshness need vs. infra tolerance. High-volume real-time → push, often with pull as a reconciliation backstop. Low-volume or you don't trust their delivery → pull.
🔑9 · Idempotency & Retries
Any side-effectful op that might be retried (network blip, double-click) forces this.
AClient-supplied key — caller sends a unique key; server dedups. Robust for money flows; needs client discipline.
BServer-side dedup — hash the payload / natural key. Works without client cooperation; trickier to get exactly right.
—Only retry idempotent ops, with backoff + jitter. Never blindly retry a charge.
Decide by: Is the op safe to repeat? If not, make it idempotent before you allow any retry. Money/state-changing → client key, always.
📈10 · Scale Now vs Scale Later
Design for today's load, or the load you might have in 3 years?
ASimple for current scale — ship faster, less to operate. Risk of a painful rewrite if growth is real.
BPre-build for 10×/100× — fewer surprises, but over-engineering you may never need (and that slows you now).
Decide by: Design for ~10× current, not 1000×. The staff finish: "this works at today's load; here's the specific thing that changes at the next order of magnitude" — own the curve without building it all now.
Coding Round

Run this before telling the interviewer you're finished. Bake it into the end of your instructions block so the AI self-verifies too.

Before declaring done, verify:

  • All acceptance criteria from the plan are met
  • Unit tests written and passing; integration test per endpoint (if applicable)
  • No hardcoded values — URLs, timeouts, secrets all externalized
  • Errors handled centrally and return clean, typed responses
  • Correlation ID propagated through logs
  • README updated: how to run, config values, endpoint contract
  • No business logic leaked into handlers or data classes
