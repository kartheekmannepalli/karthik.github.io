Q1
Filter events for a customer's city
You're given Event and Customer classes and a list of events. Implement recommend(customer) that returns the events in the customer's city. This is the warm-up — they grade how you model the domain and shape the interface, not the loop itself.

🎯Clarify before typing (say these out loud)

  • Is matching on a city string or a city/venue ID? (IDs avoid "NYC" vs "New York" bugs.)
  • Case / whitespace sensitivity on the match?
  • Can a customer have no city, or an event no city? What's the expected return — empty list, never null?
  • Roughly how many events — in-memory list, or should I assume a repository/data source behind it?

🧱Domain model — make it immutable & null-safe

Records give you immutability, equals/hashCode, and a tiny footprint. Mention you'd swap to full classes if behavior is needed.

import java.time.*;
import java.util.*;
import java.util.stream.*;

// Use an ID for the city to avoid "NYC" vs "New York" string drift.
public record Event(String id, String name, String cityId,
                    LocalDate date, double lat, double lon) {
    public Event {
        Objects.requireNonNull(id, "id");
        Objects.requireNonNull(cityId, "cityId");  // fail fast at the boundary
    }
}

public record Customer(String id, String cityId, LocalDate birthday,
                       double lat, double lon) {}

🔌The interface = the whole game here

An explicit service interface signals you think in contracts. This is the seam every later requirement plugs into.

public interface EventRecommender {
    List<Event> recommend(Customer customer);
}

public class CityEventRecommender implements EventRecommender {
    private final List<Event> events;   // injected → testable, swappable for a repo

    public CityEventRecommender(List<Event> events) {
        // defensive copy: caller can't mutate our state later
        this.events = List.copyOf(events);
    }

    @Override
    public List<Event> recommend(Customer customer) {
        if (customer == null || customer.cityId() == null) return List.of();
        return events.stream()
            .filter(e -> customer.cityId().equals(e.cityId()))
            .collect(Collectors.toList());
    }
}

Time O(n) · Space O(k). If city lookups dominate, pre-index Map<String,List<Event>> in the constructor → O(1) lookup.

⚠️ Gotchas
  • Never return null — return List.of(). Empty collections beat null checks everywhere downstream.
  • Don't compare cities with == — always .equals() (and put the non-null literal first: customer.cityId().equals(e.cityId())).
  • Defensive-copy the injected list. List.copyOf protects you from a caller mutating it under your feet.
📌 Remember
  • Inject the data source through the constructor — that single decision is what makes Q2–Q5 testable.
  • Say "I'm naming this cityId not city on purpose" — verbalizing the modeling choice is the point.
🗣️ Narrate
"I'll start with an interface so each new requirement is an implementation detail, not a rewrite. I'm modeling city as an ID to dodge string-normalization bugs, returning an empty list instead of null, and injecting the events so I can unit-test without a database."
Q2
Find the event closest to the customer's birthday
Now return the single event whose date is closest to the customer's next birthday. This is where they watch your date/time handling — the trap is treating a birthday as a fixed year.

🎯Clarify (this question is a date-edge-case minefield)

  • "Closest birthday" = the next upcoming birthday, right? Not the literal stored date (which is in the past).
  • If two events tie on distance, what breaks the tie — earlier date? event id?
  • Are dates compared in the customer's timezone or UTC? (Say it; usually LocalDate is fine and avoids the rabbit hole.)
  • What about Feb 29 birthdays in a non-leap year?

🎂Compute the next birthday correctly

// Returns the customer's next birthday on/after `today`. Handles Feb 29.
static LocalDate nextBirthday(LocalDate birthday, LocalDate today) {
    MonthDay md = MonthDay.from(birthday);          // month+day only
    LocalDate thisYear;
    try {
        thisYear = md.atYear(today.getYear());
    } catch (DateTimeException e) {        // Feb 29 in a non-leap year
        thisYear = LocalDate.of(today.getYear(), 2, 28);
    }
    return !thisYear.isBefore(today)
        ? thisYear
        : md.atYear(today.getYear() + 1);   // already passed → next year
}

⚙️Pick the closest event

public Optional<Event> closestToBirthday(Customer c, LocalDate today) {
    LocalDate target = nextBirthday(c.birthday(), today);
    return events.stream()
        .filter(e -> c.cityId().equals(e.cityId()))
        .min(Comparator
            .comparingLong(e -> Math.abs(
                ChronoUnit.DAYS.between(target, ((Event) e).date())))
            .thenComparing(e -> ((Event) e).date())      // tie-break: earlier first
            .thenComparing(e -> ((Event) e).id()));      // fully deterministic
}

Time O(n) single pass via stream().min() · returns Optional so "no events" is explicit, not a null.

⚠️ Gotchas — the date traps they're hunting for
  • Don't subtract years. The stored birthday is in the past; you want the next occurrence. Comparing raw stored dates is the #1 wrong answer.
  • Feb 29. MonthDay.atYear() throws in non-leap years — catch it and fall back to Feb 28 (or Mar 1; ask which).
  • Use ChronoUnit.DAYS.between, never millis/86400000. Manual epoch math breaks on DST/leap seconds.
  • Use LocalDate, not Date. java.util.Date is mutable, 0-indexed months, and deprecated-feeling — interviewers notice.
  • Wrap-around: an event on Dec 31 vs a Jan 2 birthday is 2 days apart, not 363. Anchoring to the next birthday handles this; call it out.
📌 Remember
  • Return Optional<Event> — forces the caller to handle "none found."
  • Add deterministic tie-breakers. Non-deterministic output is an instant red flag and makes tests flaky.
  • Pass today in as a parameter (or inject a Clock) — never call LocalDate.now() inside logic, or you can't unit-test it.
🗣️ Narrate
"Birthdays are recurring, so I compute the next birthday first, then minimize the absolute day-gap. I'm injecting today so this is testable, handling Feb 29 explicitly, and adding tie-breakers so the result is deterministic."
Q3
Return the top-K nearest events by distance
Drop the city filter — now rank all events by geographic distance to the customer and return the K closest. They'll ask: "how would you optimize this?" — the expected answer is a bounded heap, not a full sort.

📐Distance: keep it simple, justify it

For ranking you only need a monotonic distance — squared Euclidean avoids a sqrt per element. For correctness on a globe, mention Haversine.

// Squared distance — fine for RANKING (sqrt is monotonic, so order is preserved).
static double distSq(Customer c, Event e) {
    double dLat = c.lat() - e.lat(), dLon = c.lon() - e.lon();
    return dLat * dLat + dLon * dLon;
}
// If they push on real-world accuracy → Haversine (great-circle distance).

🗻The optimization they want: a max-heap of size K

Full sort is O(n log n). A bounded heap is O(n log k) and O(k) space — the right call when n ≫ k.

public List<Event> topKNearest(Customer c, int k) {
    if (k <= 0) return List.of();
    // MAX-heap on distance: the farthest of our K sits on top, ready to evict.
    PriorityQueue<Event> heap = new PriorityQueue<>(
        Comparator.comparingDouble(e -> -distSq(c, e)));  // negate → max-heap

    for (Event e : events) {
        heap.offer(e);
        if (heap.size() > k) heap.poll();   // evict the farthest, keep K closest
    }
    List<Event> result = new ArrayList<>(heap);
    result.sort(Comparator.comparingDouble(e -> distSq(c, e)));  // closest-first output
    return result;
}

Time O(n log k) · Space O(k). The final sort is O(k log k) — only on the K survivors.

ApproachTimeSpaceWhen
Sort all, take KO(n log n)O(n)K close to n; simplest code
Bounded max-heapO(n log k)O(k)K ≪ n — the interview answer
QuickselectO(n) avgO(1)One-shot, can mutate array, no streaming
⚠️ Gotchas
  • Heap direction is the classic bug. To keep the K closest you need a max-heap so you can evict the farthest. Negate the comparator or use reverseOrder.
  • Don't sqrt per element if you're only ranking — squared distance preserves order. State the assumption.
  • Lat/lon isn't flat. Euclidean is an approximation; for real distances mention Haversine. Don't silently ship the wrong model.
  • k > n and k <= 0 — guard both. Return all (sorted) when k ≥ n.
✅ Senior signal
  • "At StubHub scale I wouldn't scan every event per request — I'd pre-index events spatially (geo-hash / quadtree) or filter by city/region first, then rank within the candidate set." That one sentence shows you see past the toy.
🗣️ Narrate
"Full sort works but it's O(n log n). Since K is small I'll keep a size-K max-heap and evict the farthest as I stream — O(n log k), O(k) space. I'm using squared distance because I only need ranking order, and I'd switch to Haversine if real-world distance matters."
Q4
Call an external API for prices → cheapest events
Each event's current ticket price comes from a mock external API. Fetch prices and return the cheapest events. This is the heart of the "API integration" rubric: timeouts, retries, idempotency, pagination, error handling.

🔌Hide the API behind a port (interface)

Wrapping the client in your own interface = testable (mock it) and swappable. Never let raw HTTP leak into business logic.

public interface PriceClient {
    /** @return price, or empty if unavailable for this event. Never throws on "not found". */
    Optional<BigDecimal> getPrice(String eventId);
}

🛡️Resilient wrapper: timeout · retry w/ backoff · cache

public class ResilientPriceClient implements PriceClient {
    private final PriceApi api;            // the raw mock client
    private final int maxRetries = 3;
    private final Map<String, BigDecimal> cache = new ConcurrentHashMap<>();

    public ResilientPriceClient(PriceApi api) { this.api = api; }

    @Override
    public Optional<BigDecimal> getPrice(String eventId) {
        BigDecimal hit = cache.get(eventId);
        if (hit != null) return Optional.of(hit);   // idempotent reads → cache safely

        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                BigDecimal p = api.fetchPrice(eventId, /*timeoutMs*/ 500);
                if (p != null) cache.put(eventId, p);
                return Optional.ofNullable(p);
            } catch (TimeoutException | TransientApiException ex) {
                if (attempt == maxRetries) {
                    log.warn("price fetch failed eventId={} after {} tries", eventId, attempt, ex);
                    return Optional.empty();        // degrade gracefully, don't crash the batch
                }
                sleep(backoffMs(attempt));            // 100, 200, 400ms + jitter
            }
        }
        return Optional.empty();
    }
    private static long backoffMs(int a) {
        return (long)(Math.pow(2, a - 1) * 100 + Math.random() * 50); // jitter avoids thundering herd
    }
}

💸Cheapest events — skip unpriced, don't fail the batch

public List<Event> cheapest(List<Event> candidates, int k) {
    return candidates.stream()
        .map(e -> Map.entry(e, priceClient.getPrice(e.id())))
        .filter(en -> en.getValue().isPresent())     // drop events we couldn't price
        .sorted(Comparator.comparing(en -> en.getValue().get()))
        .limit(k)
        .map(Map.Entry::getKey)
        .collect(Collectors.toList());
}

If they ask to speed up N calls: batch endpoint if one exists, else a bounded thread pool / CompletableFuture.allOf — but mention rate limits first.

⚠️ Gotchas — the API rubric is where seniors separate
  • Money = BigDecimal, never double. Floating point loses cents. This is a guaranteed look-for.
  • Always set a timeout. A hung dependency must not hang your request. No naked blocking call.
  • Retry only transient errors (timeout, 503), never a 404/400 — retrying a bad request just wastes time.
  • Backoff + jitter, not a tight retry loop, or you DDoS your own dependency (thundering herd).
  • Cache only because reads are idempotent. Say that word — idempotency is on their rubric. Add a TTL since prices change.
  • One bad event ≠ failed batch. Degrade gracefully: skip the unpriced event, log it, keep going.
  • Pagination: if the API returns events in pages, loop until the cursor/next-token is null — don't assume one page.
📌 Remember — observability (their explicit rubric)
  • Log failures with the eventId and attempt count; emit a metric like price.fetch.failure + latency. "In prod I'd want a dashboard + alert on failure rate" earns the observability points.
🗣️ Narrate
"I'll wrap the API in my own PriceClient interface so I can mock it in tests and add resilience in one place: timeout, retry-with-backoff on transient errors only, and a cache because price reads are idempotent. If one event can't be priced I skip and log it rather than failing the whole batch — and I'm using BigDecimal for money."
Q5
Compose filters & scoring cleanly (extensibility)
Final stretch: "How would you combine these strategies — city, date, distance, price — and make it easy to add more without rewriting?" This is the extensibility / clean-design finale. Reach for Strategy + composition.

🧩Two small abstractions: Filter (yes/no) + Scorer (rank)

Separate narrowing the set from ordering the set. Each is a tiny composable unit — open for extension, closed for modification.

// A filter decides membership. Composable via default methods.
@FunctionalInterface
public interface EventFilter {
    boolean matches(Event e, Customer c);

    default EventFilter and(EventFilter other) {
        return (e, c) -> this.matches(e, c) && other.matches(e, c);
    }
}

// A scorer ranks. Higher = better. Combine with weights.
@FunctionalInterface
public interface EventScorer {
    double score(Event e, Customer c);
}

🔧Concrete strategies — each isolated & testable

EventFilter sameCity   = (e, c) -> c.cityId().equals(e.cityId());
EventFilter future     = (e, c) -> !e.date().isBefore(LocalDate.now(clock));

EventScorer nearBirthday = (e, c) ->
    -Math.abs(ChronoUnit.DAYS.between(nextBirthday(c.birthday(), today), e.date()));
EventScorer proximity    = (e, c) -> -distSq(c, e);   // closer = higher

⚙️The engine — data-driven, weighted, easy to extend

public class RecommendationEngine {
    private final EventFilter filter;                 // composed via .and(...)
    private final Map<EventScorer, Double> weighted;  // scorer → weight

    public List<Event> recommend(List<Event> events, Customer c, int k) {
        return events.stream()
            .filter(e -> filter.matches(e, c))
            .sorted(Comparator.comparingDouble(
                (Event e) -> totalScore(e, c)).reversed())
            .limit(k)
            .collect(Collectors.toList());
    }
    private double totalScore(Event e, Customer c) {
        return weighted.entrySet().stream()
            .mapToDouble(en -> en.getKey().score(e, c) * en.getValue())
            .sum();   // add a new signal = add one entry. Zero edits here.
    }
}

// Wiring (Builder makes intent obvious):
var engine = new EngineBuilder()
    .filter(sameCity.and(future))
    .score(proximity, 0.7)
    .score(nearBirthday, 0.3)
    .build();

Adding "boost cheaper tickets" later = write one EventScorer + register it with a weight. No existing code changes → Open/Closed.

⚠️ Gotchas
  • Don't over-engineer. Strategy + a weight map is plenty. Resist a plugin framework / reflection / annotations — they read that as complexity for its own sake.
  • Normalize score scales before weighting, or one signal (e.g. raw distance in the thousands) drowns the others. Mention min-max or z-score normalization.
  • Keep filtering before scoring — scoring everything then discarding wastes work, and an expensive scorer (price API!) should run on the smallest set.
  • If a scorer calls the network (price), fetch once and reuse — don't call the API inside a comparator that runs per-comparison (O(n log n) calls!).
✅ Senior signal — name the principles
  • Strategy pattern for interchangeable filters/scorers · Open/Closed (extend, don't modify) · composition over inheritance · dependency injection for testability. Saying these by name, briefly, lands the "trade-offs & design reasoning" rubric.
🗣️ Narrate
"I'll split this into two roles: filters decide membership and compose with .and(); scorers rank and combine through a weight map. Adding a new signal becomes a one-line registration — Open/Closed — without touching the pipeline. I'll keep it deliberately small; a heavier framework wouldn't earn its complexity here."

E1
Paginate the recommendations
"There are too many results — return them a page at a time." Your doc lists pagination in the assessment rubric, so this is the highest-confidence guess.

Offer offset/limit first (simple), then upgrade to cursor (keyset) pagination and explain why.

public record Page<T>(List<T> items, String nextCursor) {}  // null cursor = last page

// Cursor encodes the last seen sort key, e.g. "score:eventId".
public Page<Event> recommendPage(Customer c, String cursor, int limit) {
    List<Event> ranked = rankedFor(c);   // STABLE, deterministic order (Q2 tie-breaks!)
    int start = (cursor == null) ? 0 : indexAfter(ranked, cursor);
    List<Event> slice = ranked.subList(start, Math.min(start + limit, ranked.size()));
    String next = (start + limit < ranked.size())
        ? cursorOf(slice.get(slice.size() - 1)) : null;
    return new Page<>(slice, next);
}
⚠️ Gotchas
  • Offset pagination drifts when the underlying list changes between pages (new events inserted) → users see dupes or gaps. Cursor/keyset on a stable sort key fixes it.
  • Ordering must be fully deterministic or pages overlap — this is exactly why Q2's tie-breakers matter.
  • Validate limit (cap it; reject 0/negative) and treat a bad cursor as start-of-list, not a crash.
E2
Exclude events the user already has / has seen
"Don't recommend events the customer already bought tickets for or was already notified about." Dedup is core to a real reco/notification system and ties to the idempotency rubric.

Hide the "already seen" state behind an interface; exclude with an O(1) set membership check.

public interface SeenStore {            // owned tickets OR prior sends
    Set<String> seenEventIds(String customerId);
}

public List<Event> recommendUnseen(Customer c, int k) {
    Set<String> seen = seenStore.seenEventIds(c.id());  // HashSet → O(1) contains
    return rankedFor(c).stream()
        .filter(e -> !seen.contains(e.id()))
        .limit(k)
        .collect(Collectors.toList());
}
⚠️ Gotchas
  • Use a Set, not list.contains — the latter is O(n) per check → O(n·m) overall.
  • Where does "seen" live? Per-request it's a DB/cache read; say so. At scale, mention a Bloom filter to cheaply skip definite-not-seen.
  • Don't filter so hard you return nothing — if everything's been seen, fall back (popular/new) rather than an empty list.
E3
Fetch prices concurrently
"Pricing N events one-by-one is too slow — parallelize it." Natural escalation of Q4; tests whether you reach for concurrency safely (bounded, rate-aware).
private final ExecutorService pool = Executors.newFixedThreadPool(8); // BOUNDED, not N threads

public Map<String, BigDecimal> pricesFor(List<Event> events) {
    List<CompletableFuture<Map.Entry<String, BigDecimal>>> futures = events.stream()
        .map(e -> CompletableFuture.supplyAsync(() ->
            priceClient.getPrice(e.id())                 // already resilient (Q4)
                .map(p -> Map.entry(e.id(), p)).orElse(null), pool))
        .toList();

    return futures.stream()
        .map(CompletableFuture::join)
        .filter(Objects::nonNull)              // drop the ones that failed (partial OK)
        .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue));
}
⚠️ Gotchas
  • Bound the pool. Spawning a thread per event will exhaust the dependency and your own resources. A fixed/bounded pool (or a semaphore) is the senior move.
  • Respect the API's rate limit — parallelism that ignores it just gets you throttled. Mention it before optimizing.
  • Partial failure is normal — collect what succeeds, skip/log the rest, don't let one join() failure kill the batch.
  • Cache must be thread-safe (ConcurrentHashMap) once reads go parallel. And remember to shutdown() the pool.
E4
Frequency cap per user (don't spam)
"A user should get at most N notifications per week." Notification-specific, and a clean bridge into the system-design round's frequency-cap discussion.
public interface SendCounter {
    int countSince(String customerId, Instant since);  // sliding window
}

public boolean canNotify(Customer c, int maxPerWeek, Instant now) {
    Instant weekAgo = now.minus(7, ChronoUnit.DAYS);
    return sendCounter.countSince(c.id(), weekAgo) < maxPerWeek;
}
⚠️ Gotchas
  • Fixed calendar windows let bursts through the seam (5 Sun night + 5 Mon morning). A sliding window or token bucket is fairer — name the trade-off.
  • Check-then-send is a race under concurrency — two workers both pass the cap. Make the increment atomic (conditional write / counter), or reserve before sending.
  • Inject now (or a Clock) — same testability rule as Q2.
  • Caps usually differ by channel (email vs push) and respect user prefs — keep it configurable, not hardcoded.
E5
Personalize by followed artists/teams + diversify
StubHub users follow performers and teams. "Boost events for who they follow — but don't return five shows from the same artist." Tests scoring and a diversity constraint; plugs straight into Q5's scorer model.
// 1) Boost via a scorer (composes with Q5's weighted engine).
EventScorer followBoost = (e, c) ->
    c.followedPerformers().contains(e.performerId()) ? 1.0 : 0.0;

// 2) Greedy diversity: cap how many per performer in the final list.
public List<Event> diversify(List<Event> ranked, int k, int maxPerPerformer) {
    Map<String, Integer> seen = new HashMap<>();
    List<Event> out = new ArrayList<>();
    for (Event e : ranked) {                 // ranked = already score-sorted
        int n = seen.getOrDefault(e.performerId(), 0);
        if (n < maxPerPerformer) {
            out.add(e);
            seen.put(e.performerId(), n + 1);
            if (out.size() == k) break;
        }
    }
    return out;
}
⚠️ Gotchas
  • Relevance vs. diversity is a real trade-off — too strict a cap buries the user's favorite artist; too loose and the list is monotonous. Make the cap a parameter and say why.
  • If they push further, name MMR (Maximal Marginal Relevance) as the principled version — score = relevance − λ·similarity to already-picked.
  • Greedy over a score-sorted list keeps it O(n) and deterministic — but only if the upstream sort had tie-breaks.
