Q1
Clarify requirements & size the system
Lead by gathering requirements. Establish users, goals, success criteria, and non-goals — then do quick scale math so every later decision has numbers behind it.

🎯 Questions to ask the PM (out loud, first 5 min)

DimensionAsk
TriggerScheduled digest (daily/weekly) or event-driven (new event near you, price drop)? Both?
ChannelEmail only, or push/SMS too? (Design for one, abstract the rest.)
RelevanceReuse the code-pair logic (city, date, distance, price)? Is there an existing ML reco service I call, or do I build ranking?
ScaleHow many users? Notifications/day? Peak (event on-sale spikes)?
SLAHow fresh? "New event" notification within minutes, or is next-day digest fine?
Non-goalsAm I building the email renderer/ESP, or calling SendGrid/SES? Building the ML model, or calling a reco API? Draw the boundary.

🔢 Back-of-envelope (state assumptions, then derive)

⚠️ Gotchas
  • Don't start drawing boxes before scope is pinned. That's the documented trap. Confirm what you build vs. call.
  • Numbers should drive decisions — "10k/s peak, so I need a queue + N stateless workers," not trivia for its own sake.
  • Separate functional (filter → rank → send → don't double-send) from non-functional (reliability, latency, cost, privacy). The prep doc names all four NFRs — hit each.
📌 Remember — success metrics (PM language)
  • Tie design to business impact: delivery rate, open/click-through, conversion to ticket purchase, unsubscribe rate. "Is it working?" = these dashboards.
Q2
High-level architecture
Draw core services, stores, queues, and integration points. Keep the pipeline legible: trigger → select audience → recommend → render → deliver → track. Decouple stages with queues so each scales independently.

🧩 Why this shape

DecisionWhy · trade-off
Queues between stages (Kafka)Decouple producers from consumers; absorb spikes; replay on failure. Cost: ordering/exactly-once nuance → handle with idempotency, not strict ordering.
Stateless workersScale horizontally on queue depth. Any worker handles any job.
Precompute recos offlineSend-time reads are cheap; ranking isn't on the hot path. Trade-off: slight staleness — fine for digests.
Call ESP, don't build itSES/SendGrid handle deliverability, SPF/DKIM, bounces. Explicit non-goal — say so.
Separate tracking pipelineOpens/clicks via webhook → feeds metrics + future reco signal. Closes the "is it working?" loop.
📌 Remember
  • Narrate the data flow as a story: "a trigger fans out into per-user jobs on a queue; a reco worker attaches the best events; a render worker stamps an idempotency key; a sender hands off to the ESP; webhooks feed tracking." A clear narrative beats a busy diagram.
Q3
Relevance: recommendation + fallback
This is where the code-pair scenario plugs in. How do you pick which events go to which user — and what happens when personalized recos aren't available? Fallback strategy was explicitly probed in 2026 interviews.

🔌 Build vs. call

Say it explicitly: candidate-gen + simple scoring (the code-pair logic) you can own; a heavy ML model is likely an existing service you call. Either way, wrap it behind an interface so the fallback ladder is uniform.

⚠️ Gotchas
  • Cold start. New user with no history → ladder drops to popular/trending. Never send an empty email.
  • Reco service down ≠ no email. Circuit-break to the next ladder rung; degrade relevance, not delivery.
  • Frequency caps & dedup. Don't re-send the same event; respect "max N emails/week." Lives in user prefs + sent-log.
  • Precompute vs. real-time. Daily digest → precompute nightly. "New event near you" → must rank in near-real-time off the event stream. Different freshness, possibly different paths.
✅ Senior signal
  • Tie relevance back to metrics: "I'd A/B test ranking variants and watch click-through + purchase conversion, not just opens." Feeding tracking events back as future ranking features closes the loop.
Q4
Reliable delivery: idempotency, retries, failure
The reliability core. Guarantee at-least-once delivery without double-sending, handle ESP failures, and isolate poison messages. This mirrors the code-pair API rubric at system scale.

🔑 The idempotency story (say this clearly)

ConcernMechanism
No double-sendDeterministic key userId + campaign + date. Worker checks sent-log before calling ESP; conditional write (putIfAbsent) wins the race.
At-least-onceQueue redelivers on no-ack (worker crash). Idempotency makes redelivery safe → effectively exactly-once effect.
Transient failureESP timeout/5xx → retry with exponential backoff + jitter, capped attempts.
Permanent failureHard bounce / invalid address / repeated failure → Dead Letter Queue, alert, don't retry forever.
OrderingMostly don't need it for notifications — lean on idempotency instead of strict ordering (simpler, scales better).
⚠️ Gotchas
  • The classic race: worker sends, crashes before marking sent → redelivery double-sends. Fix: write the idempotency record conditionally, and/or mark "in-flight" before the ESP call.
  • Retry only transient errors. Retrying a hard bounce wastes quota and can hurt sender reputation.
  • Poison messages (a job that always fails) will jam a queue — route to DLQ after N attempts so the pipeline keeps flowing.
  • Respect unsubscribe instantly — checked at send time, never cached stale. A wrongful send is a compliance issue.
📌 Remember — privacy (a named NFR)
  • PII (email, location) encrypted at rest + in transit; honor opt-out / CAN-SPAM / GDPR; minimize PII in logs and queue payloads (pass IDs, hydrate late).
Q5
Scale, observability & shipping safely
Close strong on operations: scaling strategy, the metrics that answer "is it working?", and a safe rollout (flags, backfill, instrumentation) — all named in the prep doc.

📈 Scaling strategy

LeverHow
WorkersStateless; autoscale on queue depth / lag. Peak ~10k/s handled by adding consumers.
Fan-outOne trigger → millions of per-user jobs. Partition the queue by userId for parallelism + even spread.
Hot dataCache user prefs + precomputed recos (Redis). Sent-log in a fast KV store with TTL.
ESP limitsRate-limit toward the ESP (token bucket) to respect provider quotas; smooth the burst.
CostPrecompute offline (cheap batch) vs. real-time only where freshness demands. Batch ESP calls if supported.

📊 Observability — "is it working?"

🚦 Ship safely

StepDetail
Feature flagsRoll out to 1% → 10% → 100%. Kill switch per channel/campaign.
Shadow / dry-runRun reco + render, log what would send before actually sending — catches bad templates.
Backfill / migrationFor existing users, backfill prefs/recos in batches with rate control; idempotency makes reruns safe.
Instrumentation firstShip metrics + dashboards before the feature so you can prove it's working day one.
✅ Strong close (last 2 min)
  • Summarize the 3 hardest trade-offs you made (precompute vs. real-time · at-least-once + idempotency vs. exactly-once · build ranking vs. call reco service).
  • Name what you'd do next with more time: multi-channel abstraction, ML ranking with the tracking feedback loop, regional sharding for latency/privacy.
📌 Remember — the framing they grade
  • You lead, PM guides pacing. Drive the structure but check in: "Does this scope match what you had in mind?"
  • Explain it so junior engineers could build it — clear contracts, named components, obvious ownership.
  • Every choice = a trade-off + business impact sentence, not just a technology name.
