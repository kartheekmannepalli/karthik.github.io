Design the Receipt Processing Backend

VERY HIGH · CONFIRMED ON GLASSDOOR
Photo upload → extract items → match offers → award points. 5M receipts/day, zero double-awarding, even under failures.

Architecture — async pipeline

1Upload → S3, enqueue, return 202
2OCR worker pulls from SQS
3Match vs Redis-cached catalog
4Award idempotent ledger insert
5Notify push "You earned 250 pts"

Key code — idempotent consumer

@SqsListener("receipt-processing")
@Transactional
public void process(ReceiptMessage msg) {
  ParsedReceipt r = ocr.parse(msg.s3Key());
  List<OfferMatch> hits = matcher.match(r.items());

  // receipt hash = natural idempotency key
  String idemKey = sha256(msg.userId() + r.retailer()
                          + r.date() + r.total());

  // SQS = at-least-once ⇒ consumer must dedupe
  int n = jdbc.update("""
    INSERT INTO points_ledger
      (idem_key, user_id, points, receipt_id)
    VALUES (?,?,?,?)
    ON CONFLICT (idem_key) DO NOTHING""",
    idemKey, msg.userId(), total(hits), r.id());

  if (n == 0) log.info("dup redelivery — skipped");
}

⚠️ Gotchas

Exactly-once is a myth

SQS is at-least-once. Don't claim exactly-once delivery — claim at-least-once + idempotent consumer. That's the answer they want.

Sync vs async — say why

5M/day ≈ 60/sec avg, 10× at peak. OCR takes seconds → blocking HTTP would melt. Queue decouples ingest rate from process rate.

Where dedupe lives

DB unique constraint, not app memory — survives worker crashes and multiple instances. Hash the receipt content, not the upload event.

Poison messages

Unparseable receipt retried forever blocks the queue. maxReceiveCount=3 → DLQ → human review + user notified.

Follow-ups to expect

What if OCR is slow/down?

Circuit breaker → receipts stay queued, nothing lost. User sees "Processing" status.

How does the user know it's done?

Push notification / websocket; or app polls a status endpoint backed by receipt state machine: UPLOADED→PARSED→AWARDED.

Same receipt scanned twice?

Same content hash → same idem_key → second insert no-ops. Fraud, not failure — also flag the user.

Scale OCR workers?

Autoscale on queue depth (ApproximateNumberOfMessages), not CPU.

Design the Points Ledger System

HIGH · POINTS = MONEY
20M users. No double-award, atomic redemptions (never negative), full audit trail, balance reconstructable at any point in time.

Architecture — event-sourced ledger

1Every change = INSERT +award / −redeem
2idem_key unique blocks double-award
3Balance = SUM(delta) derived, not stored truth
4Reads hit async materialized view
5Audit replay events to any timestamp

Key code — atomic redemption

// guard + insert in ONE statement — no read-then-write race
public void redeem(long userId, long pts, String idemKey) {
  int n = jdbc.update("""
    INSERT INTO ledger_events (user_id, delta, type, idem_key)
    SELECT ?, -?, 'REDEEM', ?
    WHERE (SELECT COALESCE(SUM(delta),0)
           FROM ledger_events WHERE user_id = ?) >= ?
    ON CONFLICT (idem_key) DO NOTHING""",
    userId, pts, idemKey, userId, pts);

  if (n == 0) throw new InsufficientPointsException();
}
// concurrent redeems on same user: SERIALIZABLE isolation
// (or SELECT … FOR UPDATE on a user row) — pick one, say why

⚠️ Gotchas

"Why not a balance column?"

The guaranteed follow-up. Mutable balance = lost audit trail + race conditions (read-modify-write). Events give you both for free.

SUM over millions of rows?

Don't recompute from t=0. Periodic snapshots + sum events since last snapshot. Materialized view serves reads.

Two redeems, same instant

Two single-statement guards can both pass under READ COMMITTED. Need SERIALIZABLE, per-user advisory lock, or optimistic version check.

View lags the log

Balance view is eventually consistent — fine for display, never for redemption checks. Redeem always validates against the event log.

Follow-ups to expect

Reverse a fraudulent award?

Never delete — append a compensating event (−delta, type=REVERSAL, ref to original).

Balance on June 1st?

SUM(delta) WHERE ts ≤ '2026-06-01' — free time travel from append-only.

Shard at 20M users?

Partition by user_id — all of a user's events co-located, balance query stays single-shard.

Partner billing correct?

Nightly reconciliation job: sum awards per brand vs billed amount; mismatches alert.

Handle Super Bowl Sunday — 20× Traffic Spike

HIGH · REAL FETCH CAMPAIGN
Millions scan snack receipts simultaneously. No degradation, no data loss, no double-awards during the surge.

Architecture — the queue absorbs, workers drain

1Pre-scale before kickoff, not reactive
2Accept everything 202 + queue, never reject
3Drain at own pace workers scale on depth
4Degrade gracefully "Processing…" not errors
5Idempotency holds dedupe unchanged at 20×

Key code — protect the pipeline

// Resilience4j: OCR vendor slows down ≠ pipeline dies
@CircuitBreaker(name = "ocr", fallbackMethod = "deferParse")
@Bulkhead(name = "ocr")  // cap concurrent calls
public ParsedReceipt parse(String s3Key) {
  return ocrClient.parse(s3Key);
}

ParsedReceipt deferParse(String s3Key, Throwable t) {
  retryQueue.send(s3Key);          // never drop a receipt
  return ParsedReceipt.pending(); // user: "Processing…"
}
# scale consumers on backlog, not CPU
spring.cloud.aws.sqs.listener.max-concurrent-messages: 50
autoscaling.metric: ApproximateNumberOfMessagesVisible

⚠️ Gotchas

The DB is the real bottleneck

You can scale workers infinitely — Postgres can't. Read replicas for catalog reads, writes throttled by worker concurrency. Don't let the queue drain faster than the DB can absorb.

Connection pool exhaustion

50 workers × 10 connections = dead DB. Cap HikariCP pool, consider RDS Proxy / PgBouncer. Classic spike failure.

Don't cold-autoscale

Reactive autoscaling lags minutes; the halftime spike is instant. Pre-provision — Fetch knows the date.

Name the tradeoff

Strong consistency during peak vs eventual consistency with guaranteed delivery. Points arrive 5 min late > app down.

Follow-ups to expect

Queue backs up 30 min?

Fine by design — uploads still accepted, UI shows pending. Alert on depth trend, scale workers, communicate in-app.

Redis dies at peak?

Fallback to read replicas + local caffeine cache of hot offers. Matching slows; doesn't stop.

How do you know it worked?

SLO: p99 receipt→points latency. Dashboards: queue depth, DLQ rate, DB CPU, award rate vs upload rate.

Cost of pre-scaling?

Hours of over-provisioning vs revenue of the year's biggest campaign — trivially worth it. Scale down after.

Design the Offer Recommendation Engine

MED-HIGH · PERSONALIZATION
Personalized offer feed for 20M users from purchase history. Offers change daily. Home screen must load < 200ms.

Architecture — precompute offline, serve from cache

1Nightly score user×offer pairs offline
2Materialize top-20 per user → Redis
3Serve one Redis GET, ~1ms
4Fallback regional popular on miss
5Filter frequency cap + A/B at edge

Key code — serve path with fallback

@GetMapping("/feed")
public List<Offer> feed(@AuthenticationPrincipal User u) {
  List<Offer> top = redis.opsForList()
      .range("feed:" + u.id(), 0, 19);

  if (top == null || top.isEmpty())          // new user / TTL miss
    top = popularOffers.byRegion(u.region()); // cheap, cached

  return frequencyCap.filter(u.id(), top);   // ≤3 views/offer/wk
}

// nightly: 20M users scored offline — NEVER on request:
// 20M users × 10K offers = 200B pairs. That's the "why not
// real-time?" answer.

⚠️ Gotchas

"Why not score in real time?"

The guaranteed follow-up. 200B user-offer pairs can't be ranked per-request in 200ms. Precompute; spend the latency budget on one cache read.

Cold start users

No purchase history = no scores. Fallback chain: regional popular → global popular. Feed must never be empty.

Offer expires mid-day

24h TTL means a dead offer can sit in feeds. Filter against an active-offer set at serve time — cheap SISMEMBER check.

Batch job fails overnight

Yesterday's feed (stale) beats no feed. Keep TTL > job interval, alert on job lag, don't fail open to empty.

Follow-ups to expect

Make it fresher than 24h?

Hybrid: batch base scores + lightweight online re-rank on today's scans (e.g. boost categories user scanned this morning).

Measure relevance?

Offer click-through + scan-through rate per ranking variant — the A/B layer exists for exactly this.

Redis memory at 20M?

20M × 20 offer IDs ≈ small. Store IDs only, hydrate offer details from a shared catalog cache.

Sponsored offers?

Blend rule: ad slots injected at fixed positions post-ranking — keep relevance and revenue ranking separable.

Design Multi-Source Receipt Ingestion

MEDIUM · EXTENSIBILITY
Photo, eReceipt (email), POS API, browser extension → one unified pipeline, no duplicated business logic, no double-counting the same purchase.

Architecture — adapters normalize, pipeline stays source-agnostic

1Adapter per source isolates messy formats
2Normalize to one canonical Receipt event
3Single topic downstream is source-blind
4Dedup same purchase via 2 sources = 1 award
5DLQ per-source parse failures quarantined

Key code — adapter pattern

public interface ReceiptSourceAdapter {
  boolean supports(IngestEvent raw);
  NormalizedReceipt normalize(IngestEvent raw);
}

@Service
public class IngestionService {
  private final List<ReceiptSourceAdapter> adapters; // Spring injects all

  public void ingest(IngestEvent raw) {
    NormalizedReceipt r = adapters.stream()
        .filter(a -> a.supports(raw)).findFirst()
        .orElseThrow(UnknownSourceException::new)
        .normalize(raw);

    r.setDedupKey(sha256(r.userId() + r.retailer()
                       + r.date() + r.total()));
    sqs.send("receipts-normalized", r); // one topic, v1 schema
  }
}
// new source = new @Component implementing the interface. Done.

⚠️ Gotchas

Cross-source dedup is fuzzy

Photo total $42.97 vs eReceipt $42.97 + different timestamp formats. Normalize date to purchase-date, round totals, consider retailer order-ID when available.

Schema evolution

Version the NormalizedReceipt (v1, v2). Additive changes only; consumers tolerate unknown fields. Otherwise every new source risks breaking downstream.

Sources have different trust

POS API data is ground truth; OCR is guesses. Carry a confidence/source field — fraud rules and matching can weight it.

One bad source ≠ outage

Email parser breaks on a new retailer template → only EmailAdapter's DLQ fills. Per-source metrics and isolation.

Follow-ups to expect

"How do you add a 5th source?"

The scripted follow-up: one new adapter, zero pipeline changes. Say it before they ask.

Same purchase, photo + email?

Both normalize → same dedup hash → second one no-ops at the ledger. One award.

Where does OCR fit now?

Inside PhotoAdapter only — it's a source detail, not pipeline logic. Email parsing likewise lives in EmailAdapter.

Adapter in-process or service?

Start as Spring components in one service; split heavy ones (OCR) into their own deployables when scale demands.
