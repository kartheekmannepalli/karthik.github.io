🔴 VERY HIGH · DATA GROUPING & AGGREGATION

1 · Receipt Totals per User, Sorted by Spend

Group transactions (userId, brandId, amount, date) by user → total spend, txn count, top brand by spend → sort by total spend desc.

Data Flow

Structure to Use

🗂️
HashMap<String, Agg> — accumulate totals in one pass, O(n)
📊
Nested Map<brand, sum> per user → Collections.max for top brand
↕️
Sort at the end, not during — Comparator.reversed()
🧾
Java records for clean input/output types
record Txn(String userId, String brandId, double amount, LocalDate date) {}
record UserSummary(String userId, double totalSpend, int txnCount, String topBrand) {}

static List<UserSummary> summarize(List<Txn> txns) {
    record Agg(double[] total, int[] count, Map<String, Double> brandSpend) {}
    Map<String, Agg> byUser = new HashMap<>();

    for (Txn t : txns) {                                  // single pass
        Agg a = byUser.computeIfAbsent(t.userId(),
                k -> new Agg(new double[1], new int[1], new HashMap<>()));
        a.total()[0] += t.amount();
        a.count()[0]++;
        a.brandSpend().merge(t.brandId(), t.amount(), Double::sum);
    }

    return byUser.entrySet().stream()
        .map(e -> new UserSummary(
            e.getKey(),
            e.getValue().total()[0],
            e.getValue().count()[0],
            Collections.max(e.getValue().brandSpend().entrySet(),
                            Map.Entry.comparingByValue()).getKey()))
        .sorted(Comparator.comparingDouble(UserSummary::totalSpend).reversed())
        .toList();
}
➕ Follow-up: "filter to last 30 days" → t.date().isAfter(cutoff) guard in the loop ➕ Follow-up: "add rank field" → index after sort (mind ties) ⚠️ Money as double — say "BigDecimal / cents in production" ⚠️ Top-brand ties — ask how to break them

2 · Loyalty Points System — Class Design

Design Users, Receipts, BrandOffers, PointsLedger. Define interfaces + interactions, then implement points calc for one scan.

Service-Layer Class Diagram

Structure to Use

🎭
Behavior-first interfaces — service orchestrates 3 collaborators
🧮
Strategy pattern — PointsCalculator swappable (promos, multipliers)
📒
Ledger = append-only credits, not a mutable balance field
📦
Records for data, classes/interfaces for behavior
// ---- Data carriers: thin, immutable ----
record LineItem(String description, double amount) {}
record Receipt(String id, String userId, List<LineItem> items, Instant scannedAt) {}
record BrandOffer(String brandKeyword, int pointsPerDollar) {}
record PointsResult(String receiptId, int pointsAwarded) {}

// ---- Behavior: interfaces ----
interface PointsCalculator { int calculate(Receipt receipt, List<BrandOffer> offers); }
interface PointsLedger    { void credit(String userId, int pts, String receiptId);
                            int balance(String userId); }   // sum of entries = audit trail
interface OfferRepository { List<BrandOffer> activeOffersFor(Receipt receipt); }

// ---- Orchestrator: what the interviewer wants to see ----
class ReceiptScanService {
    private final OfferRepository offers;
    private final PointsCalculator calculator;
    private final PointsLedger ledger;

    ReceiptScanService(OfferRepository o, PointsCalculator c, PointsLedger l) {
        this.offers = o; this.calculator = c; this.ledger = l;
    }

    PointsResult scan(Receipt receipt) {
        List<BrandOffer> active = offers.activeOffersFor(receipt);
        int points = calculator.calculate(receipt, active);
        ledger.credit(receipt.userId(), points, receipt.id());
        return new PointsResult(receipt.id(), points);
    }
}

// ---- One concrete strategy: the asked-for calculation ----
class StandardPointsCalculator implements PointsCalculator {
    public int calculate(Receipt r, List<BrandOffer> offers) {
        int total = 0;
        for (LineItem item : r.items())
            for (BrandOffer o : offers)
                if (item.description().toLowerCase().contains(o.brandKeyword().toLowerCase()))
                    total += (int) (item.amount() * o.pointsPerDollar());
        return total;
    }
}
⚡ The confirmed trap (Glassdoor Feb 2025): candidates who modeled DB entities/ER diagrams failed. Lead with method signatures and interactions — say "behavior first, storage later."
➕ Follow-up: "2x-points promo" → new PointsCalculator impl, zero service changes ➕ Follow-up: "redeem points" → ledger.debit() + guard balance ≥ 0 ⚠️ Don't put calculate() inside Receipt — anemic data + separate behavior

3 · Match Receipt Items to Highest-Value Offers

Items like "Pepsi 12pk" + catalog Map<keyword → points> → match each item to its highest-value offer, return total points.

Matching Pipeline

Structure to Use

🔤
Token Set per item — lowercase, split on whitespace
🗺️
Multi-word keywords: match if all keyword tokens ⊆ item tokens
🏆
Best-match per item — Math.max, not sum (confirm with interviewer!)
⏱️
O(items × keywords) — fine here; inverted index at scale
static int totalPoints(List<String> items, Map<String, Integer> catalog) {
    int total = 0;
    for (String item : items) {
        Set<String> tokens = new HashSet<>(
            Arrays.asList(item.toLowerCase().split("\\s+")));

        int best = 0;                                  // no match → 0 pts
        for (Map.Entry<String, Integer> offer : catalog.entrySet()) {
            String[] kw = offer.getKey().toLowerCase().split("\\s+");
            boolean matches = Arrays.stream(kw).allMatch(tokens::contains);
            if (matches) best = Math.max(best, offer.getValue());
        }
        total += best;                                 // highest-value offer wins
    }
    return total;
}
➕ Follow-up: "multiple matches — highest or sum?" → ask; default highest (code above) ➕ Follow-up: scale → inverted index Map<token → offers>, O(item tokens) ⚠️ Naive contains(): "pepsi" matches "Diet Pepsi" — wrong tier. Tokens fix it ⚠️ Set.of(tokens) throws on duplicates ("Coke Coke 2pk") — HashSet is safe
🟣 MEDIUM-HIGH · BACKEND · IDEMPOTENCY

4 · Idempotent Receipt Processor

Same receipt (retailer + date + total) submitted twice must not award points twice — return the existing result.

Dedup Flow

Structure to Use

🔑
Deterministic ID = hash of retailer|date|total → same receipt, same key
🧵
ConcurrentHashMap.computeIfAbsent — atomic check-and-process
📤
Return cached result — duplicates get 200 + original result, not an error
🚀
Scale: Redis SET NX EX (TTL), not in-memory
record Receipt(String retailer, LocalDate date, double total, List<String> items) {}
record PointsResult(String receiptId, int pointsAwarded, boolean duplicate) {}

class ReceiptProcessor {
    private final Map<String, PointsResult> processed = new ConcurrentHashMap<>();

    PointsResult process(Receipt r) {
        String key = idempotencyKey(r);
        // atomic: expensive work runs exactly once per key, even under races
        return processed.computeIfAbsent(key, k ->
            new PointsResult(k, calculatePoints(r), false));
    }

    private String idempotencyKey(Receipt r) {
        String raw = r.retailer() + "|" + r.date() + "|" + r.total();
        return sha256(raw);             // stable, collision-safe enough here
    }

    private int calculatePoints(Receipt r) { return (int)(r.total() * 100); }

    private static String sha256(String s) {
        try {
            byte[] h = MessageDigest.getInstance("SHA-256")
                                    .digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(h);
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}
➕ Follow-up: "1M receipts/day?" → Redis SET key NX EX 86400, results in DB ➕ Follow-up: "two legit identical purchases same day?" → raise it yourself: key needs userId + items or client-generated requestId ⚠️ if(containsKey) then put = race condition. Say "atomic" out loud ⚠️ Never throw on duplicate — idempotent means same response
🟡 MEDIUM · EXTENSIBILITY · OPEN-CLOSED

5 · Multi-Source Receipt Ingestion Pipeline

Photo receipts today; add eReceipts (email) + POS digital receipts — one pipeline, no duplicated processing logic.

Plug-in Architecture

Structure to Use

🔌
ReceiptSource interface — only parse() varies per source
📇
Registry (injected list) selects source — no switch statements
🧱
Canonical Receipt model — pipeline never sees raw formats
♻️
Open-closed: new source = new class, zero processor edits
record RawPayload(String sourceType, byte[] data) {}

// Only parsing varies per source — everything downstream is shared
interface ReceiptSource {
    boolean supports(String sourceType);
    Receipt parse(RawPayload payload);          // → canonical Receipt
}

class PhotoReceiptSource implements ReceiptSource {
    public boolean supports(String t) { return "PHOTO".equals(t); }
    public Receipt parse(RawPayload p) { /* OCR pipeline */ return ocr(p.data()); }
}
class EReceiptSource implements ReceiptSource {
    public boolean supports(String t) { return "EMAIL".equals(t); }
    public Receipt parse(RawPayload p) { /* MIME/HTML parsing */ return fromEmail(p.data()); }
}
class PosReceiptSource implements ReceiptSource {
    public boolean supports(String t) { return "POS".equals(t); }
    public Receipt parse(RawPayload p) { /* structured JSON */ return fromJson(p.data()); }
}

class ReceiptIngestionService {
    private final List<ReceiptSource> sources;   // registry — DI injects all impls
    private final ReceiptProcessor processor;     // Q4's idempotent processor, reused

    ReceiptIngestionService(List<ReceiptSource> sources, ReceiptProcessor processor) {
        this.sources = sources; this.processor = processor;
    }

    PointsResult ingest(RawPayload payload) {
        ReceiptSource src = sources.stream()
            .filter(s -> s.supports(payload.sourceType()))
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException(
                "Unsupported source: " + payload.sourceType()));

        Receipt receipt = src.parse(payload);     // the ONLY source-specific step
        return processor.process(receipt);        // shared: dedupe → points → store
    }
}
⚡ The interviewer's test: "add a new source in 5 minutes." If you must edit ReceiptIngestionService or the processor — you over-coupled. Here: write one class, add to the list. Done.
➕ Follow-up: per-source confidence → add confidence() to Receipt; pipeline flags low-OCR for review ➕ Follow-up: async sources → queue per source, same pipeline consumes canonical Receipts ⚠️ switch(sourceType) inside the service = the coupling they're probing for ⚠️ Don't let raw photo/email types leak past parse() — canonical model is the boundary
